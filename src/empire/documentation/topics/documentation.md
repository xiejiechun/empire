# 文档分工与更新

## 各处负责什么

| 要查的内容 | 唯一主要查阅位置 | 更新负责人 |
| --- | --- | --- |
| 打开页面、筛选、采集、保存、生效、失败处理 | 日常操作 / 故障处理 | 改动对应页面或公共流程的开发者 |
| 数据范围、单位、日期、缺值、用途限制、更新生命周期 | 数据说明的对应业务手册 | 该采集/查询功能开发者 |
| MySQL 每张表的字段、主键、索引、读写归属 | 数据库参考 → MySQL | 数据集写入与查询契约开发者 |
| Redis 每类键的内容、拥有者、期限、清理、丢失恢复 | 数据库参考 → Redis | 公共基础设施/队列/任务服务开发者 |
| 插件边界、网络协议、维护迁移和测试要求 | 技术参考及 docs 专项开发指南 | 改动该公共路径或来源契约的开发者 |
| 当时实际采完范围、抽查、修复和发布事实 | docs/evidence；docs/implementation-status.md 汇总 | 执行验收和交付的开发者 |

## 使用者怎么查

先按目的选择目录；要查表/键直接打开 [数据库职责与查阅](help:数据库职责与查阅)，也可以搜索 stock、collection_state、checkpoint、rate 等名称。数据说明讲业务意义，数据库条目讲存储契约，技术流程通过链接引用条目，字段字典只在对应对象页维护。

## 开发者什么时候更新

实现同一功能的人负责把操作、业务、存储与开发说明一起完成，不能留给后续开发者补。新增/改表或 Redis 键要登记独立条目；改字段、索引、值契约、期限、清理或读写方须同步对应页。先更新本业务权威片段和覆盖登记，生成阅读器聚合物后再显式 review，文档检查通过后执行本次必要回归及发布门禁。

当前门禁核对页面、任务、全部 MySQL 表/字段/索引/约束、Redis 命名构造及逐项归属，并检查对应源码和正文审阅是否过期；缺项拒绝交付。Redis 的静态检查覆盖现有命名构造方式，新构造方式需补检查规则，语义正确仍须实际审阅。

## 正文维护位置

业务正文按完整主题放在本业务包的 docs/help 目录，共享说明位于 empire/documentation/topics；help-index.json 只声明归属、来源和阅读顺序。阅读器使用的 storage_reference.md 是自动生成资源。开发者在发布冻结前显式生成；缺少生成、主题关联失效或聚合字节被手改都会被门禁拒绝，审阅也不能在过期聚合物上通过。用户仍从说明文档入口搜索、选择章节和打开相关链接。

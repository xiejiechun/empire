# 开始使用

先查看已归档数据，再按需要更新；在“数据准备”检查这份数据能否用于你的用途。

## 第一次使用

1. 在“系统设置 → 运行状态”确认 MySQL、Redis 和所需插件就绪。
2. 打开“数据浏览 → 数据目录”，按名称、分类、来源或表名搜索，再打开数据页。
3. 数据缺失或过旧时，到“采集管理 → 采集任务”选择对应任务，启用并保存后立即采集。
4. 等待归档确认，再刷新数据页；最后查看“数据准备”的范围、缺口和质量检查。

Alt+1 工作台，Alt+2 股票列表，Alt+3 采集任务，F1 说明文档；Ctrl+F 聚焦查找。时间统一显示北京时间。滚轮只滚动页面，不改变数字、日期、下拉框或滑块值。

## 规划不等于已开发

“数据准备”规划 80 项采集工作和 12 项整理、计算、核对工作。未接入项仍是开发计划。已接入功能也不表示全市场、全历史已经采完；实时状态以正式查询、范围检查和运行记录为准。

开盘啦历史分时与竞价提供独立采集任务和已归档查询入口。当前股票池不包含已退市证券；竞价同一分钟可能有多点，来源仅给分钟标签，不能据此还原秒级委托或完整逐笔成交。支持范围不代表已经采完，详见 [开盘啦分时及竞价](help:开盘啦分时及竞价)。

## 用途边界

当前股票列表不提供历史任意时点股票池。新闻不承诺全历史补齐。财报缺公告日期，不宣称历史公告前选股可用。严格历史版本回放、跨来源核对、单季度和 TTM 计算不是现有采集的通用承诺。

# 查找与浏览数据

## 打开数据页

进入“数据浏览 → 数据目录”，按名称、分类、来源或业务表名检索；每页 25 项。打开的数据页按需创建，返回目录保留筛选、分页和选择。

## 查询与明细

股票支持市场、代码和名称；新闻支持搜索、重点和翻页；日历按月；停复牌按来源日历日期；增发送配及财报按证券代码前缀。点击“查询 / 刷新”，选中一条查看详情，不把未归档响应当成查询结果。

刷新失败时已有数据可能继续显示，须查看失败提示和上次成功读取时间。已归档数据来自 MySQL，Redis 暂不可用不应阻止普通浏览。

## 复制与跳转

支持复制的表格可用 Ctrl 或 Shift 多选，再 Ctrl+C 或“复制选中行”；复制内容带列标题。分页不保留隐藏选择。带“管理采集计划”的数据页可以直接定位关联任务，并保留原筛选及其他任务草稿。

## 如何判断数据是否可用

[数据准备](help:数据准备) 检查声明范围和用途；[采集进度与运行记录](help:采集进度与运行记录) 区分入队、归档和写入。

# 执行采集与计划

**入口：采集管理 → 采集任务。**

## 手动执行

1. 在“采集任务”左侧展开一级数据来源（新浪财经、巨潮资讯、通达信、同花顺等），选择二级具体任务；支持名称、分类、来源及状态筛选，每页最多 25 个任务。一级来源仅用于分组，不能启动或配置整个来源。
2. 确认任务已启用；修改启用状态后先保存。
3. 点击“立即采集”，已有断点会继续执行。
4. 在“运行记录”查看结果。归档完成前，数据页面仍可能显示上一次结果。

“重新采集”用于明确重新建立采集批次。股票重新拉取完整列表，新闻从最新一页开始，日历重新核验全部范围；已有 MySQL 业务数据不会直接清空。

## 自动更新

| 方式 | 执行规则 |
| --- | --- |
| 仅手动 | 点击采集时才运行。 |
| 固定间隔 | 从每次任务结束后等待 1～2592000 秒，同一任务不会重叠。 |
| 每日定时 | 按北京时间在选定时刻执行，应用需要保持运行。 |

任务菜单与详情独立显示，宽窗口左右分栏、窄窗口上下布局。来源括号中的数量仅指当前筛选的本页任务，不代表全部来源数量。刷新保留菜单选择、展开状态和滚动位置；切换任务或分页保留按任务保存的未保存草稿。

右侧顶部显示任务名称、来源和分类；悬停任务名称可查看任务 ID，业务说明位于运行详情内。立即/继续采集、暂停任务、重新采集在同一行，暂停仍会关闭后续计划并保留断点，重新采集会建立新批次。一级来源仅显示选任务提示，不展示空的详情表。

下方分为“运行详情”和“任务配置”。宽详情区将状态与进度、时间与计划并排显示，网络及异常随后展示；空间不足时自动改为纵向。长说明和完整错误在详情内部滚动，菜单、操作栏和配置保存栏保持在内容滚动区外；较小窗口仍可滚动整页访问底部操作。配置字段宽时按标签/输入两列对齐，窄时换行，保存和撤销只在配置标签底部出现。菜单分页采用简短页码及上一页/下一页箭头，悬停显示完整分页信息。

修改后点击“保存执行计划”。配置立即写入 MySQL，电脑重启后保留；未保存草稿不保证跨重启恢复。暂停任务会同时保存禁用状态，恢复前需重新启用并保存。

# 代理与站点速度

**入口：采集管理 → 站点访问规则 / 采集出口。**

## 网站访问速度

在“站点访问规则”保存“每个出口 IP 访问本站的最短间隔”。自动模式随独立出口 IP 增减容量；同一 `exit_ip` 的多个设备共享间隔和一个同站点在途槽。高级设置包含本机直连接口、最多同时请求数和可选的全站每秒保护；全站频率保护默认关闭。新浪股票与新闻共享 sina 组，巨潮使用 cninfo 组。

任务间隔控制多久采集一次，网站间隔控制请求多快，业务消息入队立即唤醒归档器（另有 60 秒恢复扫描），三者独立。

## 使用代理提速

在任务执行计划中选择“本机直连”“代理优先，暂不可用时自动直连”或“仅使用代理”，然后保存；下一轮采集生效。所有新任务统一默认代理优先，后续显式保存的选择不会在启动时重置；保存设置不会把当前运行切换到另一出口。

“采集管理 → 采集出口”显示设备编号、无凭据代理入口（主机/IP 与端口）、出口 IP、协议、可用状态、使用中/可用并发和最近 10 秒请求率；账号、密码和完整认证连接串不会显示。设备离线或目录过期会停止分配，新加入或重新上线会自动恢复。任务详情显示可用并发及该采集器是否支持多页同时下载。

以每出口 IP 2,000 毫秒为例：2 个独立出口理论合计每秒 1 次，20 个为 10 次，50 个为 25 次。全局下载窗口默认 128、最多 1024；站点并发 0 跟随全局，正数只收紧该站点。需要时可另设全站每秒保护。这是容量上限而非实测速率，设备数不等于独立出口 IP 数。

允许回退时，在线代理全部不可用或被临时隔离的请求使用本机直连，直连仍遵守原间隔。仅因代理正忙会等待可用位置。运行记录详情显示本轮代理、直连及其中回退的请求尝试次数（包含重试）。
## 调整容量

[下载资源与生效时间](help:下载资源与生效时间) 说明容量保存和重启；协议与许可键见 [采集出口与频控](help:采集出口与频控)。

# 采集进度与运行记录

## 四种数量分别看

| 状态 | 表示什么 |
| --- | --- |
| 下载 / 核验 | 响应已取得并检查；不等于入库 |
| 成功入队 | 规范数据与断点已原子写入 Redis |
| 归档处理 | MySQL 提交、确认相同或确认旧版本无需写入 |
| 业务写入 | 实际 INSERT / UPDATE / DELETE 数量；相同内容可以为零 |

整轮全部消息成功处理后才显示完成。采集各批入队后继续下载，不逐批等待归档；队列背压、隔离和频控仍可能等待。

## 统一运行详情

在“采集管理 → 采集任务”展开来源并选择具体任务，打开“运行详情”。运行中展示本轮状态、记录和当前位置；非运行中展示最近一次记录。记录数缺少统计时显示“暂无数量统计”，其他未提供的核验数量或当前位置显示“—”，不能据此判断为零或没有采集。已保存计划、下次执行、最近开始与结束分别显示，当前轮次运行中下次执行显示为结束后安排。

进度条只表示已处理/入队比例；没有可信总数时使用等待动画，不虚构百分比。“归档确认”独立显示，达到 100% 不代表全部已经入库。完整错误按纯文本展示，可选中复制；数据质量与用途限制仍在“数据准备”查看。来源特有的连续进度、失败证券和暂无详情字段只在实际提供时出现。

## 增发送配进度

任务显示成功入队记录、核验证券、失败证券、连续进度及当前证券。前面失败但后面仍在入队时，连续进度可能为零；不能据此判断完全没采集。最早缺口保留，有缺口不能显示整轮完成。

## 记录如何查看

“采集管理 → 运行记录”按任务选择采集、归档或错误标签，支持后台分页。选择错误后才加载正文详情。采集、归档每项目各保留最近 100 条，错误 300 条，均只存 Redis，服务重启会丢失。

## 处理错误

先登记项目和错误 ID，修复并验证后只清除已解决的确切 ID，保留新错误及未解决项。查看记录或后来采集成功不表示旧错误已经修复。

# 下载资源与生效时间

**入口：采集管理 → 下载资源。**

## 保存步骤

1. 查看“当前生效”和“已保存”的区别。
2. 输入容量或选择 100～1000 台十档生成推荐草稿。
3. 检查窗口、共享缓冲、单响应、文件和磁盘限制，点击保存。
4. 正常退出并重开 Empire，确认新值成为当前生效值。

配置保存于 MySQL app_setting，电脑重启保留；未保存草稿不保证跨重启恢复。当前请求和资源对象保持旧值直至正常关闭。

## 推荐值是什么意思

默认 100 档为 128 窗口 / 512 MiB 缓冲，1000 档为 1024 窗口 / 4096 MiB。规划设备数不是在线独立出口数，也不是实测吞吐。推荐不自动改每 IP 访问间隔、全站保护或任务代理策略。

## 限制与校验

必须满足“3 × 最大内存响应 + 256 KiB ≤ 缓冲预算”和“单文件上限 ≤ 目录配额”。默认股票、新闻、日历正文上限分别为 1 MiB、4 MiB、512 KiB；正文和临时复制计入预算，预算不是整个 Python 进程内存上限。

文件下载默认单文件 256 MiB、并发 4、目录配额 2 GiB、磁盘余量 128 MiB；当前不因此新增公告或 PDF 业务。详细参数见 [连接与容量参数](help:连接与容量参数)。

# 数据准备

## 范围与用途

一个来源即可独立满足一份数据，无需多个网站相互印证。按声明的市场、证券和日期范围检查；来源不支持的范围写明限制，自己的漏采和明显错误仍要处理。“要准备什么”区分必需与可选信息，可选信息缺少不影响通过。

默认满足估值分析和普通日频回测。停复牌以停牌、复牌日期和全天/临停类型为主，公告时间和原因可选；财报保留公布日期，完整修订历史、秒级公布时刻不作通用要求。财报等用于信号不能提前使用，仅有修订值时需说明历史回测限制。

## 查看项目

“数据准备”默认显示采集项目，共规划 80 项，每项只负责一份数据。还有 12 项整理、计算和核对工作，通过“工作类型”切换查看。这是开发清单，已接入范围见 [功能与数据范围](help:功能与数据范围)，规划项不代表已开发。

比如新闻分开看：最新新闻正文采集、以前的新闻补采、保存修改前的正文、找出对应股票。第一项做好，不要求其他三项也做好；也不会把其他三项一起标成完成。

指数成分名单和权重、融资和融券、公告列表和文件下载、业绩预告和快报，也分别跟踪。股价与股本分别采集，市值另作计算；跨数据检查另列核对项目。

## 理解检查结果

页面先显示完整项目清单，再逐项更新本轮结果。上方显示已检查数量和当前项目；进度读取不会启动额外数据库扫描，尚未结束的项目仍未确认。检查中“重新检查”暂不可用，避免叠加全量核验；切页中断后回来会重新读取，筛选和三表范围草稿保留。全股票池全历史检查可能耗时数分钟，清单及已完成项目可以先查看。

选中一行，“还差什么”先说明本项只负责什么、目前缺什么。“要准备什么”列出字段和日期要求；“逐项看看”解释怎么检查。每份数据有几项质量检查，不代表一个采集器要做几种数据。

主表分别显示开发验收、采集完整性、来源质量、用途条件和用途可用性。采集完整性说明来源报告期、业务键和内容是否已完整归档；来源质量说明源站缺值或合计矛盾，不把“与源站一致”当作“源站内容没有问题”。开发验收仍单独要求当前版本的正式测试证据，数据可用不能代替开发验收。


## 三表与分时的范围及用途

入口为一级“数据准备”。上方选择“数据分析 / 财务估值”或“历史选股回测”，填写六位证券代码（多只用逗号分隔，最多100只）和起止日期，再点击“重新检查”。三表的日期表示报告期，开盘啦分时表示交易日期。日期不能晚于今天，起始日期不能晚于结束日期。初始示例是 601139；清空代码检查当前股票池全部证券，日期留空采用来源声明范围。其他数据继续按各自来源范围检查。界面始终显示本轮实际检查范围，修改草稿不会把上次结果冒充新结果。

当前财务分析检查核心科目和已知金额关系，公告日期缺失呈现“用途限制”；不代表任意估值公式的全部输入已准备好。历史选股回测仍必须有公告 / 可用日期，缺少则不可用。范围内的必需金额缺失或合计异常继续阻断；不通过填零、改金额或不断重采来凑齐。只检查某只股票或近期区间通过，不代表全股票池全历史通过。

在“问题定位”查看具体证券、报告期和字段 / 合计原因，每个检查项最多展示 100 个样例，问题总数见逐项记录。日期范围没有来源报告期时显示未确认与范围限制，不当成软件漏采，也不宣称可用。仅有旧汇总证明或查询失败时仍不能确认完整。可以缩小范围，按需排除受影响记录或核实公司公告。

“已准备好”表示本项在声明范围和用途内完成，不承诺适用所有年份和策略。打开页面首次检查，后续点击“重新检查”更新结果，不每 30 秒重复扫描历史财报；全股票池检查可能耗时数分钟。检查中的项目与已完成结果逐项显示，未结束的数据保持未确认。范围与用途只作页面状态，不保存为采集任务配置、不改变归档内容、不启动采集。可打开相应采集任务，或复制含范围、限制及失败原因的检查记录。

# 历史停复牌

## 查看与查询

通达信任务覆盖上海、深圳 A 股，从 2004-12-27 逐自然日检查到北京时间今天。每次取得完整日集合，装满则扩大容量重取整日，避免同证券跨页重排；原始 A 股数须与来源计数一致，完全重复仅在两次完整响应内容和次数一致后合并。来源计数包含北京 A 股而不含 B 股，归档只保留沪深 A 股。月内任一天失败都不发布该月。数据准备另查来源日期缺失及现行完整性版本，任务完成不能替代验收通过。

## 日频覆盖与休市

在“数据准备”选中历史停复牌，覆盖与时效以正式巨潮交易日历中的“最近一个已结束交易日”为目标。休市日不要求当天已补查；开盘前、集合竞价、午休和交易日盘中仍检查上一已结束交易日。沪深 A 股包含有盘后交易的板块，日频检查统一以北京时间 15:30 为结束界点；15:30 后要求覆盖当天并有收市后的成功核验，上午确认到当天不能冒充全天完整。

09:15 起的集合竞价、09:30—11:30 和 13:00—15:00 的连续竞价，以及适用板块的盘后固定价格交易不是一段连续交易。15:30 是本页全沪深数据集的统一日频验收界点，不代表每只股票都交易至 15:30，也不是采集任务只能在此窗口运行。

长假期间，已覆盖最近结束交易日且在结束后成功确认的数据，不因超过三个自然日就自动过期。日历缺少今天、最近交易日或中间日期时显示未确认；不能用周末规则或自行推算节假日替代来源日历。日历只确定检查目标，不参与跨来源停复牌金额或事件对账。

2004-12-27 以前属于来源限制，不当成漏采，也不推断当时无停牌。所需交易日以内的真实历史缺口、缺来源日期或不可信核验时间仍阻断。采集仍按原来的逐自然日补查与修订回看执行，不删除休市日出现的来源记录。

后续从 MySQL 最后确认的连续日期当天重查到今天，用于取得后来补出的复牌时间。来源遗漏不会删除已有事件；迟到旧响应和空复牌值不会覆盖已知复牌时间。在“数据浏览”目录打开“历史停复牌”，左侧按通达信来源日期查询，右侧表头支持跨页排序。来源日期未知的旧记录需补采；页面会提示尚未完整核验的日期。完整规则见项目文档 `docs/tdx-suspensions.md`。

| 电脑或 Redis 服务重启 | MySQL 配置和数据保留；Redis 待归档数据、断点、下次执行时间与记录丢失 | 固定间隔从应用启动重新计时；每日计划选择下一个北京时间时间点；手动和禁用任务不执行 |
| MySQL 暂不可用 | 无法保存配置，不显示保存成功；采集依赖未就绪 | 先恢复连接，再保存或启动相关插件 |
| MySQL 已保存，Redis 同步失败 | 配置已经持久化并在当前进程生效，界面显示同步提示 | 下次启动以 MySQL 为准校正运行计划 |


## 正常退出

关闭窗口会等待采集、归档和已接收数据库操作结束，然后释放单实例锁。应用关闭期间不采集，不是后台常驻服务。

# 任务失败与数据未更新

## HTTP 200 但正文不完整

HTTP 200 只表示服务器返回了状态，不能证明正文完整。压缩响应未结束或实际传输短于声明长度时，程序保留已读字节数和脱敏前缀，将完整原文长度及摘要标为未知，并按已保存的单次请求重试次数执行有界重试；例如重试2次，最多请求3次。每次重试仍遵守代理选择、网站频控和本轮总时限，不把不完整正文入队。

正文大小超限、无效压缩格式、额外压缩成员等仍直接失败，不靠重复请求绕过限制。重试耗尽后保留断点，后续继续采集或已启用的运行计划从未完成位置恢复。重试成功不自动清除早先错误记录；程序缺陷经验证修复后，只清理对应的确切错误ID。

新轮次成功启动后，“运行详情”的当前失败原因清空，旧轮次的错误仍在运行历史和错误记录中保留。若启动状态无法保存，原失败状态保留，不伪装为已经开始。

## 数据查询不符合预期

**采集成功但页面没变？** 页面读取已归档的 MySQL 数据；检查归档状态。不完整股票列表不会发布；内容相同时不会更新业务表时间。

**新闻首次只有 50 条？** 首次及“重新采集”仅获取最新第一页；后续增量接上上次归档上界就停止，不承诺全历史补齐。

**日历显示未采集？** 缺失日期不等于休市。执行日历采集并等待整月校验、归档；未来安排可能被来源修订。

## 暂停、退出与错误记录

**暂停和退出有什么区别？** 暂停任务会持久保存禁用状态，重新打开仍暂停；正常退出仅结束当前运行，保留已保存的启用与计划设置。

**错误记录怎么处理？** 先修复并验证，再按确切 ID 清除已解决记录。记录仅查看或后续采集成功不会自动删除。

## 插件失败或运行异常

**插件显示运行失败或运行异常？** 到“系统设置 → 运行状态 / 插件管理”查看原因。关键归档、调度、代理目录或 Redis 监测循环意外退出时显示运行失败；服务暂时故障或依赖异常显示运行异常。先处理原因，再正常停用后启用，或正常退出并重开。仍有资源的失败插件不能直接重复启动，程序不自动重启故障循环或重放写入。正常一次采集完成和正常关闭不会因此报错。插件后台摘要仅保留本次进程中最近 100 条，每条最多 2048 字节，不代替项目的 Redis 错误记录。

切换页面时，隐藏页面的展示定时器和只读查询会停止；重新进入再刷新。只读页面实例采用有界缓存，被回收后会恢复搜索、筛选、分页、稳定身份选择和滚动位置。采集任务、站点规则、运行记录与下载资源等编辑/写入页面保持常驻，切页不会取消保存、精确清理等写命令，也不会清除未保存草稿。

## 网站限流与网络失败

**网站限流要等多久？** 429 冷却由所有代理和直连共享，合法长时间不截短；非法等待值回退 30 秒。极端超长整数会保守阻断并提示，不能靠换出口绕过。取消或请求超时只结束当前等待，不删除冷却。跨站跳转不会带出认证和 Cookie，HTTPS 跳到 HTTP 会拒绝。

# 采集出口与频控

## 在线目录与协议

独立 `infra.proxy_pool` 插件提供 `proxy.pool`，共享 HTTP 插件在每次重试或重定向前重新申请出口与许可。原有来源插件无需分别实现代理逻辑。后台每 5 秒刷新目录，代理分配前还会重新核实。

目录来自同一个 Redis 数据库：`router:proxies:by-code` 的 field 是设备编号，value 是包含 `code`、`proxy`、`exit_ip` 的 JSON；`router:proxies:device` 以相同 JSON 原文为 member、过期 Unix 时间为 score。通过 Redis TIME 原子核实两者，仅采用映射存在且租约未过期的设备。Empire 对这两个 key 只读。

连接值支持 `http://`、`https://`、`socks5://` 和 `socks5h://` 前缀，按声明的协议和端口使用。目录必须是包含 code、proxy、exit_ip 的 JSON；其中 proxy 未声明协议时按生产者契约使用 SOCKS5H，原始凭据按字面编码。显式 URL 按声明协议处理。完整 URL 中已编码的凭据不会再次编码；原始凭据只在连接内存中使用，不进入页面、日志、SQL 或运行记录。一个 Hash 字段只能声明一个入口，不根据端口差值猜测其他协议。

## 配置与生效

| 配置 | 作用与默认行为 |
| --- | --- |
| policy.use_proxy | 按任务启用代理，缺省为 true（代理优先）；保留显式保存的选择 |
| policy.proxy_fallback | 代理不可用时允许直连，默认为 true，仅在 use_proxy 开启时使用 |
| min_interval_ms / proxy_interval_ms | 分别限制本机直连和每个出口 IP 对同站点的请求间隔；同出口多个设备共享代理间隔 |
| scaling_mode | auto 按健康出口 IP 数扩展，fixed 执行固定限速；旧配置默认为 fixed |
| total_interval_ms | 仅固定模式使用的全站合计间隔；自动模式不使用此限制 |
| max_rps | 可选全站每秒保护，0 表示不额外限制，1～100 表示启用；不是源站承载量声明 |
| max_concurrency | 0 跟随全局下载窗口，1～1024 为更严格的站点在途请求安全阀；不能放大全局窗口，自动模式也受健康独立出口 IP 数约束 |

任务与网站设置都保存在 MySQL app_setting，无需新增表或自动迁移。任务的代理策略在下一轮生效；网站参数在后续申请许可时生效。下调并发时，已发出的请求正常完成，不再追加超过新上限的请求。

## 频控和故障处理

设备优先按实际请求次数、再按最近分配时间轮换，避免未取得许可的分配消耗公平轮次；每台设备同时最多 1 个请求，同网站跨任务按出口 IP 共享间隔。自动模式只保留每出口许可及显式全站保护，理论容量不作为额外合计间隔。固定模式保留网站合计间隔。许可由 Redis 原子检查，直连使用原有网站许可键并保留旧等待和冷却。

传输或代理认证失败时，隔离该设备 10 秒起、指数延长至最多 120 秒；仍在现有的单次请求重试预算内切换设备或回退。回退后不会关闭任务的代理选项，后续请求发现设备恢复会再次优先使用代理。移除或凭据变化时，旧连接不再分配，已在途请求结束后关闭旧客户端。

收到 429 后冷却整个网站组，包含所有代理和本机直连，遵守 Retry-After。403 不触发自动换 IP 重试。一次请求包含等待、重试和重定向的默认总期限为 120 秒；不允许回退且代理长期不可用时，本次请求超时，任务保留已有断点，等待下一轮计划或手动继续。

目录的 `exit_ip` 是公网出口身份。多个设备声明相同 `exit_ip` 时，Empire 自动归并其同站点频控；设备编号仅用于连接选择和故障隔离。

新浪股票在代理模式下可同时下载多页，受当前健康独立出口 IP、全局/站点窗口、字节预算和剩余页数共同限制，全局默认 128、最多 1024。按页号校验并提交断点，后页先返回也不能越过失败页。新闻和日历仍顺序采集。任务取消会回收全部预取请求。股票完成记录分别显示下载校验与归档确认耗时，不能把归档确认算作网络耗时；原有完整性校验和归档成功清理规则保持生效。

## 运行数据与保密

`<namespace>:rate:<网站组>:total` 保存总许可时间，`<namespace>:rate:<网站组>:proxy:<出口身份摘要>` 保存该出口的网站许可并在一天不使用后到期；出口身份统一采用 exit_ip。网站键保存直连许可和全组冷却。连接池及故障隔离只在本次进程内保存，页面只展示无凭据入口地址。

节点在线由 RouterProxy 维护，Empire 不另外主动探测。等待分配时合并目录刷新，实际分配前仍核实映射及租约。页面“目录在线”只表示生产者目录中的在线记录；“请求失败冷却”表示 Empire 正在暂缓该连接的重试。

采集历史的 network 字段仅保存 proxy_requests、direct_requests、fallback_requests 计数。网站统计为本次 HTTP 插件运行期间的尝试数；包含成功、失败、重试和重定向。错误样本仍按每项目 300 条处理，不将代理密码保存为错误原因。

# 系统架构

Empire 是运行在本机 Windows 上的单体桌面应用。界面、计划调度、采集、校验和归档在同一应用进程中，由内部插件分工；Redis 与 MySQL 是独立的本地数据服务。当前不加载第三方插件，也不使用 Docker 或 WSL。

内置数据与任务使用代码内白名单贡献注册，不扫描目录或自动加载外部包。数据贡献声明数据集、版本、归档模式和项目身份；任务贡献声明采集能力与展示信息。单个采集器停用时，仅对应任务显示不可用，任务管理和其他采集器继续运行。MySQL 核心只统一校验配置表与统一状态表，各数据插件只校验自己的业务表；无关业务表故障不应隐藏其他已归档数据。

## 整体数据流

```text
界面页面
  ↓ 只调用已声明的能力
采集任务管理 → 来源采集器 → 共享 HTTP 与站点访问规则
                         ↓
                  数据规范与完整性校验
                         ↓
                Redis 待归档消息与断点
                         ↓ 入队立即唤醒；每 60 秒恢复扫描
                    统一归档器
                         ↓ 事务提交
               MySQL 业务表 ← 数据浏览页面
```

网络请求、Redis 操作和 MySQL 查询都在后台执行，Qt 主线程只负责显示与用户操作。关闭窗口时，应用先停止计划和采集，等待归档任务及数据库连接正常退出，再释放单实例锁。

界面切换筛选、月份、采集项目或分页时会取消旧的只读查询；如果后台查询已经开始而不能取消，返回结果也会因请求条件不再匹配而被丢弃。刷新失败时，已有表格可以继续查看，但状态会明确显示“当前刷新失败”和上次成功读取时间，不能把旧数据显示成此次刷新成功。关闭或卸载页面只取消读取；保存设置、启动任务、精确清除错误等写入操作继续完成并返回结果。

数据浏览与数据库持久化使用独立的线程和连接池：浏览最多同时执行 2 项、另等待 16 项；归档、配置保存和采集进度回源最多执行 1 项、另等待 32 项。浏览慢查询不占用写入连接。队列满会明确提示本次操作尚未执行，可稍后重试；归档失败仍保留待归档消息，不会丢弃。运行状态页显示两通道执行/等待数量、容量及满队拒绝次数。

切页取消尚未执行的查询可释放等待位置；SQL 已开始后须等真实结果完成，不把取消视为事务回滚。正常关闭会等待已经接收的数据库操作结束。资源隔离并不消除 MySQL 本身的磁盘负载、锁等待或单个长事务，也不是采集提速倍数的保证。

## 插件内核

内核只管理插件清单、依赖顺序、能力注册、启停状态和后台任务回收，不理解股票字段、新闻规则或网站地址。所有插件都由项目内部白名单显式登记，通过 `requires` 声明依赖、通过 `provides` 提供能力。

| 插件层 | 主要职责 |
| --- | --- |
| 基础设施 | Redis、MySQL、HTTP 请求和共享站点访问规则 |
| 数据规范 | 定义业务唯一键、内容摘要、版本顺序和 SQL 映射 |
| 来源采集 | 请求来源、解析分页、验证边界和维护断点 |
| 数据管道 | 规范数据入队、容量保护、统一归档与安全重放 |
| 采集管理 | 手动执行、固定间隔、每日计划、任务互斥和运行记录 |
| 数据查询 | 从 MySQL 有界读取股票、新闻、交易日历和停复牌 |
| 界面插件 | 向桌面外壳贡献页面、菜单分组和数据目录登记 |

插件管理中的“停用”只影响所选插件及明确依赖它的功能。停用一个界面插件会移除相应页面，不会自动停止它展示的采集器；采集任务的日常暂停应在“采集管理 → 采集任务”操作。

## 管理界面

桌面外壳只负责一级/二级导航、页面按需创建、命令反馈和退出流程。工作台、采集管理、股票、新闻、日历、系统管理和说明文档分别由独立 UI 插件贡献。采集任务、站点访问规则和运行记录也各自拥有控件、查询条件和编辑状态，不共享一个大页面实例。

打开过的页面会保留，因而普通导航、筛选和分页不会丢失未保存草稿；停用所属 UI 插件会释放页面及草稿。数据页面使用 `catalogued`、`category`、`source`、`database_tables` 登记到数据目录，目录显示实际浏览查询的数据库业务表，多个表以逗号分隔并支持表名搜索。新增采集器不需要给侧栏增加固定菜单。

股票列表、财经快讯和交易日历的“管理采集计划”由各自页面贡献声明关联任务，点击后直接在采集任务页定位；桌面外壳不硬编码业务映射。临时定位不修改原任务筛选和页码，也不覆盖其他任务的未保存草稿，可用“返回原筛选”恢复。返回数据目录时保留原筛选、页码和按页面 ID 记录的选择。

## Redis 与 MySQL 分工

| 存储 | 保存内容 | 持久性 |
| --- | --- | --- |
| Redis | 待归档消息、断点、next_due、许可与冷却、内容摘要、运行及错误记录 | 纯内存；Redis 或电脑重启后丢失 |
| MySQL | `stock`、`finance_news`、`trade_calendar`、`suspension_event`、`dividend_plan`、`additional_issue`、`rights_issue`、`income_statement`、`balance_statement`、`cashflow_statement`、`industry`、`industry_member`、`stock_intraday`、`collection_state`、`app_setting` | 保存业务数据、每项目一条已归档状态及任务/网站/下载资源配置 |

正确业务数据先进入 Redis，归档器确认 MySQL 事务提交、内容已经相同或消息已经过时后，才确认并删除对应队列消息。SQL 出错时消息保留重试。内容摘要只是有期限的加速缓存；缺失时回到 MySQL 比较，不能作为永久真相。

股票、财经快讯、交易日历和停复牌的已归档查询只读取 MySQL，不以 Redis 在线作为前提。Redis 不可用时仍可查询这些数据，但采集、归档、断点、运行记录和“最近一次 Redis 成功核验”等临时能力会暂停或不可用；界面不得把 SQL 的最后实际发布批次冒充临时核验结果。Redis 恢复后，查询能力无需随采集链路一起重启。

## 发布和数据库维护

双击项目根目录的 Empire 快捷方式会启动打包后的 Windows EXE。代码或依赖更新后重新构建 EXE；运行时启停插件不等于热更新代码。

应用启动只检查服务和所需表，不自动创建、迁移或重建数据库。首次建表、结构调整和旧配置迁移都是明确执行的维护操作，完成前后需要核对待归档队列与业务数据。

Redis 是纯内存状态：Redis 或电脑重启后，未归档消息、断点、下次执行时间、摘要及运行/错误记录不能恢复，应按 MySQL 已归档边界重新采集，不能从 `collection_state` 伪造这些临时状态。MySQL 业务恢复必须使用经过隔离库比对的逻辑备份；当前项目未登记已验证备份，因此不承诺磁盘损坏后的 RPO/RTO。完整的备份、六表清单核对、`_restore_drill` 隔离恢复和生产恢复批准边界见项目文档 `docs/recovery-runbook.md`。

# 股票表字段（stock）

本页是数据库字段参考。查看实际股票请打开 **数据浏览 → 数据目录 → 股票列表**。

`stock` 保存新浪的一份当前完整列表，每行是一只股票，主键为 `unified_code`。来源由数据集登记固定声明；表内只存统一证券代码和名称，所有字段均不允许为空。

## 股票身份与名称

| 字段 | SQL 类型 | 含义与示例 |
| --- | --- | --- |
| unified_code | VARCHAR(9) | 项目统一代码，如 `000001.SZ`。唯一定位市场及代码，不代表跨换码永久身份。 |
| name | VARCHAR(100) | 来源股票名称，保留 ST 等标记。 |

## 发布批次与时间

全部项目的已归档状态存于 `collection_state`，以 `(namespace, project_id)` 为主键，每项目仅一行，与业务修改在同一事务中提交。

| 字段 | SQL 类型 | 准确含义 |
| --- | --- | --- |
| namespace | VARCHAR(160) | 运行环境命名空间。 |
| project_id | VARCHAR(100) | 采集项目身份，与 namespace 组成主键。 |
| source | VARCHAR(80) | 来源。 |
| dataset | VARCHAR(80) | 数据集类型。 |
| payload | JSON | 最近 SQL 确认的 progress 与版本；股票含 publication，日历含每月 observed。 |
| updated_at | DATETIME(6) | 本状态行最后实际更新的北京时间。 |

股票 publication 内的 snapshot_id、started_at、finished_at、row_count 对应**最后一次使列表内容发生变化的发布批次**。finished_at 是该批次完成采集的北京时间；不是 SQL 提交时刻，也不是最近一次成功核验时间。整份列表相同不更新 publication。

例如：09:00 完成的批次改变了列表，09:02 才归档，界面内容更新时间为 09:00；09:10 再次采集得到完全相同的列表，界面仍显示 09:00。

股票页面的“更新于”取 `collection_state.payload.publication.finished_at`；MySQL 和界面均使用北京时间。最近一次是否采集成功，应查看 **采集管理 → 运行记录**。Redis 最新成功核验标记为 `<namespace>:stocks:committed:<source>`。可信摘要命中完全不访问 MySQL；SQL 只保存最近回源确认的进度与版本，不保证恢复其后仅在缓存确认的核验上界，也不恢复未归档断点。

## 什么时候写入

- 分页未收齐或验证失败：保留原列表，不发布部分股票。
- 完整内容相同：不执行业务 INSERT、UPDATE 或 DELETE，不刷新 publication；回源 SQL 确认可推进统一状态，可信 Redis 命中则完全不访问 SQL。
- 完整内容有效变更：单个事务替换该来源的整份列表并更新发布信息，股票行不再重复存储批次及批次时间。
- 旧批次重放：经过版本校验，不能覆盖新列表。

事务提交、确认相同或确认旧版本后，统一归档器删除对应 Redis 待归档消息；出错保留重试。

`stock` 不包含股价、涨跌幅、成交量或历史股票池。其字段定义与 `sql/schema.sql`、股票归档写入逻辑一致。

# 新闻表字段（finance_news）

## 字段与规则

`finance_news` 保存新浪 7×24 全球财经直播的规范化业务内容，按 `(source, news_id)` 去重。不会每天覆盖或删除历史新闻。

| 字段 | 用途 |
| --- | --- |
| source / news_id | 来源与来源新闻 ID，组成主键。当前来源为 sina。 |
| title | 从【标题】提取；无显式标题时取正文开头，最长 256 字符。 |
| content | 去掉 HTML 标签的新闻正文，保留段落；不保留整份 API 原始响应。 |
| published_at | 来源发布时间，按北京时间保存和显示。 |
| source_updated_at | 来源修订时间，阻止旧响应重放覆盖新内容。 |
| is_important | 来源焦点标志或分类 9 表示重点新闻。 |
| tags | 规范化分类 ID 和名称，JSON 数组。 |
| url | 来源文章地址；无单篇地址时链接至直播页面。 |
| first_seen_at / version_observed_at | 首次写入和最近实际写入版本的北京时间；相同内容重复采集不刷新。 |

每页独立事务归档，成功后删除对应 Redis 消息；SQL 故障时队列留在内存。归档条数包含重复确认和更新，不等于新增条数。业务字段和来源版本相同或响应更旧时不执行 SQL 写入；仅观测时间变化也跳过。首次只采集第一页，最多 50 条；之后遇到上轮已归档新闻即停止翻页。已停止页之前的历史修订不保证被追溯发现。

界面查询使用 `ix_news_published (source, published_at, news_id)` 或重点筛选索引，以 `(published_at, news_id)` 游标取下一页，不使用 OFFSET。查询首屏返回固定上界和总数，后续页只返回数据与下一游标。该界面分页游标只属于当前查看会话，不写 Redis 或 MySQL，不是采集断点。

# 日历表字段（trade_calendar）

## 字段与规则

`trade_calendar` 保存“大 A 交易日期（巨潮资讯）”，包括交易日和休市日。日期缺失表示未采集，不当作休市。

| 字段 | 用途 |
| --- | --- |
| trade_date | 自然日 DATE，独立主键，同一天不重复插入；巨潮来源由数据集声明。 |
| is_trade | BOOLEAN，来源 isTrade=1 表示交易日，0 表示休市；不以星期自行推断。 |
| updated_at | 最近一次业务内容变更的北京时间；相同内容不更新。 |

来源最早日期为 1990-12-19。首次补齐至下一自然年 12 月；以后每轮维护本月至下一年 12 月，并补齐历史缺失月份。2026-09 维护 2026-09～2027-12。范围依据北京时间计算；未来安排可能修订，采集值只代表来源当前返回结果。

按完整月份校验后先入 Redis，入队立即唤醒并按月独立事务归档，另每 60 秒恢复扫描。日期不完整、空列表、重复/跨月、交易标记或星期无效时不覆盖数据，保留失败月以续跑。完全相同日期跳过 SQL 写入，只推进 Redis 观测标记；来源没有修订版本，使用观测时间避免旧响应覆盖新月份。

# 配置表与迁移

## 字段与规则

MySQL `app_setting` 是配置表，独立于三张业务数据表，不通过业务归档队列保存。点击保存后立即提交事务；相同配置不重复写库，也不刷新更新时间。

| 字段 | 含义 |
| --- | --- |
| namespace | 配置空间，取自 redis.namespace；改变前缀也会选择另一套配置 |
| kind | task 任务配置，site 站点访问规则，download 下载资源 |
| setting_key | 任务 ID、网站组名称或下载资源固定值 global，与 namespace、kind 组成主键 |
| payload | JSON：task 保存 enabled、mode、interval_seconds、daily_time、request_retries；site 保存访问规则；download 保存全局缓冲、各类响应上限与文件资源数值 |
| updated_at | 最近一次实际配置变更的北京时间 |

MySQL 保存值优先；没有保存值的新任务默认手动，新网站组采用 TOML 初始值。域名范围和并发上限仍由本机 TOML 持久保存。Redis 的 policy 只是运行副本，不能覆盖 MySQL；许可时间和 HTTP 429 冷却仍只在 Redis 中。

下载资源在“采集管理 → 下载资源”保存，`kind=download`、`setting_key=global`；没有保存值时使用程序默认值。页面同时区分当前运行、已保存和重启待生效；正常退出并重开软件后统一使用新值，不自动打断当前采集。“恢复默认”只修改草稿，仍需保存。资源数值只有 MySQL 这一条持久配置路径，TOML 仅保留机器路径 `http.download_directory`。

规划出口设备支持 100、200 至 1000 台共十档，一键推荐只更新规划设备、全局窗口和共享缓冲草稿，不改变单响应/文件设置、网站频率或任务代理开关。默认 100 档为 128 窗口/512 MiB；旧九字段 SQL 下载配置须通过 `scripts/migrate_download_capacity.py` 显式补齐，运行时不迁移。自动站点只有显式指定维护选项才改为跟随全局，固定策略和频率不变。

旧 TOML 的 http.buffer_budget_bytes、http.download_quota_bytes、http.disk_free_margin_bytes、http.file_concurrency 由 `scripts/migrate_download_settings.py` 显式迁移；运行时发现这些旧数值字段会拒绝启动并提示维护。先正常关闭 Empire，核对已有 SQL 配置及待迁移值；SQL 冲突不覆盖，迁移成功后退役 TOML 旧键，目录路径不变。不需要业务表结构迁移，不删除已有文件或业务数据。

当前版本升级：正常退出 Empire，确认待归档队列为零后显式运行 `python scripts/migrate_collection_state.py`。脚本迁移至统一状态表，核对业务数量和内容摘要后退役股票专用发布表。旧分钟配置及北京时间维护已完成，旧脚本退役，历史证据保留在 sql/changes。应用启动不会自动迁移。

全新环境用 `python -m empire init-db` 创建缺失表。正常启动只检查表结构，不自动改库。数据库连接信息在 EXE 同目录 `config.toml`（源码为项目根目录），勿在文档或日志复制密码。

# 存储与归档规则

## 字段与规则

**MySQL 保存每项目一条 collection_state 已归档状态和十三张业务表：`stock` 保留一份当前股票列表，`finance_news` 保留去重后的历史财经新闻，`trade_calendar` 保存交易和休市日期，`suspension_event` 保存沪深 A 股历史停复牌。另有 `dividend_plan`、`additional_issue`、`rights_issue` 保存增发送配，`income_statement`、`balance_statement`、`cashflow_statement` 保存三大财报，`industry`、`industry_member` 保存当前行业，`stock_intraday` 保存分时及竞价。成功 HTTP 请求原文不持久保存。**

有效响应解析、校验和规范化后，业务消息先进入 Redis 并立即唤醒归档器；归档器每 60 秒恢复扫描可归档批次。新数据提交 MySQL 后、确认 MySQL 已有相同内容后（含可信摘要命中）、或确认消息过时后，均确认并删除对应 Redis 消息。SQL 或后续 Redis 操作失败时保留消息重试；不完整批次继续留在 Redis，旧股票列表仍可查询。

归档统一使用 SHA-256 业务内容摘要：股票比较整份列表，新闻比较每个新闻 ID，日历比较整月，停复牌比较每个事件及连续日期覆盖段。缓存命中免业务查库；缺失、过期或不同则查询 MySQL，不存在才插入，相同不更新，有效修订才更新，旧版本不覆盖。缓存仅保留摘要与版本，不能在入库前写入。手工修改/删除 SQL 数据前，须停止归档并清除对应来源的摘要及到期索引；重新采集使用新批次。摘要不会保留整份业务数据。

三类记录分开，只留 Redis，不进入业务队列，不写入 MySQL：

| 记录 | 保留规则 |
| --- | --- |
| 采集记录 | 每个采集项目独立保留最近 100 条 |
| 归档记录 | 每个采集项目独立保留最近 100 条，独立于采集记录 |
| 错误记录 | 每个项目最近 300 条；每条脱敏样本最多 64 KiB；完整读取才提供原文完整长度/摘要，提前终止显示未知 |

任务设置、网站频控与下载资源设置保存于 MySQL app_setting；必要断点、执行时间和频控运行状态留在 Redis 内存中。只重启应用可续跑；Redis 服务或电脑重启会丢失未归档数据、断点、下次执行时间和记录，但不会丢失已保存配置。Redis 已关闭 AOF 和自动快照，没有关系型“表”，这里使用 String、Hash、Stream 和 LIST；键前缀由 `redis.namespace` 指定，通常为 `empire:dev`。

应用升级不自动迁移、重建或搬运数据库。结构调整需要显式执行针对性 SQL，保留当前业务数据并记录实际变更。不要清空共享 Redis 或删除其他项目数据。

# Redis 键索引

以下 `<namespace>` 来自 `redis.namespace`。

## 待归档业务消息

`<namespace>:ingest`

Stream，字段 `envelope` 保存规范化业务消息，包括开始、分页和完成证据，不保存成功 HTTP 原文。提交、确认已存在或确认过时后 XDEL；失败保留，不按长度裁剪未归档消息。

## 业务内容摘要

`<namespace>:archive:fingerprints:v1:<dataset>:<source>`

Hash，dataset 为 stocks/news/calendar；字段为 current/新闻 ID/YYYY-MM，值为 JSON hash（SHA-256）、version（有序版本数组）。只缓存已提交或确认相同的业务内容，默认每来源每数据集最多 10000 条、最后确认后 7 天过期。

可信证明必须满足对应数据契约的版本维数、有效日期、规范精度和时区；股票还须有合法批次 ID。新闻/日历时间使用固定微秒精度 UTC，股票开始时间使用固定微秒精度北京时间。无效格式、损坏或缺失索引、过期及异常有效期一律回 MySQL，不据此清队。观测超前本机 5 分钟或新闻修订超前观测 5 分钟只使缓存证据不可信，不拒收业务；SQL 成功后仍可清队，但不缓存该证明并精确失效旧证明。

## 摘要到期索引

`<namespace>:archive:fingerprints:v1:<dataset>:<source>:expiry`

ZSET，成员为摘要业务键、分值为过期 Unix 秒。和摘要 Hash 原子维护，到期或超限淘汰摘要；不删除待归档业务数据。两个键均有空闲 TTL。

## 采集断点

`<namespace>:checkpoint:<job_key>`

Hash，内存断点。`revision` 为 CAS 并发版本，`cursor` 为业务游标 JSON；无 TTL，服务重启仍会丢失。

## 股票发布结果

`<namespace>:stocks:result:<source>`

当前发布结果，`snapshot_id`、`status`、`row_count`、`expected_count`、`error_text`、`finished_at`、`started_at`；只留最新结果，不是历史快照库。

## 股票成功核验

`<namespace>:stocks:committed:<source>`

String / JSON，最新成功核验股票批次。保存 result 字段及 started_at；相同列表不写 SQL 时仍推进此显示/进度标记。归档器不依赖此键删除队列消息，旧批次必须由统一可信摘要或 SQL 状态核对；损坏此标记不构成清队依据。

## 归档进度

`<namespace>:archive:progress:<job_key>`

String / JSON，新闻或日历最新归档进度。`batch_id`、`page`、`status`、`row_count`、`error_text`、`observed_at`；SQL 提交后更新，供采集器确认归档，旧消息重放不回退新进度。

## 日历观测版本

日历统一使用归档摘要中的版本，SQL 回源确认的月份观测上界保存于 `collection_state.payload.observed`，按 YYYY-MM 保存最近时间，不保留历史流水或独立 Redis 观测 Hash。可信缓存命中仅推进 Redis 版本。

## 任务运行状态

`<namespace>:collection:control:v1`

String / JSON，任务配置的运行副本、下次执行时间、活动执行状态及按项目限量的采集记录；配置以 MySQL 为准。

## 归档记录

`<namespace>:collection:archives:<project_id>`

LIST，每项目最近 100 条归档记录，不归档。

## 错误记录

`<namespace>:collection:errors:<project_id>`

LIST，每项目最近 300 条错误记录及有界原文样本，不归档。

`<namespace>:collection:errors-revision:<project_id>` 是列表查询修订号。新增、替换或实际清理时递增，用于静止页面判断“未变化”；它不保存正文、记录副本或处理状态，Redis 重启后与错误列表一同丢失。

## 旧版网站间隔

`<namespace>:collection:site-intervals:v1`

旧版网站间隔配置，仅供显式迁移读取；新版不再读写此键。

## 网站许可与冷却

`<namespace>:rate:<group>`

Hash，共享频控。`next` 是下次发送许可的 Redis 毫秒时间戳，`cooldown` 是服务器冷却截止时间。

归档器使用 XRANGE 扫描 Stream，以消息本身表示待处理状态；成功后按确切 ID 执行 XDEL，不创建消费组。完整股票批次仍未齐全时继续保留队列，当前 SQL 股票列表不变。升级维护在队列归零后移除旧消费组元数据。

# 采集断点

仅供排查采集恢复流程；断点只保存在 Redis 内存中。

## 股票列表


`job_key` 为 `sina-universe-v1`。

| 字段 | 含义 |
| --- | --- |
| snapshot_id | 正在采集的列表批次标识，与发布身份关联。 |
| started_at | 本批次开始时间，带 UTC 时区。 |

| original_sha256 | 完整读取时原始内容的 SHA-256；未完整读取为空，不能把前缀摘要当作完整摘要。 |
| sample_sha256 | 最终脱敏样本的 SHA-256，与原文摘要含义不同。 |

**先修复并验证，再清除对应错误记录。** 在错误页选择具体记录，确认问题已经修复并验证，再点击“清除已修复记录”。`clear_errors(project_id, record_ids)` 仅删除明确传入的 ID，不清空项目；操作期间的新错误继续保留。

运行记录三个页签默认全部项目。归档/错误的跨项目视图由后台扫描本命名空间既有有界列表、按时间合并并分页，不新增持久化副本；无变化时按修订摘要跳过列表传输。错误列表不传正文，选中后按所属项目及原记录 ID 读取详情。全部项目视图禁止清理，先筛选具体项目再精确操作。

查看记录或后续采集成功都不会自动清除错误。超过每项目 300 条上限时最旧记录按容量规则淘汰。错误原文、诊断和归档记录始终不写入 MySQL。

分页摘要、完整详情和精确清理都读取同一个错误 LIST，没有 SQL 错误表、第二份正文或兼容查询路径。错误修订号只是轻量失效信号；不能用它证明问题已修复，也不能据此清除记录。

文本、URL、元数据和后台快照通过同一脱敏器处理，覆盖密码原文及 URL/JSON 转义形式。结构化内容先脱敏再序列化，不能对完整 JSON 字符串做简单密码替换；敏感字段键名和正常业务结构保持可读取。

## HTTP 下载资源契约

在“采集管理 → 下载资源”设置下列资源数值，保存到 MySQL 后正常重启软件生效。页面中的单响应以 KiB、缓冲和文件容量以 MiB 显示，数据库统一保存字节整数。网站频控决定请求节奏，资源上限决定大小与可持有的响应数量，不是下载速度限制。

| download payload 字段 | 默认值与用途 |
| --- | --- |
| planned_exit_devices | 默认 100；100、200 至 1000 共十档容量规划，不是当前在线数或独立 IP 数。 |
| max_parallel_downloads | 默认 128、最多 1024；全局在途下载安全阀及预取窗口上界。 |
| buffer_budget_bytes | 536870912（512 MiB），所有项目、直连及代理共享的下载缓冲预留预算，不是进程总内存上限。 |
| stock_response_bytes | 1048576（1024 KiB），股票单响应的传输与解压正文各自上限。 |
| news_response_bytes | 4194304（4096 KiB），新闻单响应的传输与解压正文各自上限。 |
| calendar_response_bytes | 524288（512 KiB），日历单响应的传输与解压正文各自上限。 |
| generic_response_bytes | 2097152（2048 KiB），通用内存响应上限；正式采集器使用自身响应分类。 |
| file_response_bytes | 268435456（256 MiB），文件传输与解压后的统一上限；插件可另外声明更严格值。 |
| download_quota_bytes | 2147483648（2048 MiB），下载目录占用与活动文件最大预留总量上限；不足则拒绝新文件，不删已有文件。 |
| disk_free_margin_bytes | 134217728（128 MiB），文件下载须保留的磁盘安全余量。 |
| file_concurrency | 默认 4，范围 1～64；文件下载仍遵守站点频控和缓冲预算。 |

保存时校验 `3 × 最大单响应上限 + 256 KiB ≤ buffer_budget_bytes`，保证每种内存响应至少能取得一份预留；同时要求 `file_response_bytes ≤ download_quota_bytes`。结构化响应按“三倍正文上限 + 256 KiB”预留缓冲，覆盖 bytearray 容量增长、组装副本和有界工作区；默认股票每页 3.25 MiB，128 个窗口共 416 MiB。缓冲预算不是进程总内存硬上限，也不会预先一次分配全部额度。发请求前取得额度，后页等待按序处理时继续占用，处理完、失败或取消才释放。额度暂时不足先消费前页，不算请求失败，也不能越页推进断点。

一键推荐将窗口按 128 的倍数向上取整。缓冲取“全部股票窗口预留×1.2”与“股票窗口预留加新闻/日历/通用各一份、文件并发工作区”中的较大值，再向上取整到 256 MiB。默认响应设置下，100/200/300/400/500/600/700/800/900/1000 台分别推荐窗口 128/256/384/512/512/640/768/896/1024/1024，缓冲 512/1024/1536/2048/2048/2560/3072/3584/4096/4096 MiB。自定义响应过大、推荐超过 4096 MiB 时拒绝生成，不暗中改小响应或窗口。推荐不会缩短网站每 IP 间隔，也不等于这些设备均在线或真实吞吐已验证。

大文件使用 FilePolicy，默认文件/传输上限 256 MiB，缓冲预留 256 KiB，流式写入专用临时文件。完整传输及插件声明的签名/可选摘要验证通过才发布；同名文件存在时不覆盖，目录不跟随符号链接或目录联接。目录扫描、配额准入、写入与发布在工作线程执行；准入/写入阶段取消等待实际操作结束后清理确切拥有的临时文件。发布提交点期间取消则等发布完成并返回文件结果，避免丢失已提交文件引用。异常退出遗留文件与已有文件仍计入目录配额，不自动扫删。未来公告业务应只将状态/文件引用放入 Redis，另行定义保留、恢复及 PDF 解析/OCR 限制；当前并未新增公告功能。

读取不单信 Content-Length，同时限制实际传输与解压正文，使用有界 gzip/deflate 解压；超限或不完整时终止，不隔离代理、不切换出口重复尝试同一超大正文。提前终止的错误原文明确标记不完整，仅保留有界脱敏样本、已读正文量与样本摘要。

## ingest 容量保护

| 参数 | 含义 |
| --- | --- |
| high_watermark / low_watermark | 共享 Redis 内存达到高水位暂停、低于低水位恢复；默认 0.70 / 0.50，要求 0 < low < high < 1。 |
| max_queue_entries | 本项目消息队列与所有未消耗整批预留的合计上限，默认 100000；达到上限暂停，不删除未归档消息。 |
| max_page_bytes | 单次入队消息正文限制及整批准入的每消息最坏预算，默认 524288，即 512 KiB。 |

股票取得总数后、发布 `start` 前一次预留 `start + 剩余分页 + complete` 的容量；断点恢复只预留剩余分页和 `complete`。普通新闻、日历及其他批次不能占用已经预留的槽位。消息成功写入 Stream 才消耗预留，发布失败、取消或提前结束释放未使用部分；同一任务不能重复预留。容量不足时在首条业务消息前显示暂停原因，不会先留下一个永远收不齐的批次。

预留只存在于当前进程，不写新 Redis key，也不替代正式 Stream 和断点。Empire 异常退出时内存预留消失，重启后按已有断点重新计算；已经入队的消息不因此删除。内存水位反映整个共享 Redis，预留是按正文上限做的准入估算，不是 Redis 物理内存担保；外部写入仍可能触发 Redis `noeviction` 或水位保护。本机配置可与默认值不同，容量参数重启后生效。`archive.index_max_entries` 必须不小于 `ingest.max_queue_entries`，否则启动拒绝该配置。

入队立即唤醒；一轮预算用完会继续下一轮，不等待 60 秒扫描。未完成股票仅保留有界 ID 索引，不在每次唤醒时重读全批次；完成标记、新批次或恢复检查触发重核。扫描完整边界通过后才判断股票缺页，不能把“下一轮才读取的页”误当成缺页。未知 schema 按已登记的数据集与任务归属隔离项目，消息原位保留；归属不明仍全局暂停。单项目归档失败保留消息，后台延后约 5 秒重试，其他已发现的项目仍可处理。

# 增发送配存储与断点

## 字段与规则

分红送转、增发和配股各自独立任务与查询页面，入口在数据浏览目录的“增发送配”。分红以当前股票目录逐股读取全部详情，增发、配股核验全部来源集合。普通采集续跑未完成断点，完成后下一轮重查全部可得历史；重新初始化重建范围，不删除历史。Redis 丢失后从完整范围重查。

`dividend_plan`、`additional_issue`、`rights_issue` 均使用 `(record_key)` 主键；`unified_code`、`name` 保存证券关联，`event_date` 保存本类型的报告/发行/除权日期，`payload` 为规范业务 JSON，`content_hash` 为规范内容摘要，`version_observed_at` 为该入库版本请求开始时间（MySQL 北京时间）。每十股比例与派息换为每股，万股换为股；不保存成功 HTTP 原文或实时行情价。JSON 字段由对应数据契约严格校验。

增发的来源 rec_id 可同时关联新旧代码，分别保留；配股同登记日的不同认购代码或缴款起日分别保留。缺少的旧发行日、缴款结束日、上市日不编造。增发/配股不包含来源未提供的公告时间、预案取消历史，不能用于公告前选股。

统一摘要命名空间为 `dividends`、`additional_issues`、`rights_issues`，每证券完整单元及最终范围证明各一项。collection_state 保存各单元的最近 SQL 确认版本和最终范围摘要；数据准备将正式 SQL 业务集合与证明比较，缺失/异常仍失败。源端移除的历史业务仍保留，不能自动删库来凑总数。

分红契约 dividends.unit@2 的业务键包含市场、代码、报告期、公告日及每股派息/送股/转增，保留同日期不同金额的并列来源方案，不自动求和。旧键通过 scripts/migrate_dividend_identity.py 显式无损重算并失效旧覆盖、缓存及断点，从头重查；金额身份变化无法据此裁定同一方案修订。

现行增发 additional_issues.unit@3 在原 additional_issue.payload.detail 保存规范明细或明确暂无状态：availability=unavailable、source_error_code=0/-1005，可选last_available保留上次有效明细。未采字段不直接转暂无；有效明细仍为原17项字段，数据身份不变。暂无参与摘要与旧版防覆盖，相同内容无业务DML，成功仍统一清队。升级只在程序关闭、队列为空时显式执行 scripts/migrate_issue_availability.py；保留业务行和观察水位，重建受影响完成证明/断点，保留规范内容不变且可验证的证券摘要。启动不自动迁移。历史未知记录仅在当前完整集合摘要精确匹配后标为当前来源范围之外，不伪造暂无。

# 财报存储与断点

## 字段与规则

`income_statement`、`balance_statement`、`cashflow_statement` 分别保存利润、资产负债和现金流量报表，以 `(unified_code, report_date)` 为主键，当前只支持来源 report 口径。JSON payload 保存规范科目、单位和舍入精度，不保存原始响应。三项目各自使用统一 collection_state；恢复清单包括三张表。运行前显式执行 scripts/migrate_business_schema.py，应用启动不自动建表。

财报来源缺值以 JSON null 原样规范保存，金额矛盾不自动更正；来源质量由规范内容即时计算，在三表页面和数据准备分别显示，不进入错误重试队列、不额外建质量副本表。结构无效仍拒绝入队。

同花顺三表 schema 2 仅改变 Redis 传输为共享科目名称的金额矩阵，SQL payload 与业务摘要仍为完整规范行；升级前清空的含义仅为旧统一归档成功清队，不允许手工丢弃旧消息。


## 状态读取与恢复

财报及分红、增发、配股仍各保存一条项目状态。归档只读取当前证券的集合/版本及项目进度、范围证明，局部更新不会丢失其他证券；范围审计继续核对完整集合。完成等待只读进度，但仍须确认整轮待归档消息清理，最高页不能替代整轮完成。此改造不改变查询、采集、保存或重启操作，也不保证 JSON 扩容时减少物理磁盘写入。

MySQL 升级入口 scripts/migrate_business_schema.py 提供 preflight、migrate、resume、verify、status、rollback。正常关闭程序并排空待归档后才能迁移；影子表复制及完整集合核验后原子切换。单独 preflight 通过不能代替完整核验。恢复业务写入后不能回退到旧副本；应用启动不改表。

## 采集与保存

点击“前往采集任务”，选择“同花顺当前行业”，启用并保存后立即采集。任务计划保存于 MySQL，网络选择下一轮生效；默认每日、代理优先且允许直连回退，显式保存的选择继续优先。每轮读取一次行业目录，每行业通过 size/1000 取得一次完整成分响应；校验后一次提交完整集合。显示“完成”时已归档且待归档消息已清除。

## 中断与故障

完整集合入队前中断，下轮从行业目录重取；入队后中断，Redis 仍在运行时先重放并确认该轮，不重复下载。重新初始化也不会跳过已入队待归档轮次。电脑或 Redis 服务重启后，SQL 最新数据保留，下轮完整刷新。

401、登录页、空正文、重复成员、残留分页或不按代码排序都会使本轮失败并保留旧完整数据；到运行记录查看具体错误。每行业最多接收 999 个成员，达到 size/1000 请求上限时不能证明没有截断，须报错处理。网页动态校验在本机计算，所有网络请求仍使用共享下载、频控和资源预算。

## 数据准备与用途限制

“数据准备 → 当前行业与成分股票”通过公共验收接口接收六项独立数据证据，分别核验开发和实际数据，检查字段、唯一键、完整集合摘要、质量、3 天内成功核验及用途。可用于当前估值分组和行业筛选。所选证券缺失不能通过覆盖检查；其他来源、历史归属、调入调出时间及行情不在本项范围。当前成员不能当作历史成员用于历史选股回测。

来源按请求逐页返回，并非同一瞬间的全站原子快照；每行业以一个完整响应避免分页期间重排；校验行业身份、连续序号、结束标记、成员唯一性及请求上限，不只比较数量。不同行业响应仍可能在采集期间更新。来源没有修订版本号，以整轮开始时间阻止较早请求覆盖较晚结果，不能识别源站自身的旧缓存。

# 开盘啦分时及竞价

### 入门与日常操作

在“采集管理 → 采集任务”中，开盘啦分为七项：分时走势、开盘竞价、分钟成交量与成交额、分时成交明细、分钟买卖委托汇总、大单净额走势、历史盘口与日行情摘要。每项独立保存配置、断点、错误和归档状态。新增七项默认停用且为手动计划，开发、启动程序与查看页面不会启动采集。需要某项时只启用并保存该项；网络策略下一轮生效，固定间隔从本轮结束开始等待。

通过“数据浏览 → 数据目录”搜索对应内容，输入市场、证券代码和交易日查询。本项一次读取完整证券日，页面每页展示最多 200 条，盘口按行情字段与买卖档位展开，并保留同分钟竞价点和同秒分笔记录的来源顺序。“数据准备”对这七项分别检查所选范围；分钟 OHLC 是另一项尚未实现的输出，不能由分钟量额代替。

### 数据说明

每个正常证券日只请求本项的完整响应一次，复用共享代理、频控、有界重试、缓冲与预取。分时/量额/委托/大单走势核对 241 个精确分钟键；竞价保留完整来源数组，但上游无总点数，不能证明交易所完整委托；分笔核对 Count、total 与数组长度，同秒多笔不合并。盘口接口只有该日历史摘要和档位，不是全天秒级回放，也没有券商席位身份。金额和未知来源标记按来源原值保存，不自造 OHLC、复权或交易所事件编号。

每项 2021 年起至本轮最近已结束交易日，限当前上市沪深北证券，排除上市前、北交所开市前及有明确全天停牌证据的日期。初始化须所有必要日校验并归档清队；普通采集按 SQL 内容与生命周期补缺，并回看最近五个交易日；重新采集复核完整范围但保留已归档历史。源站不支持或错误日留作缺口，不填零、不当空日。更早历史修订不保证持续追溯，当前股票池有幸存者偏差。

### 归档与减少写盘

本项一个完整证券日校验后，将业务与断点原子写 Redis，立即唤醒统一归档器，然后继续下载。整轮入队结束才等待归档确认。有前序缺口时后序有效日可以归档，但断点不越过最早缺口、整轮不显示完成。Redis 尚存时续跑；Redis 丢失时按 SQL 内容、上市关联和必需日集合重建，不只看最大日期。SQL 提交后清队失败重放不会重复写业务。

统一归档器的可信摘要命中免 MySQL 查询；冷摘要回 SQL。业务相同不做 INSERT/UPDATE/DELETE，也不刷新观测时间；来源计算时间等 metadata 不参与业务摘要，不因仅时间变化写盘。有效修订才更新，较早下载代次不覆盖新代次。插入、更新、相同内容或旧版无需写入均成功清除对应 Redis 消息；失败保留。Redis 纯内存，成功 HTTP 原文不另行落盘；InnoDB redo/undo 用于事务恢复，不能删除或关闭。

### 故障处理

查询无记录不等于无成交或停牌。缺分钟、分笔总数不符、字段变化、日期或证券错配、全零占位行情均失败，查看该独立任务的错误记录。未知历史来源代码须经北交所官方身份与上市日核实；正常同代码无需额外请求。业务错误不通过不断重读消除，已处理错误仅按确切 ID 清理。

### 存储与维护参考

七个 collector/data/ui 插件分别以 `kaipanla_<kind>` 登记，kind 为 trend、auction、volume、trades、entrust、large_order、quote。项目为 `kaipanla-<kind>`（下划线转换连字符），任务在项目后加 `-v1`，数据集为 `kaipanla.<kind>.day@1`，每项目一条 collection_state。

`stock_market_day` 主键 `(kind, unified_code, trade_date)`，每项每证券日一行有序业务数组；共享物理表不共享完成状态。字段如下：

| 字段 | 含义 |
| --- | --- |
| kind | 七个独立数据类型，限制为已登记产品 |
| unified_code / trade_date | 统一证券代码与交易日期，和业务内容关联一致 |
| payload | kind、market、code、trade_date、source_code、aliases、lifecycle、data 与 metadata；data 保留本接口业务字段，metadata 保留可选来源时间 |
| content_hash | 规范业务 SHA-256；包含生命周期，排除 metadata 和本次观测时间 |
| version_observed_at | 当前存储版本的下载观测代次；北京时间 DATETIME(6)，相同内容不刷新 |

显式迁移入口 `scripts/migrate_kaipanla_products.py`，默认只核查，`--apply` 才转换。必须正常关闭 Empire 并排空待归档；每个旧 stock_intraday 证券日拆成 trend 和 auction，在事务内精确读回两条数据、摘要及版本后移除旧行。旧完成状态和计划不继承，七项初始化为停用手动计划；旧表为空，作为旧结构显式维护入口的历史表保留，不是运行时业务路径。程序启动不迁移或建表。命令行 `collect-intraday --kind <kind>` 执行独立项目，须先在任务配置启用。

容量实验 `scripts/measure_kaipanla_day.py` 是临时测量入口，十个接口、gzip 文件与正式七项 MySQL 存储范围不同，不能直接把原文容量当 MySQL容量；实验结束删除正文，保留摘要报告。

## 业务结构升级后的操作

日常仍从“数据浏览”查看股票、财报、行业、事件及分时；筛选市场、输入证券代码的方式不变。市场和六位代码从 unified_code 解析，股票来源符号从该身份推导；采集消息中的 node/source_symbol 仍用于来源校验。历史证券不因退出当前股票列表而删除；缺少当前名称时显示代码。来源变更须显式维护，不能切换配置后混存不同来源。

结构升级不改变 payload 科目、金额精度、来源日期语义或摘要。规范内容相同的缓存继续有效；证券代码变更仅沿已有来源别名证明处理，不按名称合并。财报仍缺历史公告日期，升级不使其自动适用于历史选股。

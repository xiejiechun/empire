# 远航版涨跌停分析

## 如何查看

数据浏览→数据目录搜索“远航”，打开“远航涨跌停分析”。选择日期池、证券历史或证券日原因，填写日期和统一证券代码（例如000001.SZ），点击查询。日期池和历史每页200条，使用上一页、下一页翻页。输入条件后须点击查询，后台刷新不改写输入。

盘中查看选择“盘中最新/回放（Redis）”，填写日期与池，回放北京时间留空查最新，填写HH:MM:SS查询该时刻之前已采完的快照。选择“盘中变化时刻（Redis）”按时间倒序浏览，双击时刻查看；翻页固定同一快照。仅采样观察到变化时新增快照，回放不代表全部逐笔变化。

## 数据范围与更新

采集管理→任务包含涨停板、涨停冲刺、连板池、炸板池、跌停板五项，以及独立的历史涨跌停原因任务。先补齐五池，再运行原因任务；原因按五池证券日并集消重。修改策略后保存；任务每轮结束后等待所设间隔，不重叠。五池推荐固定间隔60秒，交易日09:25～11:30和13:00～15:05只采当天并保存Redis变化快照；15:30后重新核验日终结果再统一归档。原因任务保持每日18:00。已保存策略须显式修改，升级不自动覆盖。

初次按正式A股交易日历从1990-12-19逐日检查，不把2020年样本误当历史起点。历史证券离开当前股票列表仍保留。页面区分未采集、来源报告空池和有成员；空池不能证明当年市场没有事件，也不能证明来源支持边界。

正常维护只请求新增日期、缺口、最近5交易日和到期历史核验；老历史按20个交易日为周期分桶轮转，正常每天约轮到1/20的历史日期，并非每天只核验20天。已有较新核验可以跳过，停机后补到期范围。固定截止未到期且没有缺口时不请求业务接口。来源修订可能在下一次回看才被发现，停机或源站失败会延后。主动重新采集会重新核验整个所选任务范围，保留原业务事实。

涨停冲刺已将两类维护分开执行：原“远航版涨停冲刺”保留原保存的计划，日终只维护新增、精确缺口及最近5交易日；新增“远航版涨停冲刺历史核验”默认每天北京时间18:30执行已覆盖老日期的20交易日轮转。两任务可分别启停和修改计划，读取同一份业务数据与核验证据，不重复保存业务副本。初次或存在历史缺口时，原任务仍须补齐缺失日期，不能把初始化称为少量增量。原任务的“重新采集”只重核近期及补缺，老历史主动重核使用历史核验任务。历史核验停用或离线会延迟发现老修订，近期任务完成不代表历史核验已完成；另外四池和历史原因任务保持原计划。

以8754交易日且无历史缺口为例，新增一天时近期任务处理5个日期，独立历史核验处理其余约437个到期日期；不会要求近期更新等待这437个日期。总历史核验预算和20日周期不变。同截止完成后再次运行无需业务请求。近期规划只读取到期候选的摘要；一轮内后续日期批次复用内存计划，不反复扫描整份历史摘要，断点仍只保存当前有界批次。

## 限制与排错

历史原因业务状态失败时，错误样本保留请求证券、日期、业务状态和有界响应，便于按类型诊断。已核实的HTTP 200、业务状态-1/fail且两个原因栏目均为NULL或空数组，或正文按请求证券和日期通过完整结构校验时，按已保存的单次请求重试预算暂时重试；失败状态携带的正文仍不作为成功数据，只在状态恢复为0且内容校验通过后入队。业务失败与网络失败共用预算和退避，不增加第二层重试。耗尽仍不入队、不推进断点；未知状态、坏JSON、缺栏目、身份不符或正文结构异常不重试，也不改成暂无内容。旧错误未保存这些信息时，单次恢复成功不自动证明旧错误已修复。

盘中请求按股票代码升序；超过100条须逐页采样，标记为“采样区间记录”，不保证同一瞬间冻结完整池。总数变化、重复、缺页及字段错误拒绝保存当轮，保留上一有效结果。

盘中每池最多2048份、32MiB压缩正文，五池合计160MiB正文另加有界索引，每份正文独立保留最长72小时，后续写入不会续期旧正文；容量不足淘汰最早快照并显示累计淘汰数量。Redis服务或电脑重启会丢失全部盘中快照，重新从当前时刻采样；仅重启Empire可以继续读取仍在Redis的记录。无快照不推断空池，回放查询不会回退MySQL伪装历史盘中状态。


一轮内连续处理有界计划，各单元校验后先入队并继续下载，所有计划完成后才统一等待归档。日终显示完成表示本轮已归档；盘中完成只表示Redis快照已可查询，未归档MySQL；数据准备检查另按指定日期核对必需字段、集合、内容和时效。

历史初始化量大时，待归档队列达到容量水位会暂时等待，归档释放空间后继续；不要为提速清空队列。全部下载结束后仍可能显示等待归档，此时尚未完成本轮。来源明确返回失败时保留该单元断点，不能把失败栏目当作没有原因。

本次原因失败恢复不改变初始化、新增/缺口、近5交易日及20交易日历史轮转计划。正常每个必要证券日1次逻辑请求；有R次重试预算时，源响应/直连失败合计最多1+R次尝试，代理连接切换继续受共享设备排除与总超时约束。字节上界按尝试数乘共享单响应上限计；失败响应不入队、不写业务SQL，成功单元仍只入队一次，相同内容不写业务。失败只恢复当前受影响单元及有界预取，不重置全历史。

正常重启且Redis仍在时继续当前小计划。Redis服务重启会丢失未归档数据和断点，从SQL已确认内容恢复并补缺；纯缓存核验的较新时间可能丢失，允许保守重查。失败不能推进该单元，旧响应不覆盖更新确认。网络请求统一使用已保存的代理、站点频控和重试配置。

## 字段与日期

HS,GEM2STAR是当前来源过滤口径，不能用现有股票名单裁剪历史集合。来源上海风险板块编号22映射上海，北京A股编号151映射北京，按响应保留历史旧代码而不映射新代码；市场编号为空但明确创业板/科创板时使用该板块身份，保留原编号与依据。编号为空且板块仅HS时，使用已归档明确身份，必要时补查精确证券身份；保留来源依据。歧义或未知身份仍拒绝入库。

价格和金额为元，涨跌幅与换手率为百分点，成功率为0～1比例。封单量和涨速沿用来源名称，尚未充分核实的单位或时间窗口不推导。N天M板保存原文本，不当作连续板数。NULL为来源缺值，数值字段零为实际零值。时间字段来源0表示未知，独立保留并显示“未知（来源0）”，不是1970年的事件。

原因两个栏目分别保存正文、空串和NULL；来源栏目为NULL或空数组时均表示该栏目未提供内容，不影响另一个有正文的栏目。没有正文仍是已请求结果。原因没有可靠公布时刻，不能作为当时已知的历史选股信号。日终池只能用于下一可交易时点；Redis盘中记录只支持实际采样以来、仍保留范围内的回放，不能重建过去未采时段。

单池最多10000成员，规范正文最多8MiB、压缩入队消息最多480KiB；超限明确失败，不截断有效业务。数据库按有类型字段保存，成功响应原文不长期保留。

## 采集百分比

日终：已入队+计划剩余+未入计划总数；盘中：1份快照；原因剩余未知时仅当前批百分比。使用本轮实际计划和已成功处理数量计算；准备范围期间不猜总量，空计划表示无需处理。百分比达到100%不替代完整集合校验或本轮归档确认；失败仍按实际结果显示。

# 开发、排错与交付流程

## 目的与适用范围

把业务边界、失败恢复、真实查询和文档同步提前到交付前完成，减少用户复制错误、发现漏采、解释交易规则和反复确认。本文是开发执行入口；业务细则继续以 [协作约定](../AGENTS.md)、[采集开发指南](collector-development-guide.md) 和各来源契约为准，不复制另一套采集或发布流程。

2026-10-19 更新。全过程发布所有权、输入身份核对和按项目只读诊断已进入正式实现；各批验证事实见 [实现状态](implementation-status.md)，后续工具仍以具体实现和证据为准，不代表重新完成全市场实采。

## 开工：先确认问题与工作区

1. 读取协作约定、对应来源说明、最近未完成事项及相关证据。检查工作区差异，保留已有修改和未跟踪文件，不能把它们当成本次贡献或直接清理。
2. 登记目标、受影响模块、业务范围、交付条件。按错误修复时先登记项目和精确错误 ID；没有错误 ID 的界面问题记录入口、操作、实际与预期结果。
3. 核实是否有采集、归档、维护、打包或其他聊天正在操作同一环境。只读诊断不启动 collector，不启动第二归档器。能独立进行的调查继续；共享文件写入、维护、发布和桌面操作串行执行。
4. 需要并行开发时先明确文件责任；适合隔离的代码工作可使用独立工作区。独立工作区不隔离 Redis、MySQL、dist 和桌面，不能因此并行迁移或发布。未经用户授权不发送跨聊天消息，不自动启动子代理。
5. 常规读取、修复、相关验证和正常重启由开发者完成。仅业务目标无法推断、需新增授权或涉及数据丢弃时请用户决定；问题附具体选项及影响，不把查日志、运行测试转交用户。

发布和直接构建通过同一全过程独占锁串行执行，源输入及已形成的证据在各阶段核对；具体边界与中断恢复见 [发布门禁](release-gate-review.md)。这不能阻止编辑器或其他任务改源码，检测到输入变化必须重新验证，不把开工时暂时空闲当成后续不会有冲突。

发布和构建入口拒绝仍有线程的 Empire 进程；Windows 枚举中零线程的残留进程对象不代表程序仍在运行，不因此强制结束进程或删除锁文件。

## 设计：把用户后来追问的问题提前回答

每项功能先填写来源指南的生命周期表，并补充下列与用途有关的边界。可以直接引用现行契约，不重复抄写。

| 本次暴露的问题 | 开发前明确 | 交付前反例 |
| --- | --- | --- |
| 财报与网站一致仍显示失败 | 采集完整性、来源质量、用途条件分别判断 | 来源空值、金额矛盾、缺公告日期在不同用途下的结果 |
| 特殊证券解析失败 | 普通企业、银行、保险、券商及沪深北不同结构 | 非季末报告、早期年份、未知科目、超大完整响应 |
| 假期被判过期 | 来源起点、正式日历、时区与已结束交易日 | 长假、盘中、15:30 前后、日历缺日、上午确认当天 |
| 下一轮会不会补失败数据 | 增量起点、失败断点、调度策略、补缺与修订范围 | 前序失败后后序成功、任务取消、Redis 丢失 |
| 摘要命中是否可靠 | 有效期、内容与版本比较、回源及成功清队 | 过期/损坏摘要、旧响应、SQL 提交后重放 |
| 预览看不出缺漏 | 对标页面的证券、报告期、科目层级、单位与缺值 | 多类型证券、长科目、窄窗口、分页与完整科目集合 |

不要把所有来源强制套入同一日期或字段规则。停复牌来源起点 2004-12-27、财报历史信号缺公布日期等限制保留在对应来源说明；不能通过放宽质量检查或填零让页面变绿。

## 实现与验证：每类证据回答一个问题

先用最小可复现用例证明程序缺陷，再修复并保留相关回归；模拟样本采用最小必要结构，不长期保存整份成功响应。网络故障不伪装为解析 bug，来源缺值不伪装为漏采。

开发采集插件的来源核实、真实样本采集、排错及实采验收，统一优先使用代理，代理不可用时允许退回直连（`use_proxy=true / proxy_fallback=true`），避免开发检查默认直连造成过长等待。通过共享网络路径执行并核实生效策略，不静默修改已保存的日常任务配置；操作及证据要求见 [采集开发指南](collector-development-guide.md)“开发实采的网络策略”。

| 层次 | 证明什么 | 不能替代什么 |
| --- | --- | --- |
| 来源语义专项 | 解析、字段、日期、业务身份和边界符合来源 | 正式存储与查询 |
| 隔离集成 | 来源→规范化→Redis→统一归档→正式查询及恢复 | 生产实际覆盖 |
| 有限真实验证 | 明确证券/日期范围的键集合、内容和查询一致 | 未抽查证券或全市场 |
| 正式发布门禁 | 当前代码、依赖、文档、测试和包满足门禁 | 实际桌面、业务质量全部通过 |
| 真实桌面验收 | 正式 EXE 的入口、交互和结果可用 | 全历史数据审计 |

固定保留已出错的业务类型，并额外随机抽取至少30只不同股票，使用共享代理完成真实采集、Redis入队、统一归档及正式SQL查询集合/内容核对；全样本成功且待归档为0才能通过实采验收。记录抽样池摘要、种子、名单和代理次数；不得剔除失败样本凑数。详见采集开发指南“随机30股代理实采准入”。随机抽查用于发现新形态，不替代业务键集合或覆盖证明。专项通过后再执行所需集成和正式门禁，避免每改一行都全量打包；失败或后续修改才重跑受影响验证。

## 排错：助手读取证据并闭环

只读采集项目错误、任务状态、断点、待归档与正式查询，读取有界，避免周期性全历史扫描。记录核查时间；Redis 与 SQL 的分别读取不冒充原子快照。用户无需逐条复制错误。

| 分类 | 处理 | 结案条件 |
| --- | --- | --- |
| 网络/源站暂时故障 | 现有有界重试与频控，观察后续轮次 | 有恢复证据；一次成功不宣称程序已修复 |
| 可复现程序缺陷 | 精确 ID 登记、复现、修复、回归、真实范围验证和发布 | 修复覆盖该 ID，才按 ID 清理并记录结果 |
| 来源质量/能力限制 | 保留原值、质量标记与用途限制 | 说明原因；不能填零或清标记冒充通过 |
| 配置/基础设施持续故障 | 读取配置与连接诊断，按已授权范围修复 | 超出授权或缺少外部条件才请用户决定 |

处理记录写项目、错误 ID、分类、根因、变更、测试命令和结果、实采范围、发布身份、清理 ID 与剩余项。保留并发新增错误；旧错误没有复现不自动判已解决。监控只在有意义修复、持续故障、实质进展或需决定时通知；当前三表监控不等于所有来源均已自动监控。

## 发布与交接：结果必须对应同一份实现

1. 更新业务权威正文片段及关联说明，在发布冻结前显式运行 `scripts/documentation_build.py generate`，再按 [说明文档维护](documentation-maintenance.md) 记录审阅。自动生成聚合物不手工维护；门禁只读 check，过期聚合物不能通过审阅。
2. 发布前停止本次实现修改，核实共享环境操作已结束，正常关闭 Empire，保留程序配置。正式入口仍为根目录 `verify-release.ps1`。
3. 使用独立的 `build/pytest-<本次标识>` 测试临时目录，避免 Windows 历史临时目录权限干扰。不能用它跳过失败测试。
4. 测试期间若共享源码改变，先查明最终差异；旧测试不能证明新代码。正式入口核对完整源输入与输出证据，失配则拒绝发布；不要手工刷新摘要或删除锁绕过。测试、打包与搬移 smoke 完成后才切换正式程序。
5. 完成正式发布后核对配置保留、正式查询和真实桌面；记录实际操作。未做实际桌面时明确未验证，不用离屏截图代替。
6. 交付只报告修改、证据、实采范围和未完成项。源码/测试/文档按完整功能形成可追踪提交，避免长期积累一个无法归因的 dirty 工作区；不能把其他聊天修改混入本次提交或擅自推送。

纯开发文档修改执行文档契约及相关回归，不要求重打包，不改变运行中程序或数据库。

## 文档职责与更新顺序

- README：当前能力和唯一入口，避免保留过时默认值或不完整表集合。
- 程序内说明：用户入口、动作、保存/生效、结果、限制和故障处理；每个页面有非技术说明。
- 来源专项说明：生命周期、业务语义、日期/单位、修订边界和专项验证。
- 实现状态：当前能力及证据链接；日期进度明确属于当时快照。
- evidence：具体修复和验收事实，不保存凭据、成功响应全集或重复业务库。
- AGENTS：稳定执行约束与入口链接；具体操作步骤集中在指南，不为每次故障堆一套新规则。

## 工具优化与后续批次

开发变更可先执行 `python scripts/change_impact.py --changed <仓库相对路径> --output build/<新的报告>.json`，重复 `--changed` 列全实际修改与删除路径。报告读取现有归属、贡献和静态反向依赖；公共契约、维护工具、资源、未知依赖或损坏元数据扩大为全量。`selected_tests` 是建议执行的文件集合，`execution_evidence` 中未执行、跳过、失败和源码过期均不能记为通过。来源与桌面仍须单独验收，正式发布始终运行完整门禁。配置文件与仓库外路径不接受为报告输入。

F 未采用最小schema测试初始化候选，正式集成仍每例创建UUID数据库/Redis namespace、完整schema和全Engine归属守卫。旧候选绑定C时期源码，其长期维护及重新证明成本较高；本批未测得配对收益，不宣称提速，也不将未执行的可选实验算成通过。以后评估须先按F手册冻结六例并预热及四组交替实测，再决定是否采纳，不能降低隔离或原业务断言。

架构治理见 [模块化优化实施方案与验收标准](architecture-evolution-plan.md)（2026-10-19 已授权实施）。发布身份、只读诊断与依赖基线为首批；新闻、股东及后续业务按退出条件分批迁移。接手实施从 [详细执行与验收手册](architecture-evolution/README.md) 和 [状态账本](architecture-evolution/status.md) 开始，不能把准备稿当成已实现。下表的后续项只有对应实现与验收证据齐全才算完成。

| 优先级 | 改进 | 复用位置与验收条件 |
| --- | --- | --- |
| P0 | 统一只读项目诊断报告 | 扩展现有诊断/查询能力；一次得到指定项目错误 ID、阶段、next_due、断点、队列和范围检查，脱敏、有界、不启动采集、不写业务；故障时仍返回已取得证据 |
| P0 | 发布互斥与全过程源码身份核对 | 加固唯一发布入口；第二发布明确拒绝，测试前后及打包前后变化均不能生成成功证据，失败释放自己持有的锁且保留配置；不删除他人锁、不强杀进程 |
| P1 | 来源反例与用途矩阵登记 | 复用现有专项测试和 preparation 声明；新增来源必须覆盖自己的业务类型，公共恢复测试共用，避免仅靠测试总数 |
| P1 | 本次交付清单自动核对 | 关联受影响项目、源码摘要、专项/集成/实采/文档证据；缺少适用项不能标完成，不适用需说明；不额外建立业务运行历史库 |
| P2 | 按问题变化汇总监控 | 在现有有界错误/运行记录上识别持续故障和重复问题，不增加第二调度器；确认故障恢复、重复通知受控，来源质量与程序错误分开 |

前两项已有正式入口：`python -m empire doctor --project <项目ID>` 和 `verify-release.ps1`；诊断的限额、未知和部分结果见程序内“任务失败与数据未更新”，发布的恢复路径见 [发布门禁](release-gate-review.md)。其余项仍是后续工作；本文没有安装新服务、改变自动化计划或承诺无人值守修复一切问题。

## 单次任务记录模板

在本次任务记录或已有 evidence 文件填写，不为每次只读巡检创建新文件：

```text
目标与完成条件：
项目 / 错误 ID / 来源与用途范围：
工作区已有变更 / 共享操作冲突：
分类、复现与根因：
受影响契约 / 必测反例 / 不适用项及理由：
实现与说明改动：
专项 / 隔离集成 / 实采范围与结果：
发布身份 / 配置保留 / 真实桌面：
精确清理 ID / 新增与未解决项：
下一步或需用户决定的问题（没有则写无）：
```

## 表与键说明同步

每次新增或实质修改存储，同一实现者同步 [数据库参考](database-reference.md) 对应表/键条目与覆盖登记：业务表逐项说明字段、身份、索引和归属；Redis 键逐项说明类型、内容、所有者、期限、清理及恢复。数据手册链接对应对象；技术流程不复制另一套字典。文档门禁检查逐项覆盖和审阅时效，新构造方式先扩展扫描检查。

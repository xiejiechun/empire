# 同花顺三表持续巡检：长历史入队超限

本轮直接读取三项目记录，先登记 2 条利润表 HTTP 502 与 2 条资产负债表入队超限错误，见 [处理清单](evidence/ths-watch-size-repair-2026-09-30.json)。已创建当前聊天每 30 分钟的持续巡检；无变化保持安静，修复完成或持续故障时通知。

## 修复边界

资产负债表卡在 SH:600104（上汽集团），规范业务行逐报告期重复证券信息、长科目名称和金额属性名，导致单证券消息超过共享入队器的 512 KiB 上限。三表统一采用 schema 2 无损矩阵传输，公共字节上限不变；SQL 仍保存完整规范行，指纹内容、版本顺序与业务唯一键不变。

证券与期间口径传一次，唯一排序科目名传一次，完整期间逐一携带金额及分辨率。解码严格校验元数据、列唯一性、矩阵长度和金额精度，再执行原规范行验证。不会删除报告期、省略未知值或逐片推进断点。确实仍超限的消息继续拒绝，断点不前移。

## 部署与数据保留

正常关闭桌面后，使用旧 schema 的统一归档器处理完旧队列，已核实 Stream=0 后才修改契约。运行时只接受 schema 2；意外出现的旧 schema 消息仍由公共机制保留和隔离，不静默消费或丢弃。数据库无 DDL，不修改已有 SQL 业务行；新旧传输解码得到相同规范内容，所以旧业务摘要和来源期间证明仍有效，不需要重采前序证券。结构/字段不变，缓存不替代当前质量检查。

502 属于 HTTP 网络/源站异常，继续使用共享有界重试和频控。已有后续进度不能证明网络原因被修复，本轮不因一次访问成功清理这些历史记录，交由持续巡检观察新增和持续性。

没有新增来源分页、业务分片、文件下载或界面布局；相应专项不适用。错误清理仅在验证通过后按登记 ID 执行；最终发布、实采及清理结果以处理清单为准。


## 实采暴露的查询超时

对本轮已采样证券验收时，利润表 600671 和现金流量表 600537 的正式查询触发 MySQL 读超时。EXPLAIN 显示旧查询仅按 source 使用主键前缀，证券筛选前预计扫描 25,751 行，并对正文查询排序。现有主键为 (source, market, code, report_date)，修复明确市场集合、完整证券代码使用等值条件，先按主键列排序分页，再关联读取有限正文。核实完整代码查询预计扫描降为 274 行，无 DDL、额外索引、超时参数放大或第二条查询接口。

- 日摘要与分钟汇总有差异，零量分钟价格可能超出日高低价；不能凑总数、生成分钟OHLC或改写源值。额外147组核对中，量差等于 phcj_volume 仅20组，额差与 phcj_turnover 相差不超过1仅32组，不能用这两个字段自动补平。

## 3. 总体设计决定

采用 **证券日业务头 + 各类有类型事实表 + 有界扩展字段**。完整事务单位仍为一种数据的一个证券日。证券日头是现有 stock_market_day 业务聚合行的精简改造，不是新增逐日运行状态表；不保存重试、运行批次、next_due、错误或下载状态。

七种数据都完成正式字段建模。分钟、竞价和分笔基线采用类型化明细，盘口采用日摘要与档位明细。不以“一部分暂时保持整份 JSON”作为本任务完成条件。分笔容量必须通过第9节基准；若明细方案超预算，实施者在隔离实验内比较分块替代方案并提交证据，确定单一目标后再实施生产迁移，不能静默部署两种布局或勉强上线超预算方案。

继续使用 MySQL，无新数据库服务、对象存储或常驻 ETL。数据库压缩和按年分区不作为首轮默认动作；没有实测不能承诺压缩收益，不能修改共享 MySQL 全局配置试验。

## 4. 目标表与键

下列名称为实施目标。最终 DDL 必须完整列出类型、精度、约束和索引，并由第5节字段字典验证，不可只实现示意字段。

| 表 | 粒度与主键 | 正式内容 |
| --- | --- | --- |
| stock_market_day | `(kind, unified_code, trade_date)` | 聚合业务身份、来源关联/上市证明、摘要、版本、校验契约及点数，不再保存完整 payload |
| stock_intraday_trend | `(unified_code, trade_date, minute)` | 来源价格、均价、来源量、标记 |
| stock_opening_auction | `(unified_code, trade_date, seq)` | 来源分钟、价格、标记、来源量；seq从0连续，保留所有同分钟点 |
| stock_minute_volume | `(unified_code, trade_date, minute)` | 来源量、额、标记 |
| stock_intraday_trade_block | `(unified_code, trade_date, block_seq)` | 每200点一个类型化二进制压缩块，含seq边界、时间边界、点数和块摘要；保序，同秒可多笔 |
| stock_minute_entrust | `(unified_code, trade_date, minute)` | 买/卖委托量及金额 |
| stock_large_order_trend | `(unified_code, trade_date, minute)` | 来源大单净额，允许负值 |
| stock_daily_quote | `(unified_code, trade_date)` | 来源名称/状态、昨收、日行情、估值及股本等稳定指标 |
| stock_daily_quote_level | `(unified_code, trade_date, side, level)` | 买/卖1～10档的价格、量，包括来源零档位 |

父表继续登记 kaipanla 固定来源；明细每表的所属 kind 固定由 dataset 登记，不重复存 kind。因为父键包含 kind 而子表不包含，不添加无效的部分外键；通过单一事务写入与集合审计约束关联。禁止引用 `stock` 做历史级联删除。是否添加有效外键必须在完整DDL评审中说明成本，不能以未实现外键冒充已保证完整性。

父表增加 `(kind, trade_date, unified_code)` 日期查询索引。四张分钟表增加 `(trade_date, minute, unified_code)`；日摘要增加 `(trade_date, unified_code)`。分笔增加 `(unified_code, trade_date, source_time, seq)` 支持时段/游标查询；竞价用主键按日顺序分页，跨市场时间索引只在正式访问模式要求并通过预算时增加。不为每个行情指标默认建索引；指定日期内数千行筛选先测量再决定。

分钟以能无损表达来源 HH:MM 的 TIME(0) 存储，并由241键集合校验限定真实分钟；分笔时间以 TIME(0) 保存当前秒精度。若来源新增亚秒字段，升级契约，不截断。序号使用足够范围的无符号整数，不把每证券日的来源序号宣称为全局事件ID。

父表目标属性：

- `content_hash`、`version_observed_at` 保留现行业务语义；先保持 CHAR(64) 摘要格式，避免同时引入无关编码迁移。
- `contract_version`、`point_count`、`key_set_hash`：绑定当前校验契约和业务键/序列；分钟键摘要按实际分钟，竞价/分笔按有序seq与时间，quote另核对完整20档集合。条数不能代替集合与规范内容摘要。
- `source_code` 可空；上市日、上市来源、市场起点为显式字段；旧代码映射证明使用有界 `identity_extra`，排除这些证明中的重复普通字段。source_code缺失不能伪造回显。
- 来源附加统计、昨收等稳定事实放对应业务表或父表的类型专属字段时须明确唯一归属。推荐 trend/auction 的昨收及 entrust/large_order 的日统计以父表的有界 `product_extra` 保存（每项白名单、类型校验），因为它们不是本轮主分析条件；后续若成为常用筛选再显式提升为列。不得把序列移入此字段逃避建模。
- 来源 time/time2/ts 保留原语义于小型 `source_metadata`，排除于业务摘要，不能只因这些时间变化触发DML。JSON扩展每个≤16KiB作为初始预算，须用现存最大记录验证；超界不得截断，需调整有证据的契约。

## 5. 字段映射、精度和可逆规范化

实施第一步生成并审阅 `docs/kaipanla-field-dictionary.md`，逐项枚举全部已存在字段：来源JSON路径、目标列/扩展路径、SQL类型、单位、精度、必需性、摘要参与、反向重建规则。一个字段不能遗漏或同时保存于列和原payload。

数组映射以现行 PRODUCTS.width、解析器与实际内容为准：trend为5列、auction/volume为4列、trades为8列、entrust为5列、large_order为2列。未知分笔第4～7列按原位置命名 `source_field_4` 等（0起算），保留数值和限制，禁止猜测成交笔数/买卖方向。每一位置都有固定类型；未来列数变化继续明确拒绝。

quote 必须覆盖 `name, preclose_px, real, sourcetype, status, weituo`。real当前字段为：`time, up_px, avg_px, low_px, down_px, high_px, last_px, open_px, pe_rate, jtPeRate, TTMPeRate, amount_in, amplitude, px_change, vol_ratio, amount_out, dyn_pb_rate, phcj_volume, entrust_rate, market_value, total_amount, total_shares, phcj_turnover, px_change_rate, total_turnover, turnover_ratio, circulation_value, circulation_amount, actualcirculation_value`。稳定且明确的数值各为列；`time`未核实格式前不强转时间戳，保留来源字段值。盘口每档两值独立保存，不省略零值档。

SQL DECIMAL范围由来源协议、全部现存记录的最大整数位/小数位和边界样本确定；先提出如DECIMAL(24,8)的候选，再证明可无损容纳，不把候选作为最终事实。整数列须证明所有合法值均为整数。转换前检查范围和精度，禁止SQL默认舍入。JSON浮点、整数与Decimal的规范编码要统一测试，不能把1变为字符串“1”或将摘要变化视为可忽略。

每种数据实现唯一的 `canonical -> typed rows` 与 `typed rows -> canonical` 映射（建议置于 datasets 公共映射模块，通过各ProductDataset声明使用）。不是兼容旧库的运行时适配器；反向映射用于统一摘要/审计和既有day API返回契约，运行时只读新结构。若无法保持现行摘要，显式升级规范与Redis指纹命名空间并重新证明，不能静默沿用旧摘要。

## 6. 归档、覆盖和查询

### 原子归档与减少写入

沿统一归档器在同一事务内：按父键串行化同证券日 → 核实旧版本与内容 → 有界批量比对/写入明细 → 保存头部和collection_state。父行尚不存在时必须通过可重试的唯一键竞争策略处理并发首写，不能认为SELECT不存在行总能排除竞态。

可信Redis命中仍完全不访问MySQL；冷缓存相同业务零业务DML；修订时只插入/更新/删除实际变化的点或列，不整日无条件DELETE/INSERT。seq数据按本次顺序位置比较，源端插入导致后续序号变化属于实际序列变化，不能错误复用旧顺序。删除只限经完整新响应证明应移除的本证券日明细，不能删除其他日、项目或合法重复点。

失败回滚父子全部修改、保留消息；SQL提交后Redis操作失败可安全重放；旧响应成功处理后清队。旧版本栅栏必须复用/核实正式SQL与Redis版本契约：增加“新观测同内容B确认后，介于A/B的异内容旧响应C到达，冷缓存也不得覆盖”的回归。若现行持久化规则不能同时满足，不得用无条件刷新业务时间掩盖，须在实施报告中明确并修正共享版本证明设计；不能在此插件另造版本系统。

### 覆盖与数据准备分工

日常补缺按有界证券/日期范围只读父表的键、contract_version、point_count、key_set_hash、生命周期属性，核对对应项当前契约，不读取整段历史明细。父头仅在完整校验及父子同事务成功后存在有效证明，不新增complete布尔值或逐日状态表。

详细数据准备、迁移审计及显式数据维护必须读取实际明细，验证集合、语义和content_hash；不能只相信头部数量。旧契约、证明缺失、生命周期不匹配列为待核验，显式本地验证重建或按正式采集补缺，不能直接视为完整。规则变更通过维护升级证明；不允许正常每轮重复刷新校验时间写库。

### 正式查询与界面

- 保留七项 `.query.day` 的已登记业务返回语义以迁移所有现有调用方；实现仅查新表。
- 增加有界 `page` / `range` 查询，序列页默认200点并设硬上限，按稳定seq或minute游标，列表只投影所需列。分页游标带父内容版本/摘要，翻页期间修订则明确要求重新查询，防止拼接两个版本；不能依赖时间或OFFSET稳定性。
- 父子详情、多表盘口查询在一致读事务内完成，避免父版本与明细来自不同提交。盘口与独立trend仍允许各自缺失，不因联动要求同时完成。
- UI七页统一改用正式有界接口；分钟全日画图可读241点，分笔不能先取整日再显示200点。证券日摘要支持日期截面筛选/排序，明确数值来源单位。
- 批量回测用有界证券/日期/字段投影流式读取，不通过UI分页抓取，不生成永久第二份业务库。默认日频用途优先日摘要；分时数据不是分钟OHLC，也不宣称历史当时可用。

## 7. 公共框架与项目规范落地

复用并扩展 `contracts/business_schema.py`、datasets贡献、mysql_store schema核查及现有测试；同一数据集允许多表归属声明，明确表集合、完整事务单位、规范转换、覆盖字段和版本。共享框架处理事务/摘要/隔离/清队，插件处理字段、来源语义和点集合。

不得只修改开盘啦SQL而绕过全局表登记、备份/恢复清单、schema验证及文档检查。新增自动门禁按 [规范第8节](database-design-standard.md) 实施，至少检查列类型、主键、索引、CHECK和数据集归属。不要构建新的通用EAV数据库、万能ORM或另一套维护框架。

## 8. 显式迁移与回退

扩展现有业务结构升级维护模块，提供本方案独立版本的 preflight/migrate/verify/status/resume/rollback；历史 `migrate_kaipanla_products.py` 仍只负责其明确旧输入，不能运行时串联旧转换猜测数据库版本。正式新空库schema与迁移目标一致。

1. 核实共享环境与最新代码、实际正式配置，预检全量stock_market_day而非仅50股；记录库身份、当前表DDL、各kind业务键集合/摘要、未解决缺口、待归档和实际磁盘空间。不输出凭据。
2. 完成隔离测试、字段映射和容量评估后正常关闭Empire；维护锁与单实例互斥。队列归零须由原归档器成功消费实现，不能清空Redis制造条件；无法归零时保留消息并处理原因。
3. 创建日志登记的影子父子表；按主键游标有界读旧行，验证旧摘要/来源身份，转换后在影子表读回重建规范内容并比较。坏行/超界/未知字段不得跳过或填零；报告精确键并停止切换。
4. 逐项核对父键集合、明细顺序/重复、数值、来源证明、规范摘要和版本；1050样本仍应是原1016有效单元与34缺口，除非迁移前正式数据已有新增且有独立基线说明。未涉及表也核对计数及约定摘要。
5. 内容等价且目标DDL精确匹配后多表原子RENAME切换；DDL非整体事务，用可恢复日志记录阶段，不能在切换间隙启动程序。只有已验证等价且规范版本不变才保留Redis摘要，否则在停机下精确失效对应命名空间并让正式路径冷回源。
6. 发布匹配新schema程序、正式查询和可见桌面验证，核对任务设置/程序配置保留；启动遇旧schema明确拒绝，不启动迁移、不保留旧payload读分支。
7. 原表改名仅作维护恢复副本。切换后无新业务变化且内容仍等于基线才允许回退；有增量必须先保全或前向修复。旧副本清理属于单独明确表集合的维护，不在本方案默认删除。

空间预检包含旧表、完整影子明细及索引、DDL临时空间、redo/undo增长和保留副本。不可用JSON字节估算代替实际预算。迁移失败恢复仅处理本日志拥有的影子表，不删除共享表/锁，不重启数据库。

## 9. 容量与性能验收

实施者先登记同机基线和目标，再构造专属隔离库；真实样本为正确性基准，合成放大数据明确标注。按5000股×250日粗算，四种241点明细合计约12.05亿行/年；分笔按样本均值约32.87亿行/年。必须测行和索引开销，不能把类型化当成无条件节省空间。

| 场景 | 验收要求 |
| --- | --- |
| 补缺规划 | 不SELECT payload或事实正文；测试记录读取列与字节，证明历史分笔大小增加不放大正文读取；核对中间缺日/旧契约仍发现 |
| 单股单日/页 | 主键或有界索引访问；分笔200点首/后续页各仅返回该页，峰值内存不随全日点数线性增长 |

## 实施确定的布局与版本边界

逐行分笔隔离样本实测表与索引约65MiB，扩大了整批数据空间和导入成本，因此按第9节分支选择stock_intraday_trade_block。每点用秒数、类型位图和7个int64/IEEE754 binary64原类型数值无损编码，zlib6压缩；块最多200点/12400字节解码正文，block_hash校验压缩内容，读取校验块与来源时间边界。正式代码只使用块布局，逐行分笔仅留在独占实验库，不发布双布局。trade block按200笔形成修订单元，只更新受影响块和业务头。

SQL冷回源同内容确认通过既有每项目collection_state推进SQL确认进度，业务头/事实不写；同一最近确认证券日的观测栅栏阻止介于A/B的异内容C回写。Redis可信命中仍完全不访问SQL。已丢失或过期的Redis后续无变化确认观测无法从不更新的业务头恢复；项目SQL状态也不是全部证券日观测历史，因此不能承诺恢复任意内存确认上界。该边界沿既有“Redis纯内存、SQL只保存最近SQL确认”的项目规则，不通过永久逐日状态或无变化业务UPDATE制造跨Redis恢复保证。真实来源没有修订版本，仍不宣称严格历史版本回放。

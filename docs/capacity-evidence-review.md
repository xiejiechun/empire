# 隔离容量与资源稳定性验收

日期：2026-09-27。对应系统审计 P2-24。本项建立可重复的本地容量证据，目标是尽早发现代理目录、下载准入、取消和连接回收的退化；不连接 RouterProxy、共享 Redis、MySQL、真实代理或公开源站。

## 正式入口与边界

- `scripts/measure_capacity.py` 是唯一容量测量入口，默认写入 `build/capacity-report.json`；`--quick` 使用更短但固定的模拟延迟，供发布门禁使用。
- 测量直接调用生产 `ProxyPool`、`HttpService`、路由许可、响应读取和缓冲预算。虚拟目录只实现这些生产服务所调用的 Redis 脚本语义，HTTP 响应只来自 `httpx.MockTransport`。
- 所有候选在实际分配前仍执行目录映射和租约核实。脚本没有新增主动健康探测、生产者写入或第二套调度算法。
- 报告中的解析、归档排队、Redis 确认和 SQL 确认是固定延迟模型，用于观察端到端排队传播，不是共享数据库的实测延迟；真实设备、网络、来源和数据库容量必须另行隔离验收。
- 模拟出口数量表示并发模型输入，不能解释为真实设备吞吐或新浪、巨潮许可的请求速率。

## 覆盖矩阵

| 场景 | 固定输入 | 核查点 |
| --- | --- | --- |
| 独立出口 | 10、30、50、100 个设备及独立出口 | p50/p95、吞吐、峰值并发、目录读取、候选核实、RSS、句柄 |
| 同 IP 多设备 | 50 台设备、10 个出口 IP | 峰值并发不超过 10，不能按设备数放大 |
| 连接故障与重试 | 20 个请求，每 4 个请求首次连接失败 | 正式重试后恢复；每次尝试重新获取并核实候选 |
| 429 | 10 个请求，每 5 个返回 429 | 建立站点级冷却，不通过换代理绕过 |
| 取消 | 20 个慢请求，取消一半 | 请求、许可、响应和缓冲全部回收 |
| 长期抖动 | 1000 次退役/重新加入，并取消 1000 个竞争分配 | 等待、忙碌、退役和关闭任务归零；RSS/句柄不持续越过守卫线 |

每个 HTTP 场景输出请求数、完成/失败/取消、尝试数、耗时、吞吐、错误率、峰值并发、目录读取、候选核实，以及排队、下载、解析、归档排队、Redis/SQL 确认和端到端的 p50/p95/max。资源采样使用 Windows 进程工作集和句柄计数，不增加 `psutil` 运行依赖。

## 自动验收

报告只有同时满足以下条件才返回成功：

1. 所有场景结束后代理等待、忙碌、退役、关闭任务，HTTP 在途、未关闭响应、缓冲占用和准入等待均为 0。
2. 每次网络尝试均至少有一次候选租约核实。
3. 50 台共享设备不会突破 10 个独立出口的并发。
4. 429 已建立站点冷却；连接故障确实重试并恢复；取消确实发生。
5. 完成 1000 次上下线和取消；强制回收后的 RSS 相对起点增长不超过 16 MiB、句柄不超过 8 个，且所有池状态归零。

RSS 守卫线用于发现持续增长，不声称 Python 分配器每轮都把工作集恢复为完全相同的字节数。报告保留每 100 轮采样，便于判断趋势而不是只看一个瞬时终点。

## 发布门禁

`verify-release.ps1` 在完整测试后运行快速容量基线，失败即停止发布。最终 `build/release-report.json` 同时嵌入容量报告并保留 `build/capacity-report.json` 路径，随后才执行 DPI 布局、打包和 EXE smoke。普通业务启动不会自动运行压测，也不会写入生产服务。

真实 100 台设备的长期网络、来源响应和数据库积压仍是部署验收项。执行时必须使用隔离目标或明确许可的测试服务，不能以本工具为由对公开来源无节制增压。

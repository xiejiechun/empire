## 已修正：发布等待期间隔离状态变化

- 优先级：P2，正确性边界，不是数据丢失或误删。
- 位置：`src/empire/plugins/pipeline/ingest.py` 的 `publish_page`。项目隔离检查发生在获取 `capacity_lock` 之前；锁等待结束后没有再次检查。非预留路径还会等待容量查询，预留路径不再检查全局阻断。
- 确定性复现：使用现有 `tests/test_ingest_reservations.py` 的纯内存替身，先持有容量锁，启动发布并让其进入锁等待，再把 `blocked_projects` 设置为该项目，最后释放锁。
- 实际结果：普通和预留发布均成功，队列从 0 变 1，断点 revision 从 0 变 1；预留剩余量从 2 变 1。复现没有连接 Redis/MySQL、没有处理生产错误记录。
- 影响：已经识别为隔离的项目仍可能继续发布已等待的数据，违反“暂停新业务入队、不推进断点、不消耗预留”的约定；原有隔离消息仍然保留。
- 建议：在完成所有准入等待后、提交 Redis 发布命令前，以唯一公共检查复核全局阻断及项目隔离，普通与预留路径都执行。明确提交点：命令已经发出后新发生的隔离不得冒险撤销原子提交或伪造失败。
- 验收：覆盖锁等待时隔离、容量查询时隔离、预留路径全局阻断及不相关项目不受影响；被拒绝时断点、队列和预留不变。随后重新执行发布门禁并更新制品证据。
- 后续修正：`_check_archive_admission` 统一检查全局与项目隔离。普通与预留发布在完成锁等待、容量查询后，紧邻 Redis 命令提交前再次执行；命令提交后仍尊重实际原子提交结果，不事后伪造拒绝。
- 定向验收：`tests/test_ingest_reservations.py` 共 18 项通过，其中新增 11 项覆盖锁等待、容量查询、无关项目、预留条数/字节不变和提交后隔离不伪造失败。该修复来自纯内存复现，不涉及生产错误记录清理。

# 数据预览逐项目展示与实施方案

2026-10-11 · 设计交付，尚未实施。面向后续逐项目承接的 AI 与审阅者。

## 1. 范围、依据与设计结论

本次覆盖当前 `PageContribution.catalogued=True` 的全部 **27 个数据页面**，另设计数据目录入口。名称和 ID 来自当前工作区插件声明，不把数据准备中尚无页面的待建能力算作现有页面。实施前重新枚举，登记此后新增或退役项。

现状通过 UI、正式查询、字段契约和来源说明审阅确认；没有操作运行中的 EXE，没有核实现场数据库覆盖，也没有做真实桌面可用性测试。因此本文的“现状”指源码所定义的行为，“目标”均为拟实施设计。

工作区存在大量已有改动，同一项目另有聊天核实通达信增发送配接口。本轮仅新增本文，不修改功能源码、共享审阅记录、配置、数据、采集计划或发布包。未来实现以届时现行契约为准，尤其注意增发送配字段与查询的后续变化。

主要问题不是表格本身，而是展示没有匹配用户问题：

| 用户要做的事 | 合适的主视图 | 表格的职责 |
| --- | --- | --- |
| 找一只证券、比较一批记录 | 紧凑可搜索列表 | 主视图，控制默认列数 |
| 看价格和量随时间变化 | 走势图、K 线、同步量额图 | 核对精确数值 |
| 看某天是否交易 | 月历 | 备用日期清单 |
| 读新闻或公司资料 | 阅读流、资料页 | 可选批量检索 |
| 理解公司事件及关键日期 | 事件时间线、方案卡、日期节点 | 跨证券检索与比较 |
| 对比多个报告期 | 有层级的财报矩阵 | 本身就是正确主视图 |
| 找行业、指数与成分关系 | 目录与详情联动 | 成分列表 |

不以“增加图表数量”为验收目标。禁止把缺失字段推导成漂亮但不真实的分析，也不以满屏大卡片替代高效列表。

## 2. 全部页面共用的使用规则

### 2.1 进入页面就知道看什么

- 页首只保留数据名称、证券/指数身份、当前查询日期或范围、简短状态。技术字段、数据库表名、来源原始标记放入“数据说明 / 更多字段”。影响理解的限制贴近对应图表。
- 从其他页进入时优先使用传入上下文，其次恢复本页会话状态。首次单证券页提供搜索与已归档证券候选；不固定打开任意代码，也不要求用户记住来源专用代码。
- 单日页优先选择该证券该项目最近已归档日期；找不到时保持待选择状态。标明“当前展示日期”，不能因用户查的日期为空就偷偷切到其他日期。
- 日线图首次建议最近一年，提供近月、近季、近年、自定义；只有已确认范围可供导航。不能把范围筛选当作来源覆盖证明。
- 跨证券事件页默认最近已归档事件，按日期倒序；日期缺失事件单独标记。选择证券后进入该证券时间线。不得为了完整时间线无界加载全库。

### 2.2 查询、阅读与返回

- 编辑中的筛选条件和已应用条件分离。用户点击查询或回车才应用文字/日期草稿；旧结果仍显示其证券和日期。乱序响应不得覆盖新查询。
- 刷新保持所选业务记录、滚动位置、展开状态和筛选草稿。新闻阅读中不被新记录顶走；切页回来恢复位置。
- 主视图和明细视图是同一查询结果的不同呈现，共用正式查询与身份。不得各造一套数据库读取、缓存或数据解释规则。
- 页面阅读不触发采集。缺数据时可“查看采集任务”或“查看数据准备”，用户进入后再操作；图表加载失败可明确重试。
- 支持键盘搜索、焦点遍历、复制；图表必须可通过明细获取精确值。日期框、数字框、下拉框和滑块继续禁止滚轮改值；页面与表格滚动保留。
- 会话内状态交给既有 `save_ui_state / restore_ui_state`。本阶段不承诺重启保留自选、布局和收藏，不新增个人偏好存储路径。

### 2.3 状态、时间和数值

明确区分：未选条件、加载中、查询失败、范围内未归档、来源确认无记录、部分覆盖、成功展示。只有现有完整性证据支持时才显示“该范围确认无记录 / 完整”；没有证据则标记未知，不读取全历史来凑结论。

发布时间、事件生效日期、来源查询日期、报告期、内容变更时间、成功核验时间分别命名。MySQL DATETIME 按北京时间解释；不能把内容更新时间当作采集鲜度。查询页不以 Redis 可用为前提。

金额和数量每个轴/列注明单位，万/亿只是显示缩写；悬停/明细保留精确值。未知为“—”并说明原因，零为 0，来源异常保留原值与标记。未知量单位继续写“来源单位”，不转成股/手/元。红绿之外必须有正负号、文字或线型，不仅靠颜色传意。

### 2.4 图表的真实性和性能

- 分钟图有时间轴和午休间隔提示；无证据不能把缺点连成连续行情。默认按来源点绘制，不能合成分钟 OHLC。
- 所有图表写清实际加载区间；不拿第一页 200 条冒充全天。有限单日序列可沿正式游标读完后展示，读取上限由契约决定；大型分笔采用有界时间窗。
- 曲线抽样须说明，悬停和明细回到真实记录。不可用抽样点计算最高、最低、合计。K 线不得以任意删点代替周期聚合。
- 竞价及分笔同一时间多点按来源顺序保留，不能在前端按时间去重。任何聚合必须有明确业务定义与可核对的成员范围。
- 只有确认是期间增量的量额才合计；不能把累计量再累加。大单净额是分钟值还是累计值未核实前，不提供“累计净流入”。
- UI 主线程不执行 SQL、全量解压或大范围计算。使用既有 `QueryScope` 管理查询，销毁页面取消读取；管理写命令不受切页取消。

### 2.5 推荐布局骨架

这三种是布局职责，不要求建立统一巨型页面基类。

```text
行情页：身份与日期 → 查询状态 → 主图 → 同步副图 → 明细/数据说明
事件页：搜索与范围 → 事件摘要列表 | 所选方案/事件详情 → 更多来源信息
资料页：证券选择 → 关键资料 → 分组字段 → 正文/历史沿革
```

宽窗口采用左右分区，可拖动调整；窄窗口改上下分区或切换详情，不能把正文固定在 100～250 像素高区域。建议验收 1280×800、1920×1080 和 150% 缩放，以应用实际支持的最小窗口再次核实。单位、状态、主操作不得被截掉。

## 4. 逐项实施卡

每张卡的验收都必须同时通过第 2 节公共规则。下面的字段仅限当前正式数据已经提供的内容；新增查询能力不等于新增采集任务。

### V01 股票列表 · `stocks`

- **现状与目的**：现有列表适合批量查找，不应强制改成一只股票一张大卡片。主要解决“找谁、属于哪个市场、接下来查看什么”。
- **首屏**：保留名称、代码、市场及现有有用分类的紧凑列表；来源和范围放表头摘要，不把所有技术字段占作常驻列。右侧显示选中证券身份及可用的数据入口。
- **交互**：代码/名称搜索，市场筛选；点选预览，双击打开证券摘要；跳转资料、行情、财报、事件时带证券身份。来源字段不足时不显示虚构的行业/最新价格。
- **查询与改造点**：`ui/stocks.py`、`data/stocks.py`。沿用当前股票正式查询；摘要不要每行触发多个关联查询。跨页上下文见第 5 节。
- **专项验收**：同代码不同市场不会串页；北交所历史别名不被猜测映射；没有某项数据可进入对应页查看缺口；刷新保留选择。当前股票列表不宣传成历史全证券池。

### V02 财经快讯 · `news`

- **现状与目的**：表格标题加固定高度正文，读新闻需要频繁上下切换。改为能够连续阅读的时间流。
- **首屏**：按北京时间日期分组，时间窄列＋标题＋两三行正文摘要；重点用明确标签。点开可在原位展开完整正文，长篇用独立阅读区；复制和来源链接靠近正文。
- **交互**：保留全文搜索、仅重点；增加日期范围前先补正式查询。分页可表现为“加载更早”，仍用稳定游标。新内容只显示“有更新，点击查看”，不移动当前阅读位置。
- **查询与改造点**：`ui/news.py`、`data/news.py`；保留既有锚点/游标语义。日期分组由返回发布时间形成，不按前端页号分组；正文按文本安全呈现。
- **专项验收**：跨页同一天分组连续；相同时间多条新闻不丢；超长正文、无标题、无链接可读；来源修订后身份不变，历史阅读不跳动。来源新闻 ID 和存储版本进入详情，不变成普通用户主列。

### V03 交易日历 · `calendar`

- **现状与目的**：现在逐日表格，需要读文字才能看出一个月的安排。改为周一至周日的月历网格。
- **首屏**：本月 7 列日格，格内日期＋“交易 / 休市 / 未知”；当前日用边框，不改变交易状态颜色。顶部月切换、回本月；侧栏选中日期及来源信息。
- **交互**：点击日格看日期详情，显示月内交易日数、休市日数、未知数；统计限本月实际证据。支持切到“日期清单”复制核对。
- **查询与改造点**：`ui/trade_calendar.py`、`data/trade_calendar.py`。复用现有按月内容及完整性证据，不按周末生成状态；月历补齐的格子只是显示容器。
- **专项验收**：缺一天必须出现未知；1990-12 起点前标范围外；未来日期说明“来源当前安排”；Redis 不可用仍能查 MySQL；旧内容更新时间不被误报为数据过期。

### V04 上市与发行资料 · `listings`

- **现状与目的**：发行价格、募资、承销商等挤在宽表里，沿革正文被压缩。目标是阅读一家公司的上市档案。
- **首屏**：左侧证券搜索结果，右侧身份标题；第一行首次上市日、发行价、发行量、实际募资；下面“发行资料”“中介机构”“历史沿革”分节。正文获得正常阅读宽度和滚动高度。
- **交互**：资料/沿革快捷定位，长机构名换行，复制单字段或沿革正文；跨证券模式保留精简索引，不默认展示全部字段。
- **查询与改造点**：`ui/listings.py`、`data/listings.py`。列表只取摘要，选中后复用 `detail` 按需取正文。发行量、募资分别保留单位，不从价格乘数量替代来源值。
- **专项验收**：日期/募资缺失与 0 区分；历史沿革空值、长正文、中介多名称；晚到详情不能落到新证券。首次上市资料不能冒充历次上市事件或完整退市证券档案。

### V05 公司更名 · `names_company`

- **现状与目的**：平铺旧新名称，难以阅读公司全称的演变。选择证券后按时间串联“旧公司名 → 新公司名”。
- **首屏与交互**：跨证券先显示日期、证券、名称变化的紧凑事件摘要；进入单证券时间线，按年分组、最新在上，长公司名自动换行。保留日期筛选/顺序切换的设计，查询不支持的条件先补正式接口。
- **查询与改造点**：`ui/name_changes.py`、`data/name_changes.py`、`contracts/name_changes.py`。来源出现次数和行业标签放详情；业务键与游标继续按现有契约。
- **专项验收**：同日多个不同变更分别呈现；链条不连续明确显示“现有记录未形成完整名称链”，不补造中间名称；当前行业标签不放在历史日期上暗示历史归属。

### V06 股票更名 · `names_security`

- **现状与目的**：与公司更名共用表格，但用户要看的是证券简称变化。
- **首屏与交互**：证券简称变更时间线，突出简称前后对比；检索旧简称时，如正式查询暂不支持则明确补接口，不在当前页结果中假装全库搜索。提供前往 ST 事件的明确入口。
- **查询与改造点**：与 V05 共用呈现组件，保留 `security` 独立类型、页面和查询归属。标题始终写股票简称，不能把公司全称替代简称。
- **专项验收**：带 ST/*ST 的简称原样保留；不能仅凭名字推断对应 ST 实施/撤销事件；更名日期和当前证券名称分开说明；长链用有界分段加载。

### V07 实施ST · `st_implementation`

- **现状与目的**：原因塞在宽表末列。用户首先需要知道何时、发生了什么变化、原因是什么。
- **首屏与交互**：跨证券事件摘要，点选显示日期、前后简称、风险警示原因；单证券呈现事件时间线。原因完整阅读，行业标签和来源出现次数默认收起。
- **查询与改造点**：`ui/st_events.py`、`data/st_events.py`、`contracts/st_events.py`。复用实施类别；状态转换只按已核实字段解释，否则原文展示。
- **专项验收**：实施类别中存在风险类型转换时，不统一写成“首次ST”；缺原因标来源未提供；不绘制直到今天的 ST 持续区间，不宣称能还原每日 ST 状态。

### V08 撤销ST · `st_removal`

- **首屏与交互**：沿用 V07 的布局，但突出“撤销/变更后的简称”和来源原因。提供查看实施事件入口，可对照两类记录；独立记录不自动配对成完整生命周期。
- **查询与改造点**：与 V07 共用组件，保留 `removal` 的独立查询、来源类别及标题；不把两个项目的身份或归档合并。
- **专项验收**：*ST 变为 ST 时不能显示“已解除全部风险”；没有对应实施记录不补造开始日期；最新撤销事件不能被当成当前交易资格结论。

### V09 暂停恢复终止上市 · `listing_status`

- **现状与目的**：日期/类型列表和一段说明，缺少事件间的视觉区分。
- **首屏与交互**：按来源日期分组的事件时间线，以“暂停上市”“恢复上市”“终止上市”文字标签区分；保留证券、事件类型、日期范围筛选。选中后展开来源说明；单证券模式只串联已存在事件。
- **查询与改造点**：`ui/listing_status.py`、`data/listing_status.py`；正文仍按需查询，不扫历史正文生成摘要。

- **查询与改造点**：`ui/kaipanla_quote_page.py`、`ui/kaipanla_quote_view.py`、`ui/kaipanla_quote_chart.py`、`ui/kaipanla_quote_format.py`。继续读取独立分时归档，不由盘口快照造走势。
- **专项验收**：盘口有数据但分时无数据，两区分别提示；买卖空档、显式0、未知值不混淆；估值比率含负值时不删掉；不能当作实时盘口、收盘精确时刻或全天回放，来源 `time` 未有时间契约不得显示成时间戳。

## 5. 数据目录与公共能力的实施边界

### C01 数据目录入口 · `catalog`

默认按业务分类展示紧凑条目，每项一行或两行：名称、用途、来源，以及“日历 / 走势 / 事件 / 报表”等呈现提示。不让数据库表名占主屏；表名仍保留可搜索和详情展示。维持分类/来源过滤和键盘定位，不为27项新增27个固定菜单。

入口不预先启动27个业务页面，不逐页查询数据库来计算动态徽标。若以后展示“已有数据/未采集”，必须有统一有界摘要服务；当前没有就不显示。数据准备中的待建项继续说明尚无预览，不跳到无关通用表格。

### C02 公共上下文和证券选择

当前 `NavigationContext` 只有 `task_id`，所以本文的“带证券/日期跳转”是**待建能力**，不能声称现已支持。第一批实施者需在 `contracts/ui.py` 与桌面导航的正式入口明确设计：

- 证券用统一证券身份；指数使用带来源类型的指数身份，不能混进股票六位代码。
- 日期范围、单日、事件定位键为显式可校验字段；非法或接收页不支持的上下文友好提示。
- 接收页面按需创建后应用上下文，返回时还原发送页状态。管理跳转 `task_id` 仍是现行正式路径。
- 证券候选通过正式查询有界返回，保留市场和名称；不能只查当前股票列表导致历史事件中的退市证券无法定位。

这是跨页面基础任务，先独立完成和验收。若用户先做单个页面，该页可先保留自身查询入口；交付必须说明跨页带参尚未完成，而不是页面自行创建全局变量传参。

### C03 可复用但不应过度抽象的组件

候选组件：查询状态条、证券选择、单位格式化、事件卡、日期节点、图表光标/时间轴、明细面板、财报矩阵。放独立公共模块，数据语义仍由业务插件决定。复用已有 K 线与分时绘图能力前先检查接口和缺值行为，不为了统一样式换掉全部图表库。

每个业务页面只创建自身控件/计时器，保留独立插件启停与 LRU。UI Python 以300行以内为目标，350行是当前检查上限；不能继续把所有开盘啦图表塞进一个 `ProductPage` 大分支。公共模块不反向导入某个业务页面。

## 6. 查询能力差距与数据范围

下面是实现前必须逐项确认的工作，不代表接口已经存在。

| 需求 | 当前可复用基础 | 必要补充/边界 |
| --- | --- | --- |
| 跨页面证券/指数/日期联动 | PageContribution、导航入口、页面状态 | 扩展受校验的导航上下文，统一候选搜索 |
| 最近已归档日/前后日 | 开盘啦证券日头与现有正式查询 | 为指定项目/证券提供有界日期导航，不靠加载全年逐日试探 |
| 全日有限分钟图 | 开盘啦游标 page、盘口已有分时图 | 校验实际页覆盖；别把第一页作为全天 |
| 分笔时间窗 | page 的起止时间参数 | 概览另核实有界能力，非必做全天扫描 |
| 指数日线范围图 | 现有日线分页、年度覆盖与质量 | 有界分段读取、异常日展示、范围/截断说明 |
| 行业目录和指定成员 | 当前行业扁平分页 | 目录、成员、计数的正式查询，不能仅前端去重 |
| 事件时间/状态/名称筛选 | 各项目现有分页 | 按项目明确字段、排序与索引适用性；不是所有查询都已有这些过滤 |
| 新闻日期范围 | 现有全文/重点、锚点游标 | 新范围条件与游标契约一起回归 |
| 完整/确认空/未归档 | 既有数据准备和归档覆盖证据 | 有则复用、无则未知，不以行数或最新记录替代证明 |

第一阶段不默认改表、不新增采集、不存图表副本或冗余业务数据。确实需要索引、结构化字段或实质改造查询存储时，按[业务数据库设计规范](database-design-standard.md)先提交设计，沿显式维护路径实施；“美化页面”不等于授权顺便迁移业务库。

本次不把业务数据可用范围写死成已采完范围。有关来源限制以[开盘啦字段字典](kaipanla-field-dictionary.md)、[财报说明](ths-financial-statements.md)、[指数行情说明](ths-index-prices.md)、[停复牌说明](tdx-suspensions.md)、[增发送配说明](tdx-capital-actions.md)及现行契约为准。

## 7. 逐项目交接与执行顺序

建议先 C01/C02 和最小公共状态能力，再做 **V03 交易日历、V02 新闻、V21 分时走势、V19 指数日线、V04 上市资料、V11 分红送转**。这六项分别验证日历、阅读、图表、行情范围、档案、事件六类主要形式。随后完成开盘啦其余图表、行业/指数目录、公司事件；最后完善已具备正确形式的财报、复权与盘口。

不要求等待所有公共组件建完才做简单页面，也不一次开发大而全 UI 框架。每项目完成后让用户审阅实际页面，再把经验证的共性用于下一项目。

多人或多个 AI 承接时，共享组件、导航契约、财报三表公共模块、增发送配公共模块、开盘啦查询/图表公共模块各指定单一修改负责人；其余任务只改自身业务组件。单个项目可交付，但同一共享文件不能同时改。数据库、桌面和发布始终串行；其他 AI 的工作区也不隔离共享服务。

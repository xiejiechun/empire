# P2-22 归档统计口径验收

日期：2026-09-27。

## 正式口径

| 名称 | 含义 | 不能解释为 |
| --- | --- | --- |
| 采集记录数 | 来源响应通过采集校验的业务记录数量 | MySQL 新增数量 |
| 待归档消息 | Redis Stream 中尚未成功确认的业务消息数量 | 股票、新闻或日历记录数量 |
| 已处理记录 `processed_count` | 归档器成功核对的业务记录数量，包含业务写入、内容相同、可信摘要命中和旧版本确认 | INSERT/UPDATE 数量 |
| 业务写入记录 `written_count` | 本次发生业务数据写入的记录数量 | 队列消息数量 |
| 确认无需写入 | `processed_count - written_count`，仅在两个可靠统计同时存在时展示 | 归档失败或未处理数量 |

## 实施

- 新归档运行记录以 `processed_count`、`written_count` 代替含义模糊的 `row_count`。归档结果和采集确认内部仍使用各自现行契约中的 `row_count`，不把运行记录格式反向渗入业务协议。
- 缓存命中同样写入“已处理、业务写入 0”的归档运行记录；SQL 内容相同和旧版本确认也不再显示为“入库很多条”。
- 归档列表及详情分别展示已处理、业务写入和确认无需写入；字段缺失时显示“—”，不猜测旧 Redis 运行记录。
- 工作台“待入库数据”改为“待归档消息”，说明一条消息可包含多条记录；系统状态的 `archive.archived` 改显示为“本次启动已确认消息”。最近采集表明确为“采集记录数”。
- 没有增加 MySQL 统计表、双写或历史转换层。Redis 运行记录仍按项目保留最近 100 条，新格式随新归档自然进入并淘汰旧记录。

## 验证边界

集成测试覆盖首次新闻写入、可信摘要免 SQL、摘要失效后 SQL 相同确认和再次缓存命中，验证稳定运行记录均有处理数，而业务写入只计算真实变化。股票完整批次验证已处理与业务写入数量；界面测试验证 0 写入不会被显示为入库条数。

`written_count` 是发生业务写入的业务记录数，不宣称等于数据库驱动报告的全部受影响物理行数。例如股票整表替换涉及删除旧集合与插入新集合，界面展示新集合中发生写入的业务记录数，不把删除维护动作重复相加。

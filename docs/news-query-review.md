# 财经新闻查询优化验收

日期：2026-09-26。范围：完成系统审计 P2-12 剩余的新闻列表查询与分页优化；不改变采集、归档、业务表或包含搜索语义。

## 实际改动

| 项目 | 实现与价值 |
| --- | --- |
| 正式分页契约 | `news.query.list_news` 只接受首屏上界和 `(published_at, news_id)` 游标；退役 offset 参数及 100000 上限，不保留双分页路径 |
| 稳定翻页 | 首屏第一条固定本次查看上界，下一页使用严格小于末条游标；翻页期间新新闻不会导致遗漏、重复或页内容位移 |
| 统计成本 | 精确总数仅在首屏计算，后续页返回 `total=None`，界面沿用首屏总数 |
| 空搜索 | 没有搜索词时不构造 `LIKE '%%'`，直接使用已有 `ix_news_published` 或 `ix_news_important` 排序索引 |
| 搜索语义 | 标题/正文搜索继续支持包含匹配和 `%`、`_` 字面转义；没有在同一能力下暗中切换到中文分词或增加第二搜索实现 |
| 交互 | 上一页使用本地游标栈，下一页只在服务返回下一游标时可用；首页每 15 秒重新建立最新视图，后续页刷新保持当前上界 |

## 验证证据

- 隔离来源写入 130 条后取首屏，再插入 3 条更新新闻，逐页遍历结果恰好为原 130 条，ID 无遗漏和重复；重新读取首屏显示 133 条。
- SQL 事件断言：空搜索首屏恰好执行一条列表和一条 COUNT，不含 LIKE/OFFSET；后续每页仅一条游标 SELECT，不执行 COUNT/OFFSET。
- 使用当前 MySQL 会话的临时 InnoDB 表生成 1,000,000 行，测试结束随连接销毁，未写生产业务表。实测：首屏 0.0046 秒；翻过 100050 条后的游标页 0.0011 秒，对应 OFFSET 0.0475 秒；接近末页的游标 0.0008 秒，对应 OFFSET 0.4881 秒。单次本机结果不是跨设备 SLA，但确认了复杂度方向。
- 当前正式表核查时为 3,228 条，空列表 EXPLAIN 使用 `ix_news_published` 且覆盖索引。搜索仍使用同一排序索引逐条判断包含条件。
- 参数测试拒绝损坏、带时区、负数及布尔冒充整数的游标；界面测试覆盖查询切换、上下页游标、选中详情和关闭取消。
- 开启隔离集成测试的完整套件：813 passed、2 skipped；跳过项仅为当前 Windows 用户无符号链接权限。Ruff、依赖一致性与 Git 空白检查通过。正常关闭旧桌面后构建成功，新 EXE 的 8 秒 smoke 退出码 0，随后重新打开交互桌面。

## 全文索引决定

本轮不增加 MySQL 中文 ngram FULLTEXT，也不引入搜索服务。原因不是“搜索已经有全文索引”，而是当前只有 3,228 条、页面搜索要求任意包含，而 ngram 分词会改变单字、标点和部分字串的匹配语义。现有搜索慢时只占隔离浏览资源，不再阻塞归档与配置写入。未来在真实数据达到可测瓶颈后，应先确定允许的搜索语义、常用关键词和目标响应时间，再通过显式维护入口添加并验证索引；应用启动不得迁移。

## 未改变的边界

- `finance_news` 主键、现有两个排序索引和所有业务数据未修改；本轮无持久 DDL、无迁移脚本、无生产数据清理。
- 游标是界面查看状态，不是采集断点、归档确认或缓存摘要，不能授权删除待归档消息。
- 精确总数仍可能随历史增长变慢，但只在首屏/条件变化时计算；如以后成为瓶颈，应单独设计近似或缓存契约，不能悄悄显示过期总数。

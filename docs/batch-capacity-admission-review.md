# 整批入队容量验收

## 目标

新浪股票列表必须收齐全部页和完成标记才能归档。旧路径逐页检查当时剩余容量：若半批消息已经占满队列或推高 Redis 水位，采集会等待归档释放，而归档又等待尚未入队的 `complete`，形成条件死锁。本次将不可完成状态提前到首条业务消息之前判定，不删除已入队业务数据。

## 正式路径

1. 新批次先请求 count；取得总数后计算页数，在发布 `stock.universe.start` 前一次预留 `start + pages + complete`。
2. 恢复批次读取正式 checkpoint，只预留尚未发布的分页和 `complete`。
3. `pipeline.ingest` 在同一容量锁内核对 Stream 当前长度、所有其他未消耗预留、`max_queue_entries`、Redis 当前内存及高水位。普通消息也在同一锁内避开已预留槽位。
4. Lua 原子发布成功后才扣减对应消息槽及最坏字节额度。游标过期、Redis 写入失败均不扣减。
5. 批次正常结束、失败、取消或提前终止时幂等释放剩余额度；同一 `job_key` 同时申请第二份预留会明确拒绝。

预留是当前进程的准入状态，不是新的持久化协议，不写 Redis key。进程退出后，已发布 Stream 消息和 checkpoint 仍是恢复权威；重启按 checkpoint 重新计算剩余预留。这样没有增加兼容层、双写或第二套断点。

## 配置关系

- `ingest.max_queue_entries`：1～1,000,000 的整数。
- `ingest.max_page_bytes`：1 KiB～16 MiB 的整数；也是每条预留的最坏正文预算。
- `0 < low_watermark < high_watermark < 1`，布尔值和字符串不接受。
- `archive.index_max_entries >= ingest.max_queue_entries`，确保归档调度索引可覆盖允许进入的 Stream 消息。

共享 Redis 的其他使用者仍可在准入后增加物理内存，Redis 自身也有结构开销，因此进程内预留不宣称锁定物理内存。正式保护仍包括共享实例 `maxmemory/noeviction`、水位检查及 Lua 中的 Stream 条数上限；外部竞争导致发布失败时保留已发布消息和断点，后续按正式恢复路径重试。

## 自动验证

- 已预留批次后，普通任务不能偷占其完成槽；释放后容量重新可用。
- 成功发布才消耗，stale checkpoint 不消耗；释放可重复调用。
- 同一任务不能取得两份预留，预留必须覆盖本次消息数。
- 队列槽或 Redis 高水位不足时，首条业务消息前拒绝整批准入并给出所需量、现有量和上限。
- 新股票批次预留 `pages + 2`，恢复批次仅预留剩余页和完成标记；成功、异常和取消路径均按所有权释放。
- 配置默认值、类型、范围、水位顺序以及归档索引覆盖关系均有回归测试。

本验收不等于真实 100～1000 个出口的吞吐或共享 Redis 压力测试；它关闭的是 Empire 进程内可确定的容量互相挤占路径。

本轮在真实 Redis/MySQL 隔离测试范围执行全套自动测试：846 项通过；另有 2 项仅因当前 Windows 账户没有符号链接权限而跳过。Ruff、依赖一致性、差异空白检查和 Windows 打包均通过。测试不重启共享服务、不清空共享 Redis，也不删除业务数据。

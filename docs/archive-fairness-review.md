# 多项目归档公平调度验收

> 后续 P2-11 已将下文历史的未知 schema 全局保护收窄为明确登记归属的项目隔离；归属不明仍全局阻断。现行规则见 [契约隔离验收](schema-isolation-review.md)。

日期：2026-09-26。本轮落实系统审计 P2-10：扫描总预算、跨项目公平处理及未完成批次重复读取。不新增采集项目，不改变代理和网站频率，也不实施下一阶段 SQL 读写排队隔离。

## 操作与边界

软件正常重启后启用。采集数据仍先写同一 Redis Stream，入队立即唤醒统一归档器；60 秒扫描保留为恢复检查。消息多时持续分轮处理，不在每轮之间等待一分钟。“立即归档”执行一轮并继续后台处理，队列是否清空应看待归档数量，而不能仅凭按钮返回。

“系统设置 → 运行状态”新增扫描待继续、已索引消息、可调度/等待重试项目、最近一轮扫描量与处理单元。一个项目失败仍留队，其他已发现项目可以继续轮到；未知 schema 仍全局暂停，没有借本次调度优化放宽数据安全边界。

## 逐项核查

| 要求 | 实际实现 | 核查 |
| --- | --- | --- |
| 每轮读取有界 | 默认最多 500 条、8 MiB 返回消息数据；Redis Lua 在返回前截取预算内窗口，单条超限明确报错留队 | 消息/字节窗口及超大单消息测试，未处理内容不裁剪、不删除 |
| 扫描不反复回头 | 固定截止 ID、跨轮推进游标；内存只索引有界 Stream ID 与来源/批次身份，不保留全队列正文 | 1000/3000 条前置积压后的小项目，在大项目未清空前得到处理；每轮扫描条数与字节均受限 |
| 项目轮转 | 默认最多 32 个业务单元/轮，项目间轮转；同一增量批次内按 Stream 页顺序处理 | 大量新闻与独立新闻/日历项目混合时，小项目不必等大项目归档完；单次处理预算为 1 仍保持下一项目的位置 |
| 时间预算 | 扫描窗口间、处理单元间分别检查默认 50 毫秒预算 | 慢 Redis 窗口、慢写入器测试确认在下一个单元前让出；不强行中断 I/O 或事务 |
| 股票完整性 | 只在扫描通过完整固定上界后组装；股票完整列表仍是一个业务单元和一个 SQL 事务 | 完成消息与分页跨扫描窗口、缺页/变页、旧批次重放、SQL 失败保留及实际 MySQL 完整发布回归 |
| 避免反复读取未完成股票 | 不完整批次停放为 ID 索引，新完成标记、新批次或 60 秒恢复检查触发重核 | 多次无新增消息的 flush 不再读取同一未完成批次正文；重启从原 Stream 重建索引 |
| 新批次不误删旧完整数据 | 旧批次清理依赖新断点，并等待共享扫描器通过断点之后捕获的 Stream 上界 | 完成标记在旧扫描上界之后到达、此时又开始新批次及 SQL 故障的既有回归继续通过；退役原无界尾部复扫 |
| 有效消息不丢 | SQL/缓存/确认失败保留业务消息；确认成功才 XDEL，对应索引同步释放；取消后归还调度所有权 | 故障项目保留、其他项目完成、提交后确认失败、取消/重试、重启和缓存回源回归 |
| 有界调度索引 | 默认最多 100000 个 ID；满额先处理已发现的独立页，无法释放则报错留队，不伪造股票完成边界 | 小容量索引能分轮排空增量页；容量越界、字段类型、正常回收测试 |
| 未知 schema 保持保障 | 发现不支持的契约后全局暂停，扫描位置不跳过该消息 | 连续重试仍停在原未知消息，已知消息不趁机绕过，全部业务消息保留 |
| UI 与说明 | 增加诊断而不新增操作表单；更新软件内说明、桌面指南、架构及配置示例 | 880×720、1320×900 离屏布局断言与截图；页面按钮可达，无重叠 |

## 默认预算与配置

以下为 `[archive]` 的启动参数；本轮没有改写本机用户配置，缺省按正式默认值启用。不是下载资源的 512 MiB 缓冲，也不对 Python 进程总内存做上限承诺。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| batch_size | 100 | 单次 Redis 扫描窗口最大条数，1～100 |
| scan_max_messages | 500 | 每轮最多发现消息数 |
| scan_max_bytes | 8388608 | 每轮扫描返回的 ID/字段/消息字节，不含 Redis 协议开销 |
| scan_time_ms | 50 | 扫描窗口之间的协作时间预算 |
| work_max_units | 32 | 每轮最多处理业务单元数 |
| work_time_ms | 50 | 业务单元之间的协作时间预算 |
| index_max_entries | 100000 | 调度 ID 索引容量，应与入队容量配套 |

业务单元为新闻一页、日历一月或股票一个完整列表。单个完整股票的加载、校验和事务仍可能超过 50 毫秒；不能因此拆开发布、丢页或取消已开始提交的事务。项目公平是在已发现项目和业务单元边界上实现，不声称尚未扫描到的队尾消息可以零延迟得到处理。全库故障时各项目均可能失败，公平调度不代表数据库本身可用。

## 实测中发现并修复的边界

1. 成功删除队尾后，最后存活 ID 可以倒退。当前使用 `XINFO STREAM last-generated-id` 作为边界，不把正常 ACK 误认为 Stream 重建，避免重复发现和提前重试。
2. 新消息唤醒可能在扫描旧范围的前几轮被消耗。扫描范围结束时再次核对最新队尾，确保旧边界之后的消息继续被调度，不睡到 60 秒恢复扫描。全量负载首次暴露该问题后，补充固定复现测试，并连续五轮通过针对性回归；不是仅增加测试等待时间掩盖停顿。
3. 超小索引容量时先处理已发现的增量页以释放位置；不能通过假装扫描结束来释放股票批次。

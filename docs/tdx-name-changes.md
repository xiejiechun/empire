# 通达信公司与股票更名

## 入门与日常操作

“采集管理 → 任务”分别提供公司更名、股票更名；“数据浏览”搜索对应名字查看。公司更名保存公司全称，股票更名保存证券简称，两者不能互相替代。两页显示证监会行业及通达信行业，字段来自更名接口；行业没有历史生效日期。默认每天北京时间18:00执行，代理优先、不可用时允许受频控的直连回退；已保存配置优先，用户可编辑计划。立即采集和重新初始化均核验来源全部历史，已入队轮次先完成归档。

## 生命周期与数据说明

| 项目 | 契约 |
| --- | --- |
| 初始化 | 1990-01-01至本轮启动北京时间日期；公司/股票栏目分别一次POST完整响应，容量30000，达到容量或来源总数不符拒绝发布 |
| 完整单位 | 全响应先校验结构、总数、市场、代码、日期与名称类型；再按SH/SZ/BJ三个市场分别事务归档（含有效空市场），三个消息均成功且本轮队列无残留才完成 |
| 后续与修订 | 每轮重新读全部历史，发现全范围修订及缺口；没有来源版本，使用请求开始绝对时间作响应代次，防止迟到旧响应覆盖，不冒充公告时间 |
| 中断 | 入队前失败不改断点；三个市场原子一次入队与断点提交，入队后仅等待统一归档，不重下载；提交后确认失败沿原队列重放 |
| 状态丢失 | Redis存活读取已入队断点；Redis丢失重新读全响应并与SQL比较，不承诺丢失消息恢复 |
| 完成与用途 | 采集完成证明来源已返回事件可查询；数据准备独立核验缺名、相邻名称链及SQL集合摘要，普通查询显示可用（有限制），缺名、断链和方向疑点不阻断查阅；历史回放独立检查 |
| 限制 | 保存来源“更名日期”，没有公告日期；首个名称、旧代码关联及链断裂不推断补齐。公司早期旧新名称方向尚有疑点，不能宣称可回放公司全称。ST名称变化仍不是ST状态认定 |

公司栏目同一证券同日不同名称组合独立保留；完全相同的规范事件以source_occurrences保存来源出现次数，来源总数按其合计核对，不把重复吞掉。股票栏目证券与日期必须唯一，重复A替代B直接失败。空原名、新名保持NULL并显示质量问题；缺少代码、日期、未知市场或超长字段为协议错误，整轮不发布。当前证券名称不重复保存；接口行业标签以独立列随事件保存，不能将其当作更名时的历史行业。

## 存储设计卡与字段字典（实现前设计）

业务实体为一种证券名称变更，两个独立数据集共享security_name_change，name_kind区分company/security，不存整行JSON。每行一个来源名称事件，record_key=SHA256([unified_code,event_date,old_name,new_name])；允许同日并列公司事件，固定来源tdx由贡献登记，历史证券不关联当前stock外键。完整归档单位是名称类型与市场的全部可得事件。

| SQL字段 | 来源、类型与语义 |
| --- | --- |
| name_kind | company/security，VARCHAR(8) ascii；栏目参数0/1 |
| record_key | CHAR(64) ascii；规范事件身份哈希，原名新名NULL参与身份 |
| unified_code | code+sc(0=SZ,1=SH,2=BJ)，VARCHAR(9) ascii；六位代码前导零保留 |
| event_date | rq，DATE，来源更名日期，不推断公告可用日 |
| old_name/new_name | prename/lastname，VARCHAR(200) utf8mb4_bin，NULL为来源未给；非空字符串原样保留，不反转或填补 |
| csrc_industry/tdx_industry | zjhhy/tdxhy，VARCHAR(200) NULL；来源“无”转NULL，保留其余原值，无历史行业日期 |
| source_occurrences | INT UNSIGNED，完整响应中同规范事件出现次数，1～30000 |

无扩展JSON。主键(name_kind,record_key)；ix_name_security(name_kind,unified_code,event_date,record_key)用于单证券历史；ix_name_date(name_kind,event_date,unified_code,record_key)用于日期全市场及稳定键游标浏览。列表只取6个业务列，最多200；单证券详情/质量审计最多30000行（有上限，不扫描其他业务正文）。旧代码属于来源身份，暂不合并跨换码证券。

正式查询：`WHERE name_kind=:kind AND unified_code=:code AND event_date BETWEEN :start AND :end ORDER BY event_date,record_key LIMIT 200`；范围浏览以(event_date,unified_code,record_key)游标，索引方向一致；覆盖查询按kind最多30000行还原规范集合，与collection_state三市场摘要/计数/契约版本比较。写入锁定本类型市场旧事件，批量插入不同内容，来源全范围修订移除已被替代记录；不同类型与市场不受影响。业务变化和该项目collection_state同事务，内容相同零业务DML，可信摘要命中免SQL，旧响应拒绝并由统一归档清队。

容量预算：当前公司3576条（566089源字节）、股票8368条（940418源字节）；一年预计两类共15000事件、五年25000，硬上限每栏目少于30000。按每事件1KiB含索引保守预算，行业字段纳入后五年预算64MiB，上限128MiB（两类），新表初建无复制旧业务，隔离容量实验至少25000事件。响应沿通用下载预算；按三市场行业组合字典及紧凑事件数组入队，出现次数1省略为协议默认值，其余显式保留，单次发布全部三消息须满足现行max_page_bytes，超限明确失败，不提高公共上限。查询P95<=50ms、25000条导入<=10秒、表含索引<=128MiB，证据必须实测并绑定代码及DDL。

## 故障处理与显式维护

正常关闭Empire、等待待归档Stream清零，使用scripts/create_name_change_schema.py预检和--apply建唯一新表；维护持单实例及MySQL维护锁，核对现有业务表数量/摘要前后不变，检查目标DDL。启动只检查结构。新数据集无历史布局需要迁移，不转换其他表，不删除现有数据。建表DDL隐式提交，失败保留已建表供核验和安全续跑。

字段缺失和链不衔接按来源事实显示，不能不断重读把检查变绿。网络失败使用公共有界重试；错误样本、运行记录遵守项目300/100条上限。实采范围和开发验收另存日期证据，不把本页支持范围当成已采完。

## 2026-10-06 行业补齐与验收用途

新增两列通过scripts/migrate_name_industries.py显式维护，原事件字段和身份不变。schema2/contract2和v2摘要拒绝旧格式；全响应重采补齐字段，旧完成或摘要不能替代新版完整性证明。普通数据分析中，来源缺名、断链和早期方向疑点作为限制，数据可查阅；历史选股回测仍核验完整链及方向。设计、迁移和反例见[行业与用途升级](name-change-industry-upgrade.md)。

显式行业升级维护会在待归档为0时通过公共断点CAS重置旧契约断点，包括SQL已提交但旧断点仍等待归档的情况；新版断点、无关任务及执行计划保持原值。队列非空拒绝重置，随后新版采集重新取得完整响应，不沿旧完成状态跳过行业补齐。

完整来源证明存在时，指定证券没有更名事件是普通查询的合法空结果，不作为漏采；这不能证明证券的首个名称。历史名称回放仍按独立用途检查，不将无事件等同于初始名称已知。

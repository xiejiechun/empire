# 增发送配单次读取与文档澄清

## 变更原因与现行规则

2026-09-30 用户要求取消不必要的重复读取。原开发指南“集合校验”“独立于去重的复核证据”没有要求每轮双读，开发时将来源核实过度泛化为日常双读，并在增发送配功能契约中写成“两次详情”和“不同容量两次完整响应”。本次纠正实现及规范，非以降低完整性要求换取请求减少。

- [开发指南](collector-development-guide.md#请求次数与完整性证据2026-09-30-澄清)及 AGENTS 明确每个必要页面/完整响应正常只读一次，区分开发验证、网络重试和业务异常复核。
- [功能契约](tdx-capital-actions.md)改为分红逐股一次，增发/配股各栏目一次；正常不再追加第二容量请求。
- [数据准备](data-preparation.md)澄清停复牌示例只在完全重复等来源异常/容量边界触发额外请求，不是通用双读门槛。停复牌实现未改变。
- 早期分红修复报告保留真实历史证据，注明其双读策略已被替代，避免历史记录充当现行规则。

字段、唯一业务键、来源总数及别名口径、容量截断、单证券上限、失败不推进断点、独立入队归档和旧响应保护全部保留。正常空结果一次确认。网络错误由共享下载器按保存策略有界重试；业务校验失败留下有界样本和断点，排查后重试，不自动重复读取至偶然通过。

本次无新增来源、字段、身份或范围，schema 与 SQL/Redis 业务集合摘要契约未变，既有有效证明仍适用；不迁移业务表、不失效已核验范围、不重置续采断点。全范围仍按正式查询与来源集合证明检查，不能用下载成功代替归档和数据准备完成。

## 验证与实际范围

相关专项及真实 Redis/MySQL 隔离集成共 56 项通过，验证正常/空结果请求次数、原始条数异常、重复 A 替换 B、同数不同内容的恢复冲突、网络错误复用重试预算、延迟归档继续入队、断点及提交后重放。没有稳定偏移分页，因此跨页请求次数不适用，仍保留完整响应截断检查。

审查日期：2026-09-26。对象：`D:\project\empire` 当前工作区源码、测试、配置模板、SQL、构建入口与桌面页面。

本报告是审查交付，不是已完成整改的声明。本轮未修改业务实现、数据库结构、生产配置或业务数据，没有启动真实采集、清理错误记录或重启共享服务；只新增报告及无生产连接的界面审计产物。

后续整改：用户随后授权落实 P1-01～P1-04，独立实现与验收见 [首批四项基础整改](priority-one-review.md)。以下保留审计时的证据和结论，不因后续修复改写历史审查结果。

## 一、结论与推荐顺序

当前项目适合继续采用**插件化桌面单体**，不需要以微服务、额外消息中间件或第二套存储路径作为优化起点。已有事务归档、可信摘要免 SQL、单任务互斥、代理出口共享许可、页面插件化和测试基础，方向基本正确。

主要短板不是功能数量，而是四类边界：

1. 缓存信任、脱敏和界面选中身份还有可复现的正确性问题。
2. 页数/记录数有上限，但下载字节、归档每轮工作量、后台错误和 SQL 排队尚未全部有界。
3. 部分核心能力仍含股票专属分支或旧适配入口，新增项目会扩大中央模块修改面。
4. 小屏主要依赖滚动兜底；读屏名称、键盘焦点和信息语义需要统一。

建议顺序：**先正确性与安全 → 再故障隔离与资源预算 → 再交互和布局 → 最后工程化与产品化。** 不建议先全面换肤或大规模重写。

本轮合并重复问题后形成 **30 项改进：4项P1、22项P2、4项P3**。各项均包含证据、优化价值、落地建议与验收条件。

### 优先级与证据说明

- **P1**：可能影响数据正确性、凭据安全或进程稳定；应先修，再扩大代理/数据规模。
- **P2**：当前可维护性、操作体验或规模扩展的重要瓶颈，纳入下一阶段。
- **P3**：持续治理或产品化项目，可在基础问题关闭后实施。
- **已复现**：使用模拟对象、MockTransport 或无服务离屏界面执行过最小案例。
- **源码确认**：能够从当前实现直接确认，但未在生产环境触发故障。
- **条件风险/待实测**：触发依赖数据量、环境或异常输入；不等于已经发生事故。

没有证据支持把当前项目判为存在已发生的数据丢失、真实凭据泄漏或生产内存泄漏，也没有证据支持“测试全部通过所以没有问题”。

## 三、按优先级排序的改进清单

### P1-01　缓存版本的可信校验不完整

**问题/证据（已复现）**：[fingerprints.py:68](../src/empire/plugins/pipeline/fingerprints.py#L68) 仅检查 version 是非空字符串数组，未校验维数、日期及版本格式。[archive.py:279](../src/empire/plugins/pipeline/archive.py#L279) 直接比较数组。模拟 `version=["not-a-timestamp"]` 被接受，合法新闻被判为旧版本，不访问 SQL，返回 complete；后续成功路径会删除消息。

**优化价值**：避免缓存损坏把可回源恢复的情形变成有效消息被静默丢弃的风险。这是本轮第一优先级。

**落地建议**：数据契约声明版本结构和比较器，缓存层统一调用校验。非法维数、空值、非规范时间/版本一律视为 miss；无法证明旧版本时回 SQL。不要新增第二份持久摘要或取消正常可信命中的快速路径。对于异常未来时间，按来源契约定义容忍范围，不能随意将正常来源时间判坏。

**验收**：三类插件均测非法版本、缺失/损坏索引、过期和格式不一致；SQL 失败必须留队；正常命中仍零 SQL；假旧版本不能触发成功清理。

### P1-02　序列化后字符串脱敏存在漏脱敏与破坏 JSON 的边界

**问题/证据（已复现）**：[runtime.py:69](../src/empire/core/runtime.py#L69) 对整个 JSON 字符串做替换后再解析；[config.py:58](../src/empire/core/config.py#L58) 只识别原始及 URL 编码密码。模拟带引号密码在 JSON 转义后可漏匹配；单个引号密码可破坏 JSON 并触发异常。[system.py:194](../src/empire/plugins/ui/system.py#L194) 也存在先序列化后脱敏。后台异常退出路径未统一执行插件 shutdown。

**优化价值**：统一凭据保护，避免安全处理本身终止后台。这里只使用模拟凭据，未认定真实密码已经泄漏。

**落地建议**：建立一个公共脱敏器，在结构化对象的字符串值层处理，再序列化；日志、UI 状态、Redis 错误样本共用规则，不能修改 JSON 语法或身份键。异常退出进入安全清理流程。网络 INFO 请求日志按需降低级别，查询参数及代理协议凭据走相同规则，不增加常态写盘量。

**验收**：引号、反斜杠、换行、中文、URL 转义及嵌套结构的模拟凭据均不出现于输出；快照合法；注入快照异常仍能正常释放插件、连接及线程，不强制丢弃在途事务。

### P1-03　并发窗口限制页数，但没有限制下载/解压字节

**问题/证据（源码确认、异常输入风险）**：[routing.py:103](../src/empire/plugins/infra/routing.py#L103) 全量读取响应；[stock_pages.py:56](../src/empire/plugins/collectors/stock_pages.py#L56) 预取持有后页响应；[ingest.py:122](../src/empire/plugins/pipeline/ingest.py#L122) 的页字节限制发生在下载、解压、解析之后。64 个窗口不代表内存有界。

**优化价值**：在扩展几十代理前阻止超大错误页、无 Content-Length 响应、压缩膨胀耗尽内存。

**落地建议**：统一 HTTP 路径采用流式读取，限制解压后累计字节；每来源声明合理响应上限，预取另有总字节预算。超限中止、关闭响应、保留有界诊断；不能把整个超大正文留在异常上下文。

**验收**：覆盖虚假/缺失长度、chunked、压缩膨胀及64窗口；超限不推进断点，连接可回收。记录 RSS 峰值，证明其受设定预算约束，而非仅断言缓存页数≤64。

### P1-04　股票列表刷新后可能悄然改变已选股票

**问题/证据（离屏已复现）**：[stocks.py:246](../src/empire/plugins/ui/stocks.py#L246) 按行重建单元格，没有按统一代码恢复选择。列表 `[000001,000002]` 选中 `000002`，刷新为 `[000002,000003]` 后，选中仍留在第二行，实际变成 `000003`。

**优化价值**：避免复制到研究表格的是另一只股票；这比纯视觉调整更重要。

**落地建议**：统一使用公共表格更新策略，以 `(source, unified_code)` 保存多选、当前行及滚动锚点；消失对象取消选择，不继承其行号。复用单元格，避免每次创建全部 item。

**验收**：在插入、删除、排序、筛选、跨页和自动刷新下验证选中身份与复制内容；目标消失时不默认选择另一只股票。

### P2-05　代理客户端退役时遇取消，可能失去关闭所有权

**问题/证据（已复现）**：[proxy_pool.py:174](../src/empire/plugins/infra/proxy_pool.py#L174) 在等待 aclose 成功前把对象移出 retired。模拟慢关闭被取消，随后 pool.close 不能再找到该客户端；结果 `entries=0, retired=0, closed=false`。

**优化价值**：防止设备上下线、凭据轮换和取消叠加时出现连接泄漏。未证明当前生产进程已经泄漏。

**落地建议**：关闭完成后再移除，或交给持有引用、可等待和可重试的统一清理任务；取消不丢所有权。

**验收**：aclose 阻塞、异常、取消和重复关闭测试；每个创建过的客户端最终关闭或仍处于可追踪待清理状态。

### P2-06　异常 Retry-After 破坏 429 冷却

**问题/证据（已复现）**：[http.py:94](../src/empire/plugins/infra/http.py#L94) 直接 float 解析。`inf`、`1e309` 导致后续转毫秒 OverflowError，`nan` 得到0秒。

**优化价值**：保证源站或代理返回异常头时也能保守执行全出口冷却。

**落地建议**：拒绝非有限数值和不合法格式，使用既定安全回退。合法但很长的冷却不能偷偷截短后提前访问，应明确展示暂停原因并允许取消等待。

**验收**：NaN、无穷、溢出、负值、空值、HTTP 日期；所有429均建立安全冷却，不用代理切换规避。

### P2-07　跨源重定向的凭据清理不完整

**问题/证据（MockTransport 已复现）**：[http.py:205](../src/empire/plugins/infra/http.py#L205) 仅移除 headers 中的 Authorization/Cookie，保留 auth/cookies 参数，并允许 HTTPS→HTTP。模拟跳转后两类凭据仍发送。现有三个公开采集器不使用这些认证参数，属于通用服务扩展安全缺口，不是生产泄漏结论。

**优化价值**：为后续受认证来源建立可靠网络边界。

**落地建议**：按 scheme/host/port 判定 origin；默认禁止 HTTPS 降级；跨源清理所有认证入口，或收窄 HTTP 能力公开参数。跳转仍重新核实域名、出口许可。

**验收**：headers/auth/cookies 三类入口、同源/跨源/降级跳转及恶意 Location；跨源凭据不外带。

### P2-08　后台任务异常与插件健康脱节，错误集合无界

**问题/证据（源码确认）**：[plugin.py:34](../src/empire/contracts/plugin.py#L34) 使用无限增长 list；任务退出只附加错误。[manager.py:180](../src/empire/core/manager.py#L180) 虽展示错误，生命周期仍可能 RUNNING，不能表示关键循环仍存活。

**优化价值**：减少“界面可见但后台关键任务已停”的不明确状态，防止长期错误积累。

**落地建议**：有界错误队列；区分关键常驻和正常一次性任务；关键任务意外退出置 degraded/failed。若需要重启，设有限退避与唯一所有权，不盲目重试可能已提交的业务写入。

**验收**：关键任务退出、正常短任务结束、大量失败、停用重启；状态准确、错误有界且无重复循环。

### P2-09　仍有重复 HTTP 路径及旧控制适配入口

**问题/证据（源码/调用点确认）**：[http.py:141](../src/empire/plugins/infra/http.py#L141) 的无 pool 分支单独实现许可及 Semaphore；生产启动使用 routing，部分单元测试却主要覆盖旧分支。[control.py:325](../src/empire/plugins/collection/control.py#L325) 仍兼容 scalar/dict 配置，`configure_interval` 及旧全量 snapshot 主要由测试调用。

**优化价值**：落实“一项能力一条正式路径”，避免测试与实际执行算法不一致。

**落地建议**：直连、代理、回退统一走 routing；测试仅替换网络/Redis，不替换限流算法。核实消费者后删除旧 scalar、interval 和全量 snapshot；迁移测试与文档。auto/fixed 是正式策略，不能误删。

**验收**：全仓无旧调用；直连、代理、回退、跳转、取消、429 都覆盖同一生产函数；分页 UI 不获取全量历史。

### P2-10　归档扫描没有每轮总量/时间预算

**问题/证据（源码确认、规模待测）**：[archive.py:92](../src/empire/plugins/pipeline/archive.py#L92) 每轮从头扫描到尾并积累全部 groups；batch_size 只是 XRANGE 单页大小。[archive.py:146](../src/empire/plugins/pipeline/archive.py#L146) 又读取并规范化业务页。即时唤醒下，未完成股票页可能被反复扫描。

**优化价值**：限制事件循环占用和内存峰值，避免大批任务挤压新闻归档。

**落地建议**：在同一归档器内设置消息、字节、时间三重预算；有界批次索引及增量扫描，恢复时重建；按项目轮转。保留整份股票校验与单事务，不因分批调度发布半份列表。

**验收**：隔离环境1万/10万消息混合积压，统计重复扫描倍数、RSS、事件循环延迟、最老消息等待；取消/恢复不丢页。

### P2-11　未知 schema 的全局暂停应逐步收窄到故障项目

**2026-09-27 已实施**：通过 Envelope 校验且数据集与任务 ID 精确命中同一贡献登记时隔离对应项目；未知数据集、未登记任务和不可读未来版本保留全局阻断。消息原位保留，有界复查恢复后走原归档流程；新业务入队与已预留发布均检查项目隔离。详见 [契约隔离验收](schema-isolation-review.md)。下文保留原始审计证据。

**问题/证据（内存复现；有意设置的保障）**：[archive.py:109](../src/empire/plugins/pipeline/archive.py#L109) 未知 schema 会中断整个扫描并置全局 blocked；[ingest.py:82](../src/empire/plugins/pipeline/ingest.py#L82) 暂停全部采集。它保护未知业务不被误处理，但扩大了单项目升级异常的影响面。

**优化价值**：一个插件故障不拖停其他可识别业务。

**落地建议**：在保持未知消息原位、禁止删除的前提下，按已知项目/schema 隔离。无法可靠识别归属的消息仍采取保守阻断并告警；全局内存不足继续全局背压。这属于收窄现有安全策略，实施前应单独审阅边界，不直接绕过保护。

**验收**：未知消息在合法消息前/中/后均保留；可识别独立项目继续归档；契约恢复后重放；归属不明时不误删或误判成功。

### P2-12　SQL 单线程共享与新闻 OFFSET/全文查询形成扩展瓶颈

**问题/证据（源码确认、EXPLAIN 已核查）**：[mysql_store.py:67](../src/empire/plugins/infra/mysql_store.py#L67) 读、归档及配置写共用单工作线程。[news.py:30](../src/empire/plugins/data/news.py#L30) 每次精确COUNT、正文 `%词%` 和 OFFSET，空搜索也保留LIKE；服务 offset≤100000，但界面只按总数开放下一页，足够多历史数据时会出现可点却拒绝的页面。

### 建议验收指标（目标，非本轮已经达到的结果）

- 正确性：可信缓存零SQL；不可信证据不导致误清理；SQL/Redis任一步失败均可安全重放。
- 资源：明确响应/预取/归档工作单元预算；重复取消/上下线后连接、任务、句柄数量无持续单调增长。
- 响应：先固定硬件与数据量记录基线，再设UI主线程阻塞、查询p95、归档等待p95预算；不能用一个任意毫秒数覆盖全部机器。
- 故障隔离：一个插件停止或单项目schema不兼容不应无意停止独立业务；不确定消息继续保守保留。
- 操作：不靠鼠标完成核心路径；刷新不改变业务对象选择、不覆盖草稿；小屏保存/暂停清晰可达。
- 工程：报告对应源码/制品版本，所有正式入口有测试，旧适配路径同步删除，维护不自动改生产结构。

### 明确不做的“优化”

- 不为当前规模引入微服务或另一套消息队列。
- 不把Redis命中改成每次查SQL，也不为每次采集增加SQL流水。
- 不降低股票完整性校验、不并行提交越过失败前页。
- 不靠删除有效待归档数据、绕过429、强杀服务或放宽单实例来解决性能问题。
- 不将RouterProxy的在线维护搬进Empire，不把协议支持误当兼容层删除。
- 不默认改变日志、持久化或备份的用户授权边界。

# 增发暂无详情的采集规则

## 日常操作

在“采集管理 → 采集任务”选择增发，正常继续采集；“数据浏览 → 增发”选择方案查看详情状态。列表有方案而详情暂无可用内容时保留列表字段，显示“来源暂无可用详情”，不反复报失败。接口状态单独保留：明确空详情为0，通达信 -1005 为“数据库执行失败”；这不表示没有增发方案或源站数据库不存在该数据。

若以前有有效明细，界面保留“上次有效明细”并标为历史参考，不当成来源本次新内容。未请求、网络失败、字段损坏、方案关联不符仍是未完成/异常，不能套用暂无状态。

## 生命周期和范围

| 项目 | 现行约定 |
| --- | --- |
| 初始化 | 一次完整列表，逐方案读取详情，公开/定向及历史代码关联保留；有效详情或明确暂无状态都须校验、入队及统一归档。 |
| 正常后续 | 已有有效未变详情继续复用；新增、变化、缺失及暂无详情方案在新正常轮次核实一次，别名同编号本轮复用。近期90天规则不变。 |
| 强制与恢复 | 新的显式全量轮次重新核实；同一强制轮次中已核实的未变内容可凭当前SQL内容和可信指纹复用，包括暂无状态；缺摘要保守重查。 |
| 来源变化 | 自动换来源批次重建有序范围证明，已核实未变内容可复用；不能混用旧位置/计数。 |
| 完成 | 所有来源关联都已有有效详情或明确暂无状态，归档确认后显示完成；真正异常不推进断点、不发布最终证明。 |
| 可用性 | 暂无明细属于来源用途限制，依赖这些明细的分析不能假定字段为零或可用。列表字段仍按来源保存。 |
| 历史范围 | 旧SQL缺详情记录不直接改成暂无；仅当排除这些未知历史行后的完整业务集合、范围、数量和摘要均匹配已确认来源证明，才明确列为当前来源范围之外。否则仍失败。 |
| 状态丢失 | Redis丢失后按SQL已有数据恢复普通增量；暂无方案重新核实，未归档消息/精确内存位置不保证恢复。 |

## 存储和维护

现行 additional_issues.unit@3 使用同一 additional_issue.payload.detail。有效明细仍为原规范字段；暂无时为 `availability=unavailable / source_error_code=0或-1005`，可选 `last_available` 保留上次有效明细。未采集为缺失，三者分别展示。标记/明细参与规范内容摘要；相同状态/内容不执行业务DML，可信摘要命中完全免归档SQL，成功仍清理待归档消息，旧观测不能覆盖新内容。

关闭Empire、确认待归档队列为空后执行 `python scripts/migrate_issue_availability.py`。无DDL、不修改现有业务内容；升级状态版本、重建受影响的完成证明和断点，保留SQL观察水位及已验证规范内容不变的证券指纹。旧维护入口 migrate_issue_details.py 退役。Redis阶段失败保留pending，重跑维护完成；启动只校验，不自动迁移。

旧的六小时失败诊断冷却路径退役，暂无状态不进入错误列表，也不需要另一套失败缓存。真正异常仍沿用共享有界重试和错误限额。旧 -1005 记录须先登记确切ID，待对应暂无状态实际归档并经正式查询验证后精确清理；并发新增及尚未确认的问题保留。

## 验证与限制

专项和隔离集成覆盖明确空结果/-1005、损坏结构、关联错配、未采字段、旧明细保留、冷热摘要无DML、源端恢复、迟到重放、队列成功清理以及历史范围摘要验证。列表无偏移分页，详情为单方案，跨页重排不适用；本次没有文件业务或DDL。动态实采进度及发布证据另记，不把代码支持范围当作已采完范围。

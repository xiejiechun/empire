## 1. 已核实的问题与优化目标

现行[采集器](../src/empire/features/yuanhang/collector.py)每轮从FIRST请求每证券完整日线，拆年全部入队；金融任务每证券一次211联合响应取得完整权息及三种股本。统一摘要及SQL比较减少重复写库，但没有减少来源下载及重复入队。这次完成的[全池初始化](evidence/ths-yuanhang-final-acceptance-2026-10-25.json)仍有效，不能把它当作日常增量效率已经通过的证据。

固定5,578证券的两任务约需11,156个基础历史请求，另有按节点登录、沪市备用市场尝试、上市状态辅助请求和有界重试。初始13,197次代理请求是该次实测，不能作为每轮固定次数。原生连接内登录帧、网络连接数、逻辑行情请求与HTTP请求必须分别统计。

目标按四项分别验收：来源请求次数、传输/解压字节、Redis入队条数/字节、SQL实际业务写入。并行提速不等于减少来源成本，缓存命中也不等于没有下载。维持同源日线、权息、股本、节点身份与共享网络路径。

## 2. 推荐日常策略

| 内容 | 推荐策略 | 需要保留的边界 |
| --- | --- | --- |
| 日线正常维护 | 上次可信连续覆盖之后至本轮已结束交易日，向前重叠5个交易日；停机超过5日时补足整个遗漏区间，不能只取最后5日 | 按正式交易日历确定截止，不用自然日或SQL最大日期替代覆盖证明；5日为拟定默认值，可配置且不宣称能发现全部旧修订 |
| 无新增交易日 | 已核实本轮截止日、近期核验已完成且无缺口/审计到期时，日线业务请求为0 | 当日失败、未确认、来源修订核验到期仍须执行；不能跳过金融任务独立到期的检查 |
| 新增证券 | 只对缺少可信初始覆盖的新证券补齐全历史 | 退出当前池保留历史；代码/市场变化单独核实；新增股票不使其他股票重新初始化 |
| 历史缺口 | 按证券及缺口范围合并下载；仅证据不可信的受影响证券/年份扩大重核 | 停牌无行情不等于漏采；不能按交易日历强造每日K线 |
| 权息及三种股本 | 第一阶段仍每日一次每证券211联合全序列，默认北京时间18:00；已完成同一计划轮次不重复执行 | 事件较小但影响当天复权，不能默认为每周才更新；休市日是否到期按金融任务自己的日历日计划判断 |
| 老日线修订 | 按稳定证券集合轮转，20个交易日完成一轮全池历史核验；每证券约每月完整核验一次 | 当天选中完整核验的证券，用该完整响应同时满足近期增量，不再另发短区间请求；20日是建议目标，失败/离线顺延并显示逾期 |
| 已知异常/用户指定核验 | 精确证券/区间进入补缺或核验计划，复用已有请求去重 | 异常不能作为无限重试理由，不扩大到全池；已知源质量仍保留 |

5交易日回看、20交易日轮转是本方案建议默认值，不是现行功能或源端修订保证。旧修订可能在下一次成功轮转才被发现；程序须显示“增量覆盖截止”和“完整历史最后核验”两个不同事实。要求即时确认任意旧修订时，显式执行完整核验。

沪市请求优先使用已有可信证明中的native_market。现行证明保存了实际市场，但采集器调用fetch_history未传该值，仍从默认市场开始尝试；接通这个信息可避免已知风险警示板股票反复先请求错误市场。市场信息失效或发生迁移时，仅按已验证的严格空响应规则尝试另一市场，最多一次，并验证新响应身份。格式错误、认证拒绝及网络失败不能作为切市场理由。具体减少次数以固定股票池实测为准。

节点账号继续按code固定。认证开销先分别记录公钥、登录、passport和连接内登录；现行按节点在任务轮内复用会话的行为保留。跨两个任务共享会话或复用已认证连接放在协议生命周期验证之后，不能假设有效期、跨节点借用会话或因认证拒绝重新注册。连接复用即使成功，也只减少连接/认证成本，不能算减少了业务请求数。

## 3. 降低请求次数：先验证协议，再选择实现

第一阶段缩短日线范围主要减少字节、解码、入队和归档负担；逐股日线和每日金融仍约2N个逻辑请求，不承诺次数大降。下一阶段重点验证原生批量能力，且不得以增加代理替代请求合并。

| 能力 | 现有证据 | 实施前必须证明 |
| --- | --- | --- |
| 210指定日期区间 | 构造器有start/end，已有有限单证券区间样本 | 沪深北、跨年、停牌、上市首日、空区间、服务器截断及边界包含规则；区间结果与同一次开发核验的完整历史对应集合/内容一致 |
| 多证券指定日/区间日线 | 尚未证明 | 一次响应是否精确包含全部请求证券、真实交易日期、不复权OHLC、成交量/额及单位；数量上限、分包/分页、截断、漏股和错误证券处理 |
| 最新批量行情 | 不能视为已证明的历史日线 | 最新报价携带的日期可能是停牌前旧日，成交量可能盘中或累计；只有收盘后数据与210逐字段/逐股相符且覆盖可证明才可作为当日增量；历史缺口仍走区间历史 |
| 211批量证券或可靠变更标识 | 当前仅证明单证券0/0完整联合响应 | 批量是否保持每证券三口径与事件集合完整；标识是否覆盖历史修订、删除及未来生效点变化；不能用日线变动或除权日猜全部股本变化 |
| 已认证连接内连续多请求 | 当前每次历史调用含原生登录交换 | 响应对应关系、连接失效/取消、服务端限制与资源回收；不能只凭成功发两个包就宣称支持长期复用 |

采用已证明能力中的唯一正式策略：能可靠批量则优先批量；不能批量则按股短区间。若批量协议未通过，交付明确“请求次数尚未降低”，保留按股可用方案，不宣称必须回退全历史。不能验证区间完整性时，该项优化不得发布为完整增量。

权息/股本若没有可靠批量或全覆盖变更标识，维持每日小响应全序列，并明确这是来源限制下的例外。若以后选择降低金融核验频率，必须同步声明时效及受影响的复权/估值用途，不能将旧事件输入标为当天已核实。本轮不改变这个默认时效。

## 4. 请求预算与可见指标

设N为本轮证券数，B为实测可接受的批量证券数，D为批量接口需要分别请求的日期数，E为未被正常请求覆盖的缺口补采请求，A为登录等辅助请求，R为重试及已声明的市场分支请求。轮转核验与近期请求按证券消重后计数。

- 现行：日线N＋金融N＋A＋R，正常每股一个完整响应，不是逐年网络下载。
- 第一阶段：有新交易日日线约N＋E，金融到期约N；轮转证券完整请求替代其短请求。无新日线且无其他到期事项，日线请求0。字节与入队必须实测下降，不能把N不变写成请求数下降。
- 若验证多证券单日接口：新增一天日线约ceil(N/B)，近期回看及历史轮转另按已经证明的批量/区间能力计入；若逐日取5个日期，则是5×ceil(N/B)，不能省略回看成本。
- 仅举预算算例：N=5,578、B=100时单日约56次；金融若仍逐股则约5,578次。B=100只是算例，不是协议能力或发布承诺，实际还需加近期复查、轮转、辅助和重试。

每轮计划和记录展示：初始化/增量/补缺/历史核验的证券及日期范围，各类预计/实际逻辑请求，原生认证交换、连接数、代理/直连次数，线上/解压字节，源记录/入队记录/新增/修订/相同确认数量。统计复用共享下载与有界运行记录，不另建逐请求SQL日志。超计划时保留具体原因；禁止静默从一次短区间失败升级为全池历史。

初版默认预算按实际协议及当前N计算，来源请求正文和解压后上限继续独立生效；网络重试使用原保存预算，429继续站点全出口冷却。禁止用降低完整性检查或漏计登录/失败请求来满足预算。

## 5. 归档与覆盖证明必须同步改造

当前日线归档语义是完整证券年。直接把5天数据送入现行replace_year会有错误替换风险，不能只改请求start参数。先按[数据库设计规范](database-design-standard.md)扩展[存储设计卡](ths-yuanhang-storage-design.md)，冻结下列契约后实现：

1. 一条正式数据路径：保留原始日线、权息和股本事实表，扩展同一采集器的计划与现有归档贡献；不另建“增量行情”业务副本或第二归档器。
2. 区间消息显式携带证券、起止、截止日、来源身份、模式、规范版本和该区间键/内容证明。完整年度与区间消息不能混淆。局部响应只替换源已完整证明的区间；区间外数据保持。删除需完整区间权威集合证据，快照缺行不能解释为删除。
3. 年度覆盖仅在既存可信覆盖＋本次已证明相邻/重叠范围合并后推进；中间缺口保留。部分更新最多读取受影响证券年重算规范摘要，正常日常不扫描整库历史。跨年按受影响年更新，同事务提交事实与证明。
4. 快照只证明明确返回的证券日。停牌前旧日期、漏股或无效空响应不能填到当天；缺失证券按原生区间契约补查。交易日历说明交易所开市，不证明每只股票必须有日线。
5. 初始化可信证明可经显式兼容审计沿用，不因新增区间功能就重采全部已有历史。若旧证据不能满足新契约，明确受影响范围与重核成本，不能静默信任或清除全部证据。
6. 继续使用业务与断点原子入Redis、统一归档、相同业务无DML、可信摘要免SQL、成功清队及旧响应防覆盖。区间重叠的版本顺序须能拒绝旧区间/旧整年覆盖较新点，不能仅给整年统一刷新版本后误拒绝另一段有效更新；这是设计与回归必答项。
7. 每项目仍一条collection_state；恢复计划优先用已有结构化年度/序列证明及有界状态。实施前给出新增字段、索引、序列化容量、查询和显式迁移设计；本方案不创建新表或默认将完整覆盖明细塞进JSON。
8. Redis丢失时从SQL可信覆盖恢复，先补未确认窗口；摘要丢失本身不能强制全池历史重下。SQL缺乏最后一次纯缓存核验时间时允许保守重查该范围，不冒充知道丢失的内存上界。轮转进度丢失后的重查上限也须明确。

采集与归档继续解耦：每批入队即继续下载；整轮末尾等待所有该轮消息成功处理才显示完成。历史核验未到期不是当天增量缺失，核验已到期失败须单独显示；本轮承诺的必要数据失败仍不能显示完整成功。

## 6. 上线顺序与退出条件

| 阶段 | 工作 | 必须取得的结果 |
| --- | --- | --- |
| P0 协议与成本核实 | 共享代理验证区间、批量候选、连接连续请求；同池同日期记录基线 | 区分已支持/不支持/未知，给出数据与认证请求及字节预算，不改生产策略 |
| P1 区间归档与恢复设计 | 补设计卡、规范消息、覆盖与重叠版本语义、迁移和容量 | 局部不会删整年、旧响应不覆盖、Redis丢失可按范围恢复；原完整初始化仍可追踪 |
| P2 日常增量 | 新股全历史、已有证券增量＋5日回看、到期轮转消重、金融每日联合；接入已证明批量能力 | 普通轮次不重新下全部历史；同截止重复运行不重复做已完成工作；准确区分次数和流量收益 |
| P3 验收与发布 | 来源语义/隔离SQL、随机30股＋固定反例、同池预算比较、正式门禁和桌面 | 来源→Redis→统一归档→SQL集合及内容一致，本轮pending0；统计可复核、配置保存优先、实际发布与桌面分开记录 |

新增专项反例：初始化后的第二轮无变化、只增加一日、5日内修订、窗口外旧修订待轮转、单证券历史缺口、新股/退市池变化、长停牌、跨年、批量漏股/同数异集、批量截断、未知空帧、迟到整年与较新区间交错、Redis丢失以及断点恢复不重下已确认全池。历史修订核验落后时显示时效，不能用最新日期掩盖。

真实验收保留随机30证券及现有固定反例，至少验证一次初始化基础上的无变化维护和一次有新增日期/有效修订的维护；真实源暂未发生的场景使用隔离回放并明确不是真实变更观察。开发对照所需额外下载不进入日常固定双读。生产上线后核查已有历史和新增范围，不要求仅因优化再次重采所有1700万条。

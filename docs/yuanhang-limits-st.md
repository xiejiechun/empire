# 远航五池补充 ST

2026-11-04，用户授权在现有采集口径补充 ST，并要求避免另设 ST 请求。五池共用一条来源路径，过滤从 `HS,GEM2STAR` 改为 `HS,GEM2STAR,ST`；不新增任务、接口、表或 Redis 键。

## 业务及存储设计

完整单位仍为交易日、池类型，成员主键仍为交易日、池类型、unified_code，字段、类型、索引、查询上限及容量边界沿用[原设计](ths-yuanhang-limits-implementation.md)。ST 名称按来源保存，不按涨幅猜测，也不添加独立业务副本。11 月 3 日来源核实：新口径单响应返回 52 只，其中 4 只名称包含 ST。

池头新口径证明使用 contract_version=2。已有旧口径头及盘中快照保留原过滤与版本，浏览明确说明未补充 ST；它们不构成新口径完整覆盖。归档只接受新口径，新旧规范内容因 filter 不同而摘要不同。旧业务数据不删除、不直接改写为新版本，须经完整来源池重采和统一归档重建证明。

SQL 仅将池头过滤 CHECK 扩展为允许已保存的旧口径及当前含 ST 口径，无字段或索引变化。独立维护入口在正常停机、归档器停止、取得数据库维护锁后执行；完整有界扫描待归档队列，须不存在五池消息且消息结构和归属可读。其他项目消息原位保留，不要求为修改五池约束先归档全部无关项目。核对五池三表及统一状态内容摘要前后一致，失效五池来源摘要，保留盘中历史、业务和断点。启动不迁移。DDL 失败不刷新证明。

## 生命周期与成本

近期十交易日优先补齐，历史按原有每批最多 64 个完整日期单元分批补缺；恢复仍从对应口径的 SQL 证明规划。旧口径重新核验属于一次性补齐，不声称没有请求成本；已有更小实采样本不为凑比例扩采。

用户要求完整历史补齐时，正常关闭桌面后使用独立维护入口 `scripts/initialize_yuanhang_limits.py --apply --through <已结束交易日> --report <新报告路径>`。维护须显式选择 all 范围；若存在近期或历史分批断点，先沿原范围完成该轮，再规划完整历史。五池完成并通过全范围审计后补原因，最后核对待归档清零；不能将近期一轮或64个日期池完成当作全历史完成。使用同一来源、共享预取、频控、断点和统一归档，不修改日常保存计划，不重采已经具有当前含ST口径的历史单位。脚本修正只影响显式维护执行范围，不改变桌面日常调度、表结构或请求协议。

维护可显式设置`--request-retries 0～10`，默认2；仅改变本次维护的单请求共享重试预算，不保存到日常计划，也不新增外层重试。正常必要响应仍请求一次，有R次预算时每必要请求最多1+R次尝试，业务暂时失败、网络及已支持HTTP状态共用退避预算；耗尽保留断点并失败，不将失败响应归为无内容。报告记录实际预算及路由次数；HTTP 500仍按现有共享下载器策略报错，不借维护参数放宽解析。

正常每个必要页一次请求，无独立 ST 请求、集合双读或额外认证。请求数仍为 max(1,ceil(含 ST 总数/100))；48+4=52 仍为一次，跨越每页 100 条才增加分页。原因任务按五池证券日并集消重，新增加的 ST 原因详情按原有单证券日接口获取，其请求数随新增证券日增加。无变化维护和缓存恢复仍沿用已有范围、频控和重试边界。

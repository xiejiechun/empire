# 新增采集功能开发指南

本指南是新增或实质修改采集功能的开发与验收入口，不新增运行时路径。项目约束以 [AGENTS.md](../AGENTS.md) 为准；历史验收报告用于理解背景，不把其中“下一步”当作现行待办。日常操作见 [采集管理](collection-management.md)，整体职责见 [系统架构](architecture.md)。

## 完整性五项准入（2026-09-29 用户确认）

以下是所有后续新增或实质修改采集插件的必需验收条件，具体执行沿用后文契约、公共流程、测试和交付清单，不另建一套机制。

1. **生命周期先明确**：实现前写明初始化起止与完成条件、后续起点、补缺及修订回看范围、中断和状态丢失恢复依据；说明、代码与测试一致。
2. **完整性不能只数条数**：核对来源统计与过滤口径、业务键集合及分页边界；测试“重复 A、遗漏 B 但条数相等”。分页不稳定须采用可验证的获取方式，无法证明完整则失败。源端重复须有独立于去重操作的复核证据和专项测试，不能直接吞掉冲突。
3. **失败不推进断点**：必要完整单元校验通过后才将业务数据与已入队断点原子发布至 Redis；缺页、数量不符或冲突不得跳过。空单元必须有有效来源响应证明，后续成功不能掩盖前序缺口。独立归档及整轮完成确认规则不变。
4. **验证到正式查询**：专项测试贯穿来源响应、规范化、Redis、统一归档及正式查询，覆盖旧记录必需字段补齐、重复无业务写入、修订与旧响应、断点恢复、提交后重放及成功清队；公共测试不能替代来源语义测试。
5. **开发与实采分别验收**：发布报告分别给出开发测试证据和实际数据证据，写明已归档范围、缺口、异常、待归档残留及下一轮起点。范围内证据不足不能宣称数据完整；未实采或只验证部分历史时如实标记，不能用运行成功代替完整性。

适用项缺少证据时不得宣称验收完成，不适用项写明理由。来源差异由插件声明和专项测试，公共安全规则由共享框架执行，实际完整性由范围明确的验收证明。继续复用下载、代理、频控、入队、摘要和归档；不新增永久业务副本或逐日 SQL 状态表，不为验收长期保存成功响应。该规则不扩大实采授权，也不要求每次发布都重采全部历史。

### 请求次数与完整性证据（2026-09-30 澄清）

正常采集默认每个必要页面或完整响应请求一次，校验结构、必需字段、业务键集合、来源总数口径及适用的分页/截断边界。集合校验指核对业务身份及覆盖关系，不等于把同一数据下载两遍；两次返回相同也不能独立证明源站没有遗漏。

“独立于去重操作的复核证据”指来源协议/字段语义、总数口径、分页或快照契约、开发时核实的样本与专项测试等，不能把去重后的条数作为自己的完整性证据。开发核实或故障排查时的再次请求，不自动变为日常每轮的第二次请求。只有来源协议确实需要额外请求才能证明边界时，插件才单独说明理由、触发条件及请求上限；不得为所有正常响应默认双读。

网络及可重试 HTTP 异常使用共享下载器的有界重试与频控；业务校验失败保留断点和有界错误样本，按诊断证据复核，不能不断重读直到偶然通过，也不能将校验失败伪装成空结果。自动重试的支持范围由来源插件明确声明。专项测试必须验证正常请求次数，以及重复 A 替换 B、总数不符、截断等适用异常仍不能推进断点。

来源明确暂无可用内容时可声明独立可用性状态，保留已有业务身份、接口状态及上次有效信息，说明来源限制及复查规则；不能把未请求、网络失败、字段损坏或未知协议当暂无。通达信增发按用户确认的页面口径将明确空详情/-1005归为“暂无可用详情”，不是无增发方案，既有明细为历史参考；状态归档与来源恢复均须端到端测试，不因此填零或跳过必需列表字段。

### 开发实采的网络策略（2026-10-09 用户要求）

开发、排错或验收采集插件，需要真实请求来源、采集样本或检查插件是否正常时，使用“代理优先，代理不可用时可退回直连”（`use_proxy=true / proxy_fallback=true`），减少用户等待时间。该要求同时覆盖来源核实、临时验证脚本和正式插件实采，不能只为正式任务配置代理，而在开发检查中默认直连。

请求复用共享下载器、代理目录与连接池、网站频控、有界重试和资源额度；独立单元按来源契约复用共享有界预取。验证入口应显式设置并核实实际生效的网络策略，运行证据记录验证范围、策略及代理/直连/回退请求次数。不得用另写requests或httpx直连脚本代替正式网络路径，不打印代理凭据。

代理暂忙仍由公共调度等待，代理不可用或被临时隔离时才按公共规则回退本机；直连遵守本机频控，429冷却仍覆盖整个网站组，不因赶时间绕过。开发验证采用上述策略，不静默覆盖用户已保存的日常任务配置；明确要求测试直连或仅代理行为的专项场景按其测试目的执行并记录原因。

### 随机30股代理实采准入（2026-10-17 用户要求）

新增、实质修改及来源解析修复的采集插件，实采验收至少随机抽取30只不同股票。抽样来自当前适用的正式股票池，记录池数量及集合摘要、随机种子、抽样算法和最终股票名单；已知出错证券另行固定加入，不占随机30只名额。样本确定后保留，失败须修复并重验该集合，不能换掉失败证券凑够成功数量。

验收使用共享下载器及代理基础设施，采用`use_proxy=true / proxy_fallback=false`确保实际走代理。代理不可用时保留未完成状态；排错阶段允许的直连回退不计入代理验收，日常保存的任务配置不变。记录代理请求及直连/回退次数，不记录凭据。

全部样本须经正式采集、原子Redis入队、统一归档、MySQL正式查询，逐证券核对来源业务键集合、必需关联及规范内容；整轮确认所有消息成功清队后才通过。可以使用独立验证库及Redis命名空间，但必须走正式路径并报告隔离范围，不能宣称生产全市场已完成。只下载或解析成功、模拟样本通过、条数一致均不够。

验收报告绑定当前代码，记录日期范围、每只股票的入库/查询结果、完整性审计和本轮待归档为0。股票池不足30只时如实报告数量，不宣称通过30股门槛；新闻、交易日历等非股票粒度来源说明不适用原因与对应完整单位验收。此项是必须执行的验收约定；未接入的自动化检查不得宣称为已有通用门禁。

## 业务表设计准入

新增及实质改造数据集必须先完成 [业务数据库设计规范](database-design-standard.md) 中的存储设计卡，提交字段字典、查询与索引、容量预算、完整性证明及显式迁移方案。正式核心字段不能默认全部放入 JSON，性能和容量验证纳入首次交付。开盘啦七项的待实施案例见 [优化方案](kaipanla-storage-optimization-plan.md)，不能将其目标结构或待建门禁当成当前已实现能力。

## 1. 实现前明确业务契约

在功能说明中记录以下内容。能从接口和现有证据确定的实现细节直接落实；仅在缺失信息会改变业务范围或需要新增权限时询问，不把清单变成逐步审批。

- 来源、数据集名称、稳定的 job_key/project_id、分类 category 与 source_name。
- 对标页面有详情入口时，核实详情接口、列表关联身份及详情字段；用户要求该业务完整采集时，不能只读列表就宣称完整。来源明确返回的空字段与未请求、请求失败必须区分；详情采集须区分初始化、日常增量和强制回查；可用已归档业务与列表变化判断是否补采，不默认每轮全读。若列表不能反映详情独立修订，明确回查方式及普通增量的追溯限制，不把无限追溯作为日常采集门槛。
- 业务唯一键、内容规范化、来源修订版本和旧版本防覆盖规则；不要把采集时间一律当作来源修订版本。
- 选择增量归档或整份聚合，定义“完整”和空结果的含义、分页顺序、停止条件、断点及恢复方式。
- 新增、更新、相同内容和迟到旧响应如何处理。历史新闻不能照搬股票整份替换，缺失日期不能推断为休市。
- 所属网站频控组、响应类别和资源需求。只有来源确实支持独立分页时才能声明并行预取。
- 是否需要新表或文件业务。沿用现有表语义时不新增重复表；新表须有显式结构维护方案和前后完整性核查，启动不迁移。

### 生命周期契约（每个插件必填）

在插件自身功能说明中按下表填写具体答案，并对应实现入口和专项测试；不能只写“支持断点续采”。统一的是问题、公共路径及验收标准，不是所有来源的续采算法。整份股票列表、增量新闻、日历和事件历史应按来源能力分别设计；不适用项须写明理由。

| 项目 | 必须明确的答案 |
| --- | --- |
| 用途与支持范围 | 用于什么分析，证券与市场范围、最早支持日期、必需/可选字段、来源限制；事件生效日期与信号公布/可用日期分别解释。来源不支持不等于程序漏采。 |
| 初始化边界 | 从哪里开始，到哪里结束，采用什么时区；终点固定于本轮启动日、来源上界或其他规则。运行期间跨日、跨月、跨年时，本轮与下一轮各负责什么范围。 |
| 完整性单位 | 按日、月、分页集合或其他单位核验，如何检查缺失、重复、排序、总数及尾页；什么证据证明空结果有效。不能将查询失败或缺失日期当成合法空结果。 |
| 初始化完成 | 声明范围内所有必要单元已校验，业务已归档或确认无需写入，无未解决缺口；需要完整集合的业务还须确认集合完整。请求结束、已入 Redis、最大日期到达终点均不能单独证明完成。 |
| 后续起点与停止 | 根据哪个已确认业务边界或状态开始，是否重查边界、回看多长范围，何时停止；历史缺口如何发现和补齐，新增日期如何延长。不得仅依赖最大业务日期推断前面无缺口。 |
| 修订与追溯 | 回看范围内如何接收来源修订、防止迟到旧响应覆盖；是否能发现更早历史修订，不能发现的范围明确写出，不承诺来源不提供的完整历史版本。 |
| 中断恢复 | 下载中、入队前、入队后未确认、SQL 提交后确认失败分别从哪里恢复；哪些数据重下载、哪些消息重放，如何保证不跳过未确认单元。 |
| 状态丢失 | 仅重启 Empire 且 Redis 存活时使用什么断点；Redis/电脑重启时依据哪条 SQL 状态及业务完整性恢复，允许重查多少范围。可信摘要命中可能不推进 SQL 核验上界，因此不能承诺恢复最后一次内存核验位置。 |
| 操作与配置 | 普通/继续采集、重新初始化各自含义和副作用；配置修改对在途批次及下一轮何时生效。断点与新范围冲突如何处理，不得静默跳过或混用不同范围。自动启动取决于已保存的任务策略，不等于具有恢复能力就自动执行。 |
| 进度与证据 | 区分下载、已入队、已归档及连续完整覆盖；没有日期意义的业务用自身稳定边界。分别记录代码支持范围、实采范围、验证范围、未完成范围及错误。 |

开发顺序为：核实来源与用途 → 填写生命周期和存储契约 → 接入公共路径 → 专项及隔离集成测试 → 范围明确的实采核验 → 同步说明和执行发布门禁 → 报告实际进度与下一步。实采受当前授权和资源约束，不默认启动全历史采集；无法实采时明确未验证项，不用模拟结果替代。用户要求先审阅方案时，先停在方案交付边界。

三个必答问题是：**初始化完成到哪里？下一轮从哪里开始？中断后从哪里恢复？** 设计、代码、测试和使用说明必须一致。功能交付只验证了部分历史时，应按实写明已归档上界及范围内缺口，不把“支持某日至今”写成“某日至今已采完”。

### 开发时配好合理默认任务配置

以后新增采集组件必须按实际来源更新、数据粒度、完整性单位、资源消耗和生命周期，声明 `TaskContribution.default_schedule` 的推荐默认执行方式、间隔或北京时间每日时间，不把首次选择执行方式转交用户。默认配置应能直接使用，并说明推荐理由；数据粒度不等于任务运行频率。配置页保留执行方式、时间、启停、重试和网络编辑能力，用户保存的合法配置优先于插件默认值，程序重启、Redis丢失和默认值升级都不覆盖已保存选择。高容量插件默认停用不等于默认手动。助手需要设置现有项目时，通过正式配置或显式维护入口保存，不在启动时静默重置已有配置。

## 2. 按现有插件贡献接入

| 接入点 | 必须完成 | 不要做 |
| --- | --- | --- |
| 采集插件与 TaskContribution | 在内部白名单登记能力、任务身份、分类和来源；声明自身依赖 | 让控制器强依赖所有采集器，或扫描任意外部插件包 |
| DatasetContribution | 声明数据集、摘要命名空间、版本契约、归档模式及明确的 job_key → project_id 映射 | 依赖名称猜测归属，或在中央归档器添加来源特判 |
| 数据映射与存储 | 提供规范化、fingerprint_plan / fingerprint_subset、版本比较及 SQL 写入规则；聚合类型提供组装和完成判定 | 插件直接清待归档消息，或创建第二套摘要/进度系统 |
| 业务查询插件 | 校验自身业务表，只读已归档业务数据；按需提供有界分页查询 | 让纯 MySQL 浏览非必要地依赖 Redis |
| 可选数据页面 | 以 PageContribution 及 catalogued/category/source 登记到数据目录 | 每增加一个来源就增加固定顶层菜单，或把业务逻辑放进桌面外壳 |

新增功能可能需要修改白名单登记、声明及自身存储能力，并非只放入一个文件就自动发现。优先参考 [插件贡献边界](plugin-contributions-review.md)、[采集器契约](collector-contracts-review.md) 和 [管理界面插件](ui-plugins.md)。现有股票、新闻、日历只能作为各自业务类型的示例，不能整份复制生命周期循环。

## 3. 必须复用的公共流程

### 下载、代理和频控

所有当前及未来采集插件通过公共任务策略默认“代理优先，暂不可用时自动直连”（`use_proxy=true / proxy_fallback=true`）。界面与运行时默认必须一致；已明确保存的用户选择优先，禁止启动时重置策略。来源插件不得绕过公共任务入口另设直连默认；实际网络策略在下一轮生效，回退仍受本机频控约束。

所有请求通过共享 HTTP 下载器与现行 routing 路径；复用统一代理发现、按出口 IP 的网站许可、429 冷却、重试、脱敏、重定向保护和下载资源预算。不得另建 requests/httpx 客户端绕过这些约束，也不得通过更换代理绕过站点冷却。

并行预取必须有界，按原页序校验与发布；失败、取消和提前结束要回收全部请求及额度。容量不足先消费已持有的前页，不等待自己占用的额度。响应上限和共享缓冲取正式下载设置，不把规划设备数当作实际并发。

文件业务使用同一下载器的流式文件契约，另外声明文件签名、摘要、引用和保留规则；不把 PDF 原文放进 Redis。本指南不意味着已经实现文件业务归档或授权新增公告功能。详见 [下载资源](download-resources.md) 与 [代理采集](proxy-collection.md)。

### 采集、入队和完成

复用 `contracts/collector.py` 的公共能力边界以及 `collectors/support.py` 的容量等待、发布重试、归档确认和诊断辅助函数。来源分页和校验保持在自身模块，不增加万能采集基类或第二套轮询流程。

- 任务不重叠，固定间隔从任务结束后等待；配置仍走 MySQL app_setting 的正式路径。
- 规范数据通过 `ingest.publish_page` 与断点原子发布，不直接 XADD 或自行提前更新成功断点。
- 需要完整集合才能归档的采集器，在首条业务消息前完成整批容量准入；取消、失败释放预留，恢复时重新计算剩余量。
- 普通与预留发布都由统一入队器在全部准入等待结束、提交 Redis 命令前复核全局及项目隔离；提交后的成功结果不能因随后发生隔离而伪造失败。采集器不得绕过检查。
- 入队立即唤醒统一归档器，60 秒扫描仅为恢复兜底。采集完成仍须等待业务归档成功或确认无需写入，不把“已下载”当作“业务可查询”。
- 采集和归档是独立流程：每批原子入队后继续采集，恢复时按已入队断点下载未发布范围，不逐页/月/段等待归档。归档器自行决定处理时机，采集器不调用归档执行或清队。只有整轮入队结束才进入等待归档，公共确认同时核对完成标记与本轮无残留消息；最高页码不是整轮成功证明。背压、隔离及频控等待仍须保留，不能以解耦为由绕过。

### 归档、缓存与故障

业务数据先入 Redis，统一归档器负责事务、摘要和成功清队。数据集若在一个完整目录事务中删除其他业务键对应的数据，须声明SQL成功结果reset_fingerprints=true；统一归档器在持有归档所有权时，提交后先失效该数据集/来源摘要，再发布新摘要，失败保留消息。SQL提交后的相同内容重放仍须声明失效，避免失效失败后遗漏。普通不涉及跨键替换的归档不声明此项，热摘要继续免SQL。相同内容不写业务 DML，可信摘要命中免 SQL；缺失、损坏、不可信或异常超前版本回 SQL。SQL 状态与业务修改同事务，旧响应不得覆盖新版本。

插入、更新、相同确认及过时确认均属于成功处理，统一删除对应待归档消息；失败保留，不因无 DML 而积压，不因错误样本限额而丢弃业务数据。聚合未收齐的分页继续保留。每项目统一状态仅一条，不另建逐轮状态表。

未知 schema 只有在结构有效、数据集与任务精确登记时才能隔离项目；其他项目可继续。归属不明仍保守全局阻断。恢复必须走原归档路径，不清队解锁。详见 [归档去重](archive-deduplication.md) 与 [schema 隔离](schema-isolation-review.md)。

Redis 纯内存丢失边界不变，不承诺服务重启后恢复待归档数据。错误样本及运行记录沿用项目限量、脱敏和精确 ID 清理规则；成功响应不长期保存。MySQL DATETIME 按北京时间，内部版本比较保留带时区绝对时间。

### 断点、资源与磁盘访问

断点只保存恢复必需的范围、位置、计数、批次和阶段等有界状态；可由起止范围重建的完整日期/月计划在内存生成，不逐次复制进断点。以声明的最大历史跨度测试实际序列化字节数，满足公共断点上限，不以调大限制代替精简设计。

分别限制单响应、单条入队消息、整批聚合和并行预取的容量。大批量超过上限时，只能在业务允许的完整单元边界拆分，并保持连续覆盖和按序确认；不能拆分的单元应明确报错、保留可恢复位置，不截断数据或静默跳过。后续成功不能掩盖前序失败。

配置与可重建计划按生命周期加载和复用，避免按记录、日期或页面反复读本地配置及扫描磁盘；SQL 完整性检查采用有界范围查询，避免逐条回源。不得为“少读磁盘”增加永久业务副本或跳过必要校验。继续复用统一可信摘要：命中免 MySQL 读写，未命中回源比较；相同业务不做 DML，不为刷新观测时间写库。成功原文不落盘长期缓存，诊断和运行记录遵守现有 Redis 有界规则。

### 界面

公共控件、格式化、分页和 QueryScope 只读管理沿用正式模块；写命令不随切页取消。页面按需创建、隐藏时停用刷新，稳定身份恢复选择，刷新不覆盖草稿。滚轮不得改数值。UI 文件目标 300 行以内、当前检查上限 350 行，不通过压行或放宽限制规避职责拆分。

## 4. 必测场景

每个新增采集器都要新增自身测试，不能只依赖旧测试全绿。按业务适用性覆盖；不适用项说明原因，不人为构造不存在的分页或文件路径。

- 正常结果、空结果、字段异常、缺页/重复页/乱序/尾页边界，以及完整集合不能被半成品替换。
- 相同内容零业务 DML、有效修订、迟到旧响应、事务失败留队、提交后重放，以及成功但无 DML 时仍清队。
- 可信摘要命中免 SQL；损坏、过期或不可信摘要回 SQL，回源失败保留消息。
- 中断后断点恢复、同任务不重叠、容量不足与恢复、取消时回收；聚合类型补充整批预留测试。
- 实际登记的任务与数据集身份正确；未知版本保留并隔离对应项目，独立项目继续，归属不明仍阻断。
- 下载额度、代理回退和频控确实使用公共路径；并行声明需增加按序提交、失败和取消测试。
- 单个采集器停用、依赖失败不牵连无关项目；有页面时补充懒加载、查询过期、选择和草稿保护测试。
- 最大声明历史跨度的真实序列化断点大小、响应/入队边界及超大单元；合法重复去重前后仍正确核对来源数量，冲突重复不得被静默吞掉。
- 不能只测条数相同：构造重复 A、遗漏 B 的等数量集合，以及同证券多事件跨页重排；先证明分页稳定或使用可验证的完整集合。适用的插件复用 `contracts/collection_integrity.py` 的唯一集合核验，合法重复须另有来源证据证明完整性，不能用去重本身作为证明。
- 增加从来源响应到正式业务查询的端到端场景：已有业务记录但缺少新增必需字段/日期关联，补采后必须可查；覆盖冷热摘要和提交后重放。升级后旧覆盖证明必须显式失效，缺少关联字段时数据验收失败；不因运行成功放行。
- 初始化到增量的转换、重查边界、历史中间缺口、有效空单元、跨日/月/年和修订回看边界；验证每个必要单元无遗漏，而非只检查首尾日期。
- 在下载、发布、归档等待、SQL 提交后和最终确认阶段分别中断；覆盖 Redis 存活续采及测试环境中断点丢失后的 SQL 恢复。可拆分批次补充段间中断，确认前段失败不会被后段进度掩盖。
- 配置修改与已有断点的范围冲突、继续采集与重新初始化的语义；以功能实际支持的操作为准，不为测试新建第二条运行路径。
- 延迟归档时仍可继续发布后续批次，恢复下载不等待前批；整轮入队后才等待，早期消息残留或提交后清队失败不能被最后成功页掩盖。测试公共完成确认，不引入逐批等待作为修复办法。

公共入队竞态测试必须继续保留：锁等待/容量查询期间隔离、预留路径全局阻断、拒绝时断点及额度不变、无关项目不受影响、提交后不伪造失败。无需每个采集器复制一份相同测试，但不得替换公共入口逃避覆盖。

集成测试使用随机专属命名空间和测试来源，只清理测试拥有的数据，不清空共享 Redis、不改生产业务行、不重启数据库制造故障。

## 5. 交付核对清单

开工冲突检查、错误分类、分层验证及交付记录使用 [开发流程](development-workflow.md)；本节继续负责采集业务专项准入，不另造发布路径。

- [ ] 实际业务契约与插件登记齐全；没有重复实现或遗留旧路径。
- [ ] 生命周期表逐项填写并对应实现、专项测试和使用说明；初始化终点、增量起点、补缺、修订限制以及两类重启恢复依据均明确。
- [ ] 专项测试、隔离集成测试通过；结构变化完成明确授权范围内的显式维护和完整性核查。
- [ ] 更新功能日常操作说明、实现状态及受影响的架构/存储参考；新增表同步更新 SQL 定义、恢复清单和文档契约的正式表集合，不单纯关闭检查。
- [ ] 发布交付执行 `verify-release.ps1`，正常关闭桌面后验证，完成后重开；更新发布证据，不将快速单测称作完整发布门禁。
- [ ] 明确实际验证、跳过原因及未验证事项；模拟容量/离屏布局不冒充真实设备压测/读屏验收。
- [ ] 单列实际采集进度：来源及范围、已归档连续边界（或业务完成单位）、缺口与未完成范围、待归档/错误检查结果、下一次继续起点；注明核查时间，不把动态进度当作永久规则。
- [ ] 开发验收结果与实际采集进度分别报告；未跑完历史必须明确说明。按错误记录修复时先登记项目和确切错误 ID，修复验证通过后仅清理这些已解决记录，记录验证及清理结果，保留并发新增和未解决项。

纯文档修改只需文档契约和相关回归，不要求因此重打包。指南不增加逐步审批，不自动授权生产数据丢弃、周期备份、第三方发布或新的外部服务。现有测试不是自动证明新插件所有业务语义正确，交付时必须逐项核查本清单。

## 数据准备接入

新增数据查询插件须按 [数据准备契约](data-preparation.md) 声明 preparation 检查贡献，明确范围、必需/可选字段及漏采语义，并测试缺数据、插件停用、查询失败和范围内完整场景。一个来源即可独立满足，不强制多网站互证、源端版本号或完整修订历史。可选信息缺少、来源范围外历史及不适用项说明原因，不因此返回 fail/unknown；本项必需字段错误、范围内漏采和查询失败仍不能通过。财报等用于信号的公布日期要求按用途保留。

同时登记项目/任务/数据集身份和来源/归档专项测试集合；发布门禁生成绑定源代码摘要的执行证据。返回逐条 CheckEvidence，不接受整体完成布尔值；必要检查缺证据、测试跳过和查询错误不能完成。处理项目检查真正必需的输入，采集项目不等待其他数据项目。发布后页面自动检查；“已准备好”限于声明范围及用途，不表示适用所有回测。

数据准备按独立输出划分，通常独立采集插件各自登记项目与归属。2026-10-13用户修订：同一完整响应已经包含全部所需业务时，可由一个采集任务一次下载、全部校验、统一入队和同事务归档，避免重复请求。各数据准备项仍独立核验自身字段、集合与用途；共享响应必须显式声明response_group，并精确共用来源、项目、job_key、数据集及采集能力，不能用一个项目运行成功给多项直接打勾。不同接口、生命周期或可独立失败的响应不得仅按网站栏目合并。每项写明负责/不负责什么，来源和整理计算分开，related仅配合展示；跨数据核对另立处理项目。

## 2026-10-01 说明文档同步要求

新增或实质修改功能时同步程序内说明主题和 docs/documentation-coverage.json 页面关联；每个页面必须有操作或数据说明，不得仅补技术字段。正文按入门、日常操作、数据说明、故障处理、技术参考组织，写明入口、操作、保存/生效、结果与限制。动态实采进度与开发验收分别记载，不写成永久规则。

最后一次实现修改后执行 scripts/documentation_contract.py review --note <具体审阅说明>，再运行文档契约及相关回归；正式发布执行统一门禁。源码或正文改变会使旧审阅失效，不能只更新摘要冒充内容同步；确实不影响用户行为的调整须以 --unchanged-reason 记录具体理由。完整流程见 [说明文档维护](documentation-maintenance.md)。

## 2026-10-09 文档按功能同步

新增采集项目同时登记 docs/documentation-coverage.json 的 tasks 关联，即使没有单独数据页也需要数据范围文章；查询页面须关联数据说明。数据手册使用“如何查看、数据范围与更新、字段与日期、限制与排错、相关说明”五章和业务分组，技术字段/维护单列。相关模块改变后，修改无关文章不能代替对应正文同步；确无用户行为变化才可逐 page:ID / task:ID 记录具体理由。正文、专项完成后再建立审阅并在共享源码稳定时执行正式发布。模板和命令见 [说明文档维护](documentation-maintenance.md)。

## 表与键说明同步

每次新增或实质修改存储，同一实现者同步 [数据库参考](database-reference.md) 对应表/键条目与覆盖登记：业务表逐项说明字段、身份、索引和归属；Redis 键逐项说明类型、内容、所有者、期限、清理及恢复。数据手册链接对应对象；技术流程不复制另一套字典。文档门禁检查逐项覆盖和审阅时效，新构造方式先扩展扫描检查。

共享下载器提供显式retry_not_found契约，默认关闭，不能与允许返回404的allow_not_found同时启用。仅已核实存在临时404的来源必要单元声明；同花顺指数YYYY文件由last目录明确声明年份和数量，因此采用同一请求重试预算。last接口不可用规则及其他插件默认保持；不在插件另建重试循环。

## 采集规则准入

新增或修改采集任务须遵循[采集规则登记规范](collection-rules-standard.md)，填写逐任务接口与参数、开始/结束范围、初始化/增量/恢复、Redis和MySQL归属；规则页与实现同步，文档门禁检查覆盖与正式登记。规则可见不等于已完成实采。

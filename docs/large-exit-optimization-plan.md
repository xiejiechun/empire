## 1. 目标、依据与边界

目标是让 Empire 在数十至上千个独立出口之间扩展，保持业务完整性、版本顺序和成功清队，同时使下载、解析、归档的负载匹配。第一交付等级是 **1000 个独立出口的受控模拟端到端验收**，扩展等级是 **3000 个独立出口的受控模拟验收**。真实出口数量、来源实采与模拟等级单独报告。

当前实现依据：

| 已核对事实 | 影响及本方案处理 |
| --- | --- |
| `proxy_pool.py` 的目录 Lua 在 Hash 超过 1000 项时拒绝整个读取；限制对象不是在线 IP 数 | P3 扩展有界目录容量，覆盖失效项和同 IP 多设备；不能只改配置面板数字 |
| 全局下载最大值为 1024，保存的下载缓冲上限为 4 GiB | P3 将允许的窗口上限扩至 4096，保存值和启动值不自动提高；缓冲继续独立约束实际窗口 |
| 代理分配、健康计数和冷却更新存在按请求遍历节点集合的路径；共享事件会唤醒多个等待者 | P3 建立站点/出口索引、就绪队列和定时队列，减少重复遍历与无效唤醒 |
| 增量归档先经 `_load_records`，后经 `_flush_incremental` 再读取和规范化同一消息 | P1 消除同次处理的重复回读与完整规范化 |
| 归档总调度逐条串行；`mysql.archive` 使用单工作线程的 control 通道 | P2 同步改造调度、冲突所有权、归档执行通道和有界事务，不能仅多开协程 |
| 解析、规范化和摘要存在在后台事件循环中同步执行的部分 | P0 先测事件循环延迟；P4 只把实际热点纯计算移入有界处理进程 |
| 现有千节点容量记录主要证明模拟调度、配置边界和回收 | 不能直接宣称真实千节点、所有来源或 SQL 写入已达对应吞吐 |

### 1.1 当前问题的诊断依据

2026-11-06 北京时间约 10:29～10:31，本聊天只读观察到 28 个有效在线设备、27 个独立出口；同花顺 27 个出口均有最近 10 秒许可记录。一次 20.1 秒采样中，Stream 新增 169 条、长度从 8999 增至 9123，推得成功移除 45 条，即入队约 8.4 条/秒、移除约 2.24 条/秒。股东户数与题材详情断点处于等待归档；指数行情保留的 168 条错误中有 166 条 502。

以上是分时运行诊断，原输出在本聊天，未冻结完整源码/硬件/负载且不是配对基准。移除速率按当时仅有正式归档器清队的环境解释；P0 必须使用明确的成功 ACK 计数重新测量。不得用这段短采样证明数据库单独耗时、全部消息故障、缓存命中率或任何优化倍数。业务写入数为零也不代表未访问 SQL。

### 1.2 本方案保持的正式契约

- 保留一个采集运行时、一个统一归档协调器、一条正式 Stream 扫描与 XDEL 路径；不增加消费组或第二套归档实现。
- 同站点同出口 IP 最多一个在途请求；各站独立使用出口，合计受全局窗口和字节预算限制。429 继续冷却整个站点组，403 不以换出口绕过。
- RouterProxy 两个目录键只读；分配前通过 Redis TIME 原子复核最新映射及租约。账号绑定请求仍只使用指定设备。
- 每批业务与已入队断点原子提交，后续下载不逐批等待归档；整轮全部成功处理且清队后才能声明业务可查询。
- 同内容确认、旧版无需写入、真实写入都可成功清队；失败保留。缓存的摘要、版本及有效期必须同时可信，不能以进度标记替代。
- `collection_state` 仍每项目一行；不按 worker 拆状态行，不引入逐轮持久化表，不新增业务数据库 DDL。
- 业务版本、来源日期、精度、完整集合、补缺及修订周期不因性能优化放宽；历史响应和成功原始正文不长期保存。
- Redis 仍为纯内存。Empire 重启可重放保留消息，Redis 服务重启丢失队列后的恢复仍依据各来源的 SQL/覆盖契约。

## 2. 容量模型与交付等级

用四组量分别描述容量：HTTP/原生尝试次数每秒、实际传输/解压字节每秒、规范业务行每秒、归档消息/事务每秒。认证、辅助请求、重试和重定向计入请求成本；一请求不一定是一消息，一消息也不一定是一条 SQL 记录。

单站点的理想请求率上界为 `min(N / I, C / L, R_site, R_bandwidth)`：N 是健康独立出口数，I 是每 IP 最短间隔（秒），C 是可用在途窗口，L 是响应耗时（秒）；未配置全站保护时 R_site 不额外收紧。实际还受任务依赖、解析和归档约束。

1000 出口、2 秒间隔仅给出最多 500 次/秒的频控上界。若响应需 3 秒且同站每出口只有一个在途，请求率上界进一步降至约 333 次/秒。平均 100 KiB 正文、500 次/秒约为 48.8 MiB/秒正文流量，尚未计协议和解压。示例不是来源许可或本机实测能力。

| 等级 | 必测规模 | 可宣称的结论 |
| --- | --- | --- |
| P0 基线 | 冻结当前代表任务、30/100 出口受控负载 | 明确各段耗时、资源与吞吐；不存在优化结论 |
| S1000 第一交付 | 100/300/1000 健康独立出口；另测 3000 目录项中只有 1000 个有效独立出口 | 通过的具体负载在千出口模拟环境下稳定；需列出实际 SQL 写入能力 |
| S3000 扩展交付 | 3000 独立出口、5000 目录项边界、5001 超界行为 | 仅在扩展项全部通过后声明三千出口模拟等级 |
| R 实采 | 当时实际在线节点，来源约 5% 最小完整业务样本 | 只证明该来源、样本及实际出口环境；不冒充真实千节点持续压测 |

第一阶段仍部署在单机。P0 固定测试机 CPU、内存、磁盘、网卡、数据库及版本；按实际结果判定是否达标。单机持续 CPU、带宽或数据库成为硬瓶颈时，形成独立扩容设计再实施，不能以“未来分布式”替代本次未达标项。

## 3. 目标结构

```mermaid
flowchart LR
    A[任务规划与公平调度] --> B[站点及出口许可]
    B --> C[有界异步下载]
    C --> D[有界解析和规范化]
    D --> E[按业务顺序校验发布]
    E --> F[现有 Redis Stream 与断点]
    F --> G[单一归档协调器]
    G --> H[按冲突域分配的批处理执行槽]
    H --> I[SQL 事务或可信摘要确认]
    I --> J[摘要与成功记录及精确 ACK]
    J --> G
    G -.积压与延迟反馈.-> A
    D -.内存与处理能力反馈.-> A
```

协调器拥有消息领取、项目隔离、完成栅栏和 ACK；工作线程/进程只是同一路径的执行资源，不自行扫描队列或删除消息。每一段限制在手数量和字节；达到下游高水位时只收缩新准入，已有资源仍由原所有者完成或取消回收。

## 5. 各批实现规格

### 5.1 P0：先获得可归因指标

在现有计数器上增加固定桶直方图及阶段累计值：下载准入等待、源站交换、解压、解析、规范化、摘要计算、缓存读写、SQL 排队/事务、归档调度等待、成功 ACK、事件循环延迟。区分墙钟耗时与可取得的 CPU 耗时；不能把 await 期间其他任务的执行时间归为当前函数 CPU。

指标按已登记项目/站点聚合，使用固定容量的 10 秒和 5 分钟窗口，不按每消息新增永久记录。业务阶段用现有 job/batch/stream ID 关联；明细证据限于隔离测试及必要错误 ID，去除凭据、成功原始响应和大业务正文。恢复后最老待处理年龄用 Stream ID 计算，并区分尚未收齐的聚合批与可立即处理的消息。

缓存命中数、SQL 尝试数、业务 DML 行数、成功 ACK 数分别统计。重放/旧版确认不可计作新增业务写入。指标采集本身不刷新摘要有效期、不改变业务状态；浏览诊断不创建 Runtime 或第二归档器。

### 5.2 P1：减少归档重复工作与往返

1. 独立增量消息在进入处理槽后只回读一次，保留这一条/小批完整规范化结果直到处理结束。队列常驻索引只保留有界标识和必要元数据；扫描阶段仍做结构、精确登记和隔离归属检查，完整业务校验必须发生在写库或可信确认之前。
2. 同一处理尝试复用已算出的规范内容摘要，不在 SQL 返回后再次序列化同一内容；版本及来源修订参与方式沿用现行契约。
3. 对同 namespace/source 的摘要批量查询和更新，Redis 往返用有界 pipeline 或单个有界 Lua 合并；pipeline 不被当作事务。历史记录按同项目一批读取既有保留项、按 ID 幂等替换并截断，保留现有最近 100 条和 revision 语义。
4. 将已确定成功的确切 ID 合并 XDEL。若前置摘要/记录/进度写失败，消息保留；提交后 ACK 失败仍可安全重放。任何批内失败都不能把未确认成员放进 ACK 列表。
5. 聚合股票等完整批次保持集合校验、完整栅栏和业务原子性，不按独立增量页套用处理捷径。

初始实验批量取 1/8/16/32 条，另设规范字节和业务行数上限；P0 冻结选档方法。P1 首选目标为最多 16 条、4 MiB 规范数据、10000 行，先到者结束取批；单个合法完整单元超批量目标时单独处理，仍受既有单元硬边界约束。事务或 Lua 已开始后不因墙钟预算强行中断；超预算只阻止继续追加工作。

### 5.3 P2：冲突所有权与并行归档

不能假定“不同项目就没有写冲突”。登记每个数据集实际读写的业务表/唯一键范围、共享摘要范围、附带状态及整表替换行为：

- 第一版同项目只允许一个处理槽，覆盖同一 `collection_state` 行和项目完成标记。项目内连续单元通过批处理提高吞吐。
- 不同项目只有在共享写集合、摘要键及整表替换互不冲突时才可并行；不确定的数据集进入保守独占域，不能靠命名不同判断安全。
- 业务锁序由统一协调器按固定顺序取得，覆盖缓存读取、SQL 提交、摘要确认到 ACK/结果收尾，避免旧版本在新版本之后刷新摘要。数据库行锁和旧版防覆盖仍是最终保护。
- 未收齐的聚合批暂存；manifest/complete 只能在该项目本轮所有前序单元成功后执行。最高成功页号不代替完整集合。
- 项目隔离同时阻止该项目待启动槽和新入队；已经提交的真实成功不能改报失败。隔离竞态与取消都必须按既有契约验证。

`mysql.archive` 保持唯一写入口，内部接入独立的有界 archive SQLLane 与对应连接池；控制配置通道仍独立有界，防止长归档阻塞任务保存。候选 worker 数为 2/4/8，连接池与 worker 上限一致、禁止无界 overflow；选择满足吞吐且锁等待/尾延迟最低的最小档，记录 P0 硬件条件和选档数据。

批量 SQL 只组合同一冲突域、合法连续且可同事务的完整业务单元，调用正式 writer，完整返回每个成员的确认结果。一个事务中任一成员失败则整体回滚，整批成员不 ACK；不跨业务补写半份集合。同内容不产生业务 DML，来源修订正常更新，旧响应不覆盖。线程被取消后仍等待实际事务结束，不释放尚在执行的连接或冲突所有权。

### 5.4 P3：出口索引与目录边界

建立三个职责清楚的结构：设备表按 code 索引；出口表按 exit_ip 聚合设备；站点表记录该出口的忙闲、最早可用时间和等待者。就绪队列公平选出口，最小堆管理冷却/频控到期，用代次标记淘汰过期项并周期压缩，避免无限堆积。健康数量增量维护；同出口变动只更新关联项。每次分配仍对选中设备执行原子候选复核。

绑定设备请求用 code 直接定位；普通请求维护本次失败设备排除集合。该集合的尝试上限与目录容量分别定义，不能把目录扩容等同于单请求尝试几千设备。保留总请求时限、退避、认证边界及已有故障冷却。

目录设计初版保持每次快照的 Hash/ZSET/Redis TIME 原子关系，采用 **最多 5000 项、单项最多 4 KiB、返回总字节最多 8 MiB** 的明确边界。超大单项归为无效项且不输出原文；目录总量/总字节超限返回明确诊断，不静默取前 N 项，也不改写 RouterProxy。已知项只可在最新候选原子复核成功后继续使用；目录超限不能自行解释为全部出口失效并静默转直连。

常规目录全量刷新由共享周期任务负责（初始 5 秒）；等待者不触发各自全目录刷新。分配前候选复核保证删除、过期和凭据变动立即拒绝旧项；新节点在下一成功刷新后加入。对空目录恢复只允许合并的受控刷新。若原子快照不能满足 Redis 阻塞门槛，再单独设计分批发现；不得直接将 HSCAN 当一致快照或据不完整枚举认定设备删除。

窗口契约允许值上限扩至 4096，已有保存值不变；默认/固定限速/每 IP 间隔/max_rps/代理选择不被推荐或自适应修改。4 GiB 下载缓冲上限本批不随节点数提高；实际大响应并发由预算决定。对可复用连接进行基准测试后设定有界 keepalive 数与闲置回收，保留共享 TLS 上下文和退役连接关闭所有权。

### 5.5 P4：纯计算隔离与有序消费

先对 P0 测出的解析、规范化、摘要热点去重和局部优化，再比较直接执行与 2/4 个处理进程。2026-11-06 正式长测暴露生产与归档争用计算槽，增加 8 进程实验档；默认档位须依据收益、RSS 和配对结果选择，不能仅凭核数提高。处理进程仅接受有界正文/规范数据及声明的纯函数参数；Redis、SQL、网络、代理凭据、Qt 对象和来源身份由原运行时持有。Qt/QJSEngine 绑定的请求签名不移入通用工作进程。

使用同一业务解析函数，不复制第二套规则。入队前将正文、解压、待解析、解析结果及 IPC 复制的额度计入同一公共预算所有权；不能在传给子进程时提前释放。响应大于单元预算明确失败，不互等扩容、不借磁盘保存成功原始响应。解析结束后尽快释放原始正文。

可以乱序完成独立单元，但仍按来源契约消费、校验和发布；前序失败不推进连续断点。慢项阻塞只允许在有界窗口内积累结果。处理进程崩溃时该单元失败，回收任务与额度；替换执行进程不自动重发 HTTP。单响应或前页 ID 依赖的来源不制造无意义并行。

实测资本运作 C 合成 HTML 直接解析中位约 230 ms，已接入同一计算通道。来源输入在共享预算内有界，完整解析结果 IPC 上限 16 MiB；默认预取为每证券预留三倍结果工作区，计算复用该租约，不重复占额度。小于 64 MiB 的保存预算不预留该工作区，由解析前非阻塞申请决定是否可处理。大源解析与后续规范化的不同结果上限分别保留，不把压缩后消息上限误作来源 HTML 上限。完整 C 基准须显式启用计时内来源解析；此前仅测 Envelope 的结果不能替代。

### 5.6 P5：软反馈与硬边界

采用统一控制器每秒读取固定窗口聚合值，调节下一次准入的有效窗口，永远不超过保存的全局/站点/来源上限。反馈看可处理队列最老年龄、归档成功吞吐、解析积压、字节预算和事件循环延迟；项目隔离单独显示，不把未知 schema 当可通过增大资源解决。

初始实验策略：可处理队列年龄持续 3 个周期超过 30 秒、下游持续增长或资源超过软高水位时，将新增窗口减至当前的 75%；连续 10 秒低于 10 秒且资源低于软低水位时，每周期最多增加一个小档。增长必须受测得的下游能力约束；具体高低水位、窗口下限和增幅由验收固定，不覆盖已有硬水位。监测缺失时保守限流，不能用零队列假值放开。

必须保留完成当前合法单元、补齐已开始聚合批和归档处理所需的资源；反馈只挡新工作，不挡已持有预算的收尾，不形成“等归档完整批，而下载被完全停住”的环路。单项目队列压力不得无故饿死其他可运行项目，预留的资源计入总上限，不另建隐形额度。

同站任务先使用等权公平队列，保留所有已保存计划；大、小任务都获得有限等待的机会。实时任务优先级作为后续明确的产品策略，不依据任务名称暗中改优先级。对持续 502 先通过共享下载路径核实错误来源；只有证实的节点传输故障才进入节点冷却，不能把来源错误批量误判为坏代理。30 次重试的保存值不静默降低；必要策略变更单独形成可见配置/来源契约。

## 6. 配置、存储与文档交付

本方案不增加业务表、业务消息 schema 或正式 Redis 键。指标、调度索引、执行槽及自适应窗口为可重建内存状态；沿用现有队列、断点、摘要、记录和 app_setting。若实现发现必须新增物理键或持久设置字段，先补所属对象的类型、身份、容量、期限、清理、恢复及显式配置迁移设计，再实施，启动不自动迁移。

允许窗口上限变化属于资源契约变化，现有合法保存值必须原样读取；不根据在线节点数自动保存新配置。公开 UI 只展示有效窗口、正在下载/解析/等待归档、积压和失败原因，不把内部 worker、锁域或 Lua 参数塞进日常设置。新增可变值控件仍遵守滚轮不改值。

各批同步对应权威说明：代理与下载公共主题、受影响来源、归档/摘要/记录对象、Electron 资源及问题说明；新增实质功能按覆盖登记核实。先更新权威正文再 generate；最后实际实现修改后执行逐功能 review 和正式门禁。不能为本方案给当前其他并发改动签署全量审阅。

# 业务数据库设计规范

## 状态与适用范围

2026-10-05 用户要求建立统一表设计准入，避免每新增一个采集器再返工。本文是后续新增及实质改造的设计规范；不是现有数据库已经完成改造的声明。现行部署结构仍以 `sql/schema.sql` 和正式数据集登记为准。开盘啦的具体实施见 [七项存储优化方案](kaipanla-storage-optimization-plan.md)。

规范约束设计结果与验收证据，不强制每个插件相同的物理布局，也不要求每个新插件新增表。执行常规设计、测试及已授权维护无需增加逐步审批。

## 1. 先确定业务粒度和查询，再设计表

每个数据集实现前提交一份存储设计卡，至少写明：

| 必填项 | 必须回答 |
| --- | --- |
| 业务粒度 | 一行代表证券、事件、报告科目、日期快照、时间点还是来源序号？完整归档单位是什么？ |
| 身份与来源 | 唯一键、允许重复的维度、固定/多来源归属；来源身份与分析身份是否相同？ |
| 字段字典 | 来源路径、含义、类型、精度、单位、NULL/零/缺失区别、值域、时间语义、未知字段处理 |
| 访问模式 | 至少列出正式详情、范围浏览、分析筛选、覆盖检查、修订写入所需 SQL 及返回上限 |
| 数据规模 | 当前样本、预计一年/五年行数及字节、最大完整单元、索引与临时迁移空间预算 |
| 一致性 | 原子提交范围、无变化零业务 DML、旧版防覆盖、完整性证明如何失效 |
| 生命周期 | 初始化、补缺、修订、Redis 丢失恢复、历史保留与维护边界 |
| 交付 | 唯一读写路径、显式迁移、反例、性能预算、用户说明及正式发布证据 |

模板可直接使用上述表格。不能仅填“JSON 灵活”“以后优化”“按需加索引”。来源字段含义未确认时保留来源字段名/序号与单位限制，不根据样本猜测。

## 2. 表按业务实体组织，不按接口数量组织

- 相同业务实体、键及修订规则才允许共表；不能仅因同一网站而塞入万能 `kind + payload` 表。
- 相同接口可对应父子表；多个接口也可共用一个业务表，但必须证明字段口径、生命周期、修订和完整性独立性不被破坏。
- 固定来源在数据集登记中声明并于写入前校验，不机械增加恒定 `source` 列。多来源记录按来源参与唯一身份，不能覆盖掉另一来源的事实。
- 证券键统一 `unified_code`，不新增另一套 market/code SQL 身份。历史业务不外键级联到当前 `stock` 名单，证券退出现有名单不能删除历史。
- 父表仅保存真实聚合业务的身份、来源证明、内容摘要及必要校验属性；不能把逐轮日志、下载进度或独立每日完成表伪装成业务表。项目进度仍只在每项目一行 `collection_state`，临时运行状态仍在 Redis。
- 明细只存自己的原子事实；主键和索引所需身份重复属于关系关联成本，不是重复业务副本。正式业务字段只拥有一个权威存储位置。

## 3. 普通列、JSON、长正文及压缩内容的边界

| 内容 | 默认选择 |
| --- | --- |
| 身份、关联、日期、状态、常用筛选/排序/聚合数值 | 有类型普通列及必要约束 |
| 稳定、需按点查询的时间序列 | 有类型明细表，保留真实点键或来源序号 |
| 动态科目 | 报告/事件头与有科目身份的明细；先保留层级和来源科目语义，不能强行对齐未知科目 |
| 文章正文、说明文本 | 有明确上限的 TEXT 类字段，不能为规避建模包装成 JSON |
| 少用、稀疏、尚未确认语义的附加属性 | 有 schema/version、大小上限、允许字段策略的 JSON 扩展 |
| 只按完整块读取的大量有序数据 | 经容量与查询实测后选用块存储；必须有正式解码契约、块边界及安全上限 |

不能以 JSON 当作完整行、整份接口响应或全部业务字段的默认兜底。需要查询的扩展属性升为列后，显式迁移并从扩展删除该字段，不能长期双写。生成列/函数索引只用于有明确查询收益且不重复持久化整份对象的场景，不能替代主体建模。

不全面禁止 JSON，不把数组展开或压缩等同于节省空间。选用块存储必须说明失去哪些 SQL 条件下推能力；正式系统只部署一种权威布局，不长期维护 JSON 与明细两套业务库。

## 4. 类型、精度与数据约束

- 价格、金额、比例优先用足够精度的 DECIMAL；整数仅在协议和样本证明确为整数时使用。具体 precision/scale 根据来源契约及极值验证确定，不能统一套 `DECIMAL(10,2)`。新值超界或精度增加须明确失败，不能静默截断、四舍五入或溢出。
- 解码、规范化、摘要与 SQL 的数字语义须一致。引入 Decimal 必须验证现有 JSON 数字往返及摘要兼容；不能借类型升级改变旧值。
- NULL、零、空数组、缺记录、源端暂无、未采集各有不同语义。必需字段使用 NOT NULL 和适用 CHECK；不以 0/空串填补未知值。
- 业务日期、来源观察时刻、公布/可用日期、入库观测版本分别定义。MySQL DATETIME 为北京时间；内部版本继续使用带时区绝对时间。没有发布时间不能伪造历史信号可用时间。
- 有唯一时间键才用时间作唯一键；同秒/同分钟多条必须保留来源序号或真实 ID。修订中序号只代表该完整单元内顺序，不冒充跨修订稳定事件 ID。
- 文本及 JSON 都设业务上限；超限走有界失败与诊断，禁止截断有效业务。未知扩展必须有字段/大小策略及测试，不无限接收未来结构。

## 5. 查询和索引准入

索引来自已登记访问模式，至少评审“单证券日期范围”和适用的“日期范围全市场”。不能认为 `(security, date)` 同时适用于后者。

必须提供 EXPLAIN、实际返回行数、扫描量、读取字节及延迟。大正文不进入覆盖扫描、列表投影或 COUNT 查询；按需展开详情。大列表使用稳定键游标分页，单页有界；不能只在 UI 对全量结果切片。组合主键与每个二级索引都计入空间和写入预算，不给每列建索引。

避免逐点 SQL、逐证券日回源 N+1；使用有界批量查询/批写。查询总量、并发和字节有明确预算；一个页面按需创建且可取消的只读调用继续走 QueryScope。写命令不因切页取消。

## 6. 完整性证明、摘要与版本

可信覆盖依据必须与同事务提交的业务内容、完整单位、校验契约版本及必需关联信息绑定。行数、最大日期、一个布尔 complete 均不足以证明完整。

日常规划读取当前可信业务头/覆盖属性；详细数据准备和维护审计仍核验正文、业务键集合及摘要。规范/必需字段/来源规则改变时，通过显式维护重建受影响证明；旧证明不能因为数量相同而沿用。直接修改 SQL 必须停止归档并失效相关 Redis 摘要及受影响覆盖证明，修改后重新审计。轻量证明不承诺自动发现绕过正式路径的任意篡改。

相同规范内容不写业务表；仅为了刷新时间、计数、证明或布局版本而发生的改动不得混入普通重复归档，结构证明升级走维护入口。有效修订只更新受影响事实；完整单位的父子记录、摘要、版本及项目状态同事务提交。旧消息不得倒退业务，SQL 后清队失败可重放。Redis 命中免 SQL、成功清队和隔离规则继续由统一归档器执行。

## 7. 容量与迁移是首次交付的一部分

至少用真实小样本及隔离放大数据测量：平均/P95/最大单元、全年/五年规模、表与索引实际分配、峰值内存、初始导入、重复无写入、少量修订、列表/详情/范围分析和覆盖扫描。注明冷/热缓存、机器、MySQL 版本与测量条件；不能把一次热查询或 JSON_STORAGE_SIZE 当生产容量证明。

性能预算先定义再测量；不满足时优化设计或如实提交范围限制，不能删掉测试或只提高超时。预计空间不足时在迁移前报告，并继续隔离验证，不能删除业务或恢复副本腾空间。

维护复用现有显式升级模式：只读预检、持锁停机、等待队列归零、影子表复制、逐业务单位等价校验、多表切换、发布匹配程序及可恢复日志。DDL 隐式提交，不能声称迁移全部可事务回滚。启动不迁移，正式路径无旧布局回退；恢复副本不是双写路径。切换后有新写入时禁止直接回退旧快照丢失增量。

## 8. 自动检查与人工证据

以下检查由 sql/schema-contract.json、docs/database-design-cards.json、运行schema核验和 scripts/verify_database_design.py 接入构建/发布门禁；来源语义与性能证据仍需人工实质核对：

1. 数据集到表、主键、字段类型、索引、约束及来源归属与 DDL 一致；schema 检查不能仅比列名。
2. 每个新数据集有存储设计卡、字段字典、查询预算及相应反例测试。
3. JSON 列登记用途、上限和允许字段；核心字段不能仅藏在 payload 而无设计说明。
4. 完整性证明失效、重复零 DML、旧响应、同数异集、事务失败、SQL 后重放及成功清队均有证据。
5. 迁移报告绑定程序/DDL/字段映射版本和数据库身份；代码或结构变化使旧证据失效。

工具能校验登记与测试存在，不能自动证明字段语义和来源单位正确。不能用形式化清单代替来源核实。

## 9. 现有表的分批治理边界

开盘啦七项作为首次完整改造。随后按此规范评审财报三表与资本事件 JSON 表：先确认实际科目、重复方案、查询用途和类型，再编写各自迁移方案；不套用分钟表模型。股票、新闻、日历、行业和停复牌优先核查现有字段、索引、关联和预算，不为统一外观重建已经合适的表。`app_setting` 与 `collection_state` 是配置和状态，不能因采用 JSON 就按业务明细拆分。

本次文档交付不授权批量迁移其他业务表。目标是新设计首次交付即考虑查询、容量和恢复，并在需求/来源变化时有受控演进路径；不是承诺数据库永远无需优化。

## 容量证据时效门禁

设计卡capacity状态分为measured与明确已有的legacy_baseline。实质改造按measured登记机器可核验报告：测量范围、环境、代码/DDL SHA-256、数值及上限、超原目标时的实质取舍；发布检查绑定文件与每项预算，过期或超限拒绝。已有未改造表的legacy_baseline仅登记旧契约，不能冒充完成新容量验收。语义与取舍仍由审阅者负责，不因为静态字段齐全就自动接受设计。

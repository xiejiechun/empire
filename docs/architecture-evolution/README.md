# 模块化优化执行入口：给接手的开发者与 AI

本文档组把 [已批准方案](../architecture-evolution-plan.md) 拆成可执行任务。目标是完成 A–F 的代码、迁移、验证、发布和交付，不以目录整理、测试数量、草稿数量或一份方案代替实现。制定于2026-10-19；实际进度只以 [状态账本](status.md) 及它引用的证据为准。

## 1. 从哪里开始

按顺序阅读：

1. 项目根 [AGENTS.md](../../AGENTS.md) 与 [开发流程](../development-workflow.md)：保留已有变更，核实共享环境和授权，业务数据与配置的边界。
2. [状态账本](status.md)：当前源码、远程、已安装包、正在执行的任务，以及第一项未完成工作。
3. 本文第2～7节：任务状态、环境、实施方法和共享资源约束。
4. [C 收尾、D 股东、F 维护工具实施手册](cdf-implementation.md) 或 [E 逐业务实施手册](e-implementation.md)：只读取本轮需要的阶段及其前置。
5. [验收手册](acceptance.md)：在改代码前确定适用反例、证据及完成条件。
6. [计划迁移登记](planned-migrations.json)：未实施路径的设计清单，不是运行时登记，不证明已经迁移。

任一文档与当前代码不同，先记录差异并核对提交。历史证据保持原样；更新当前状态和计划，不重写旧报告使其看起来对应新代码。当前用户的新指令优先于本交接文档；本文件不授予超出当前任务的权限。

## 2. 最终要交付什么

- 正式业务按 `features/<业务>/` 归属，完整业务有一个 README 定位入口；普通函数和控件不强制包装成可启停插件。
- 内核、下载、代理、限流、入队、统一归档、摘要、SQL执行、任务调度及公共UI仍只有一个正式实现。公共模块通过贡献契约接入业务，不导入具体业务实现。
- 跨业务只使用公开契约/查询能力，不导入对方采集执行器、UI或私有函数。
- 身份和数据语义保持：插件/能力/任务/数据集/schema/job/namespace/页面/稳定顺序、用户保存配置、来源规则和恢复规则均有精确证据。
- 所有本轮涉及的旧入口与调用方同批退役；没有转发兼容层、双登记、双写或第二调度/归档路径。
- 单源文档、影响报告与类型边界进入正式路径，相关反例、性能和真实桌面证据齐全。
- 每批形成可追踪提交、完整门禁、产物身份和真实桌面记录；最终按验收矩阵逐项结案，列明来源限制与未通过范围。

新增独立业务最多增加一项业务工厂白名单。必要SQL设计、文档覆盖和测试登记单独列明，不为追求“只改一个目录”隐瞒公共契约消费者。

## 3. 任务状态的唯一解释

| 状态 | 必须已有的事实 | 可以做的下一步 |
| --- | --- | --- |
| 未开始 | 仅有需求与退出条件 | 阅读、设计、范围核实 |
| 草稿已准备 | 候选在本地准备目录；可有文本/AST审阅 | 对真实前像重基、审阅；不能声明功能已存在 |
| 已合入待验证 | 正式树已有实现和旧入口退役 | 执行定向、恢复、实采适用验证 |
| 开发验证通过 | 所有本批适用开发检查与证据通过 | 冻结最终输入，运行正式发布 |
| 已发布待桌面 | 发布 journal 为 committed/passed 且安装身份匹配 | 配置、异工作目录、正式查询、实际窗口验证 |
| 已验收 | 全部适用出口满足并有证据；限制准确说明 | 提交证据、推送，进入下批 |
| 失败/阻塞 | 有具体失败项、资源状态和恢复动作 | 修复或取得缺失条件；保留失败证据 |
| 不适用 | 有针对本批改动的具体理由，且其他相关证据齐全 | 按适用范围继续；不等同通过 |

只有“已验收”可以用于已完成阶段。不得用预写的 `passed: true`、占位报告、旧源码测试、跳过的用例、草稿静态检查或离屏截图代替相应实际证据。不要为了使应用助手放行而制造 acceptance 文件。

## 4. 批次顺序与并行边界

```text
A/B发布与桌面 → C发布与桌面 → D发布与桌面
→ E0 SQL归属 → E1财报 → E2指数/行业/指数行情
→ E3股票/日历/停复牌/准备与目录 → E4开盘啦
→ E5资本行为与复权 → E6a～E6g各事件业务 → F收束
```

E各批的真实依赖和可调整顺序见E手册。顺序调整需明确共同契约、前批产物和验收范围，不把整个E一次套入以减少发布次数。未迁业务仍由 `features/remaining.py` 持有声明；最后一项迁完且全部引用退役后才删除它。

可以并行：只读源码审查、职责清晰且互不覆盖的实现草稿、文档草稿、反例设计。必须串行：正式源码应用、最后文档审阅、真实来源验证、测试库压测、性能测量、构建发布、桌面操作、共享数据库维护。

正式发布开始后，冻结所有受保护输入和Git HEAD；等待的不只是pytest，还包括构建、搬移/配置smoke及最终发布切换。此期间只在忽略的准备目录工作，不提交正式文档、测试、配置或代码。性能测量还要求停止同期扫描、测试和构建，避免污染冻结指标。

## 5. 本机环境与初次核实

下面是2026-10-19的本机定位信息，不是永远有效的环境事实。新会话先核实，不能仅按端口或旧PID推断归属。

| 对象 | 当前定位 | 约束 |
| --- | --- | --- |
| 项目 | `D:\project\empire` | PowerShell，源码开发根目录 |
| Python | `.venv/Scripts/python.exe` | 依赖/解释器以正式环境门禁为准 |
| 正式程序 | `dist/Empire/Empire.exe` | 完整目录发布；保留同目录config |
| 正式MySQL | 项目既有3307实例 | 不关服务、不清数据、不执行本任务未设计DDL |
| 独立测试MySQL | 本轮自有13348实例 | 配置在本地build；须核实实际server_uuid及数据目录 |
| 测试配置定位 | `build/architecture-evolution-20261019/mysql-settings.json` | 真实凭据不打印、不提交、不放入文档 |
| 本轮测试数据目录 | `build/architecture-evolution-20261019/mysql-data` | 任务最终结束且确认无人使用后才关闭自有实例 |
| Redis | 正式配置所指共享服务 | 不清空、不重启；验证仅用独占前缀和归属核实清理 |
| 配置 | 根目录及EXE目录各自的 `config.toml` | 唯一默认位置，保留现有字节，不搜索旧用户配置 |
| 插件偏好 | `%LOCALAPPDATA%/Empire/plugin-state.json` | 保留；不以重置偏好解决身份漂移 |

初次只读命令：

```powershell
Set-Location -LiteralPath 'D:\project\empire'
git status --short
git branch --show-current
git log -6 --oneline
git remote -v
Get-Content docs/architecture-evolution/status.md
```

随后查看现有发布日志、journal、独占锁所反映的活动所有者和相关进程，确认是否存在未结束的发布/维护/桌面。不要删除锁文件或强杀进程。遇到已有dirty内容，逐项判定归属并保留；不能用reset/clean恢复“干净状态”。

发布、测试和网络环境不得在命令中输出密码。当前测试服务若已不存在，应按现有测试环境流程建立新的独立实例，记录真实身份后再执行；不能将测试配置改指生产库以凑通过。集成fixture默认完整schema，不能提前启用F实验模式。

## 6. 每一批的固定执行流程

| 步骤 | 操作 | 必须留下的结果 |
| --- | --- | --- |
| 01 定位 | 对照状态账本、HEAD、上批发布和当前差异，读取本批手册 | 本批ID、前批证据、源码身份、已有变更归属 |
| 02 列范围 | 列明业务、修改职责、旧→新路径、公共消费者和持久化身份 | 精确变更/退役清单；不改表或键的声明必须对应diff |
| 03 定验收 | 在实现前选定适用专项、失败恢复、来源、容量、UI和性能项 | 本批验收矩阵；不适用理由；冻结随机种子/协议 |
| 04 准备 | 审阅现有草稿与真实前像；缺少草稿按登记重建 | 候选hash、冲突列表、审阅结论；不得整树覆盖 |
| 05 应用 | 一次完成调用方迁移及旧路径退役，保留原实现语义 | 可审diff、正式单一路径、所有任务与贡献精确身份 |
| 06 开发验证 | 静态/类型/专项→隔离归档恢复→适用实际链路 | 每条命令、退出码、JUnit/JSON、范围与限制 |
| 07 容量/性能 | 只运行已审阅安全入口，串行测量 | 新报告；原阈值；真实环境；清理证明；旧报告保留 |
| 08 文档 | 修改使用说明、结构/存储文档和覆盖关联，最后review | 具体语义说明和逐功能不变理由；契约检查通过 |
| 09 冻结提交 | 确认无其他正式编辑，形成完整实现提交 | 提交ID、干净状态、受保护输入摘要 |
| 10 完整发布 | 正常关桌面，运行唯一 `verify-release.ps1` | 全量测试、依赖、配置、包smoke、committed journal |
| 11 实际验收 | 对安装包做异cwd、真实查询、可见桌面和正常退出/重开 | 真实操作、版本标识、配置/偏好保留、资源状态 |
| 12 结案推进 | 逐项复核验收矩阵，更新事实文档、提交并推送 | 证据提交、远程确认、状态变更、下一批入口 |

任何步骤失败，不跳到后面写“已完成”。先记录失败、受影响输入、残留资源和处理动作；修复导致输入变化时，重新执行受影响检查。正式发布因输入漂移或测试失败退出，要在最终新提交上重新完整运行，不能复用失败轮的成功片段拼装发布证据。

常规操作在既有授权内自主完成；这里只规定工程顺序，不增加逐步向用户申请批准的流程。涉及业务数据丢弃、超出任务范围或新增权限时再说明具体问题。

## 7. 准备稿的用法与缺失时的处理

`build/` 被Git忽略。本机可能保有多个作者、多个基线和多次修订的草稿；它们是实现加速材料，不是正式产品或唯一交付来源。远程克隆没有这些文件是正常情况。

使用任何草稿前：

1. 从本批手册定位最终manifest，逐项核对候选hash与记录的原文件前像。先读取助手全文，确认它只操作声明范围。
2. 对照当前HEAD及上批新增安全工具、类型、文档和测试。候选基线过旧时按职责合并，不刷新前像hash假装可直接应用。
3. 严禁直接把完整 `tree/` 覆盖正式仓库，严禁一次套入全量E闭合草稿。
4. 默认检查、静态AST和补丁预检只证明候选可审；后续真实运行验证一个都不能省。
5. 本批结果不依赖忽略目录才能复核：将脱敏事实、必要的设计/迁移登记和报告保存到正式docs/evidence；源码和测试保存到正式目录。

草稿缺失或hash不符：以当前正式源码、计划迁移登记和相应阶段手册重建该批。先取真实声明/路径/函数体，再进行职责迁移；保留旧源码作为前像，AST/身份/顺序比较后运行相同验收。文档列出的“待实现脚本”必须先实现并测其反例，不能运行同名过时脚本或把待建能力称为保障。

## 8. 失败处理与恢复底线

- 来源请求失败或来源质量缺口：保留真实结果；不换随机样本、不填零、不推进断点、不清未修复错误。业务完整性和结构迁移的适用判断分开报告。
- SQL/Redis故障：保留待归档消息。只由唯一正式归档器重放；不手工XDEL、不清共享Redis。
- 私有测试资源清理失败：报告失败及确切owner/库/namespace；使用已审恢复入口。生产库/共享前缀不能作为恢复目标。
- 构建或切换失败：原安装包和config应保持；查看本轮journal，按正式恢复入口处理。不删除他人锁，不擅自覆盖dist。
- 性能超阈值：记录原数据，查干扰、修复或缩减本批改动。不得调宽冻结阈值、改基线或只保留通过轮。
- 文档review失败：核对具体功能和正文。不通过全局理由、复制摘要或无关正文修改来遮盖语义差异。
- 数据表确需变化：停止把它当作组织迁移，遵守数据库设计准入和显式维护流程，先核查数据与队列。启动不自动迁移。

`scripts/release_lock.py` 及已冻结的架构性能工具/协议/阈值不属于本轮可改范围。冻结值和文件清单以对应证据为准，不以当前执行者方便为理由重建。

```text
核实当前真实源码、远程、安装包和共享环境；从状态账本第一项未验收任务继续。

不把 build 草稿、模拟测试、旧报告或跳过项视为实际验收。
每批完成调用方迁移、旧入口退役、相关说明、适用专项/恢复/实采/容量/性能、
完整发布与真实桌面，再更新状态和证据进入下一批。
保持配置、用户策略、生产数据和公共唯一流程；不改冻结工具或阈值。

已做验证、资源状态及恢复入口，不能用方案替代实现或虚写通过。

```

阶段结案模板、证据命名及最终完成条件见 [验收手册](acceptance.md)。如果用户本轮只要求文档审阅或交接，按当前用户范围交付文档，不自动把后续所有实现当作本轮授权新增执行。

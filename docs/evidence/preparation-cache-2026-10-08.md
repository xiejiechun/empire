# 数据准备检查结果 Redis 缓存

## 范围和工作区

用户要求数据预览不要每次重新检查，普通检查和主动重新检查的结果都保存在 Redis 7 天。实际入口为一级“数据准备”。本次只改变结果复用与显示，不改采集、归档、业务表或正式数据查询规则，不启动额外采集器或归档器；没有生产错误样本 ID，不执行错误清理。

开始时工作区干净；随后另一聊天移除了“股票代码变更记录”规划项，并修改了目录和说明。本次保留这些共享变更，不把该目录调整计为缓存功能贡献。发布验证针对最终共享源码。

## 实现和反例

完整报告保存在 Redis `<namespace>:preparation:report:<SHA-256>`；身份包含规范用途、去重排序后的证券、起止日期、软件版本、插件贡献及能力启停状态。结果可包含通过、失败及待验收项。报告恢复现行目录的规格对象；JSON 往返保持问题样例集合类型，正文大小上限 8 MiB，不缓存完整业务正文或凭据。`SET EX 604800` 原子覆盖结果和 TTL，读取不续期。

页面初次查询优先读取有效缓存，手动重新检查绕过读取并更新缓存；中断不写入部分报告，损坏、缺失、过期或不同范围/版本走同一检查入口。Redis 故障仍返回本轮结果，界面明确提示缓存失败。检查时间保持原始时点，缓存不证明之后的业务数据没有变化。只重启 Empire 可以复用仍运行的 Redis；服务或电脑重启会丢失缓存。

相关 43 项回归通过：`tests/test_preparation_cache.py`、`tests/test_preparation_progress.py`、`tests/test_preparation.py`，包含插件重建命中、不调用检查器、手动更新失败结果、范围/版本隔离、损坏与过期、取消、Redis 故障和代码集合规范化。

真实 Redis 使用随机测试命名空间验证 TTL=604800、缓存读取不改写、主动重查恢复 TTL、立即失效后重查；仅清理本次拥有的确切键，没有 SQL 或生产键写入。结果见 `build/preparation-cache-redis-live.json`。这是缓存协议验证，不代替全市场数据验收。

程序内“数据准备”主题、数据准备指南、架构、实现状态及文档审阅已同步；原页面关联仍精确指向该主题，无新增或退役页面。非采集功能，不适用来源下载、生命周期及归档专项准入；业务数据集与数据库结构未变化，不需要 SQL 迁移。

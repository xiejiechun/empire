## 2. 目标、事实与范围

目标：减少固定来源和证券身份的重复表达；使查询索引匹配实际入口；降低财报项目大状态的读取和写入开销；保持完整性、恢复、来源追溯和历史业务数据。

2026-10-03 对项目根目录配置指向的实际 MySQL 8.4.9 进行了只读核查：

| 观察 | 证据与解释 |
| --- | --- |
| 三张财报表体量 | information_schema 的 DATA_LENGTH 合计约 9.57 GB，是 InnoDB 分配统计，不是净 JSON 字节或精确行数 |
| 财报 SQL 状态 | balance/cashflow/income 的 JSON_STORAGE_SIZE 分别为 5,415,108 / 5,428,758 / 5,577,914 字节 |
| 日期浏览 | 利润表代表查询 EXPLAIN 估算约 227,844 行且 filesort；分红约 24,039 行且 filesort |
| 来源日期查询 | 停复牌 JSON 日期查询代表计划估算约 48,200 行且 filesort |
| 股票名称关联 | 关联条件为 source/market/code，stock 仅有 source/unified_code 主键及 source/source_symbol 唯一索引 |
| 核查限制 | 上述计划是估算，不是 EXPLAIN ANALYZE 或实际耗时。一次状态大小排序诊断出现 sort memory 错误，去掉排序后读取成功；不能据此声称正式页面已经同样失败 |

实施前重新核实，不能把本快照当永久基线；仅查询 Empire 的已登记表，真实库还存在其他应用的 router_* 表，禁止改动。

本轮包含：固定来源列精简、证券业务键统一、查询及索引优化、项目状态局部访问、停复牌来源日期索引化、显式维护工具和验证。

本轮不包含：全市场重新采集、分库分表、永久历史快照、财报全科目关系化、新增指标平台、分钟明细拆表、历史信号公告日期补造、稳定 security_id 与跨年代证券身份平台。财报常用 DECIMAL 指标及永久证券身份目录作为后续独立需求，不混入本次迁移。

## 3. 结构决策

### 3.1 固定来源归属

只有“当前已明确固定来源契约 + 迁移前全部行来源核实一致”的表才可删除 source。来源从行级字段移到数据集声明；统一归档器在 SQL 写入前验证 Envelope.source 与声明相符，错误来源拒绝，不能因 SQL 不再带 source 而混入数据。

| 表 | 本轮 source 决策 | 正式归属 |
| --- | --- | --- |
| stock | 删除 | sina |
| industry、industry_member | 删除 | ths |
| income_statement、balance_statement、cashflow_statement | 删除 | ths |
| dividend_plan、additional_issue、rights_issue、suspension_event | 删除 | tdx |
| stock_intraday | 删除 | kaipanla，实施前以插件声明核实精确字符串 |
| trade_calendar | 删除 | 以现行巨潮插件声明核实精确字符串 |
| finance_news | 保留 | 来源及 news_id 共同定义新闻身份，继续现行多来源命名空间契约 |
| collection_state | 保留 | 项目状态、数据集及来源归属校验 |
| app_setting | 无 source 变更 | namespace/kind/setting_key 保持 |

固定来源不只写在说明中：登记契约、启动结构检查、归档准入、查询绑定和维护清单必须使用同一权威声明，不能多处维护互相矛盾的常量。原 source 查询参数如需保留在公共接口，应精确验证固定来源，不得静默忽略不同参数。

迁移 preflight 检出额外来源立即失败并列出脱敏的表/来源/数量，不过滤、不覆盖、不自行挑选一个。切换来源以后须显式维护并保留迁移记录，不允许修改常量后把旧数据冒充新来源。

Envelope、项目登记、Redis 摘要命名空间和来源观测语义仍保留 source；SQL 精简不等于删除端到端来源信息。finance_news 的 source 是有用的身份字段，不为了统一外观强行删除。

### 3.2 证券身份：沿用 unified_code，避免新增身份系统

本轮选择现有 stock.unified_code 的正式编码契约，证券业务表统一为一个 unified_code 字段，替换重复 market/code 组合。不新造另一套格式；先找到现有构造、解析、合法市场及长度规则，提取到公共证券身份模块，形成唯一入口并测试。

unified_code 表达现行“市场 + 证券代码”的身份，不宣称是跨换码的永久 security_id。历史旧代码保留原身份；只有已有明确来源证明的别名流程允许映射，不能依靠名称或代码前缀自动合并。

stock 保留 unified_code、name 及确有独立来源意义的字段。market/code 改为由统一身份解析供 UI/API 使用；source_symbol、node 是否可退役必须逐调用点核实，能严格推导且无独立语义才删除。payload 中为验证来源响应所需的 market/code/source_codes/aliases 不机械删除，本轮精简的是 SQL 身份列；必须核验其与行键一致。

业务历史不得外键依赖会整份更新的当前 stock：没有当前股票记录的退市、旧代码和历史证券仍保留，查询使用 LEFT JOIN 并明确名称回退。禁止 INNER JOIN 导致历史记录从正式查询消失。

### 3.3 目标业务键和索引

| 表 | 目标主键或唯一键 | 查询索引/注意事项 |
| --- | --- | --- |
| stock | unified_code | 证券名称查询直接关联；来源符号若保留则检查唯一性 |
| industry | industry_code | 当前行业列表语义不变 |
| industry_member | industry_code, unified_code | 反向索引 unified_code, industry_code |
| 三张财报表 | unified_code, report_date | 日期浏览候选 report_date DESC, unified_code；单证券历史走主键 |
| stock_intraday | unified_code, trade_date | 当前按证券/日期访问走主键；没有实际全市场日期入口则不额外建索引 |
| dividend_plan/additional_issue/rights_issue | record_key | 单证券候选 unified_code,event_date；全市场候选 event_date DESC,unified_code,record_key |
| suspension_event | unified_code,suspended_at,resume_key,record_key | 生效日期查询按正式用途配置；所有不同复牌时间、说明/原因记录继续并存 |
| trade_calendar | trade_date | 缺日期仍未知，不能生成周末休市记录 |
| finance_news | source,news_id | 现有发布日期及重要性索引保留 |

索引是目标候选，不要求机械全部添加。必须以每个页面的真实过滤、排序、分页 SQL 验证，删除 source 后取消空代码 LIKE '%' 等无效过滤，消除可分支处理的 OR 条件。所有排序带唯一稳定尾键；如 unified_code 字典序与原 market/code 顺序不一致，明确保留原用户排序并据此调整实现。财报、事件先取有界业务键再读大正文。

先保留现有分页交互。游标分页仅在实际深分页瓶颈且能完整迁移页面交互时采用，不允许固定页数、截断结果或偷偷改变筛选语义作为提速。

### 3.4 停复牌来源日期

把 source_dates JSON 数组迁为唯一正式的来源日期关联表 suspension_source_date：source_date DATE + 与 suspension_event 完整一致的事件身份，主键按 source_date 在前；增加按完整事件身份访问的索引。日期表不是采集历史、逐轮状态或重复业务副本，而是业务记录的出现日期集合。

完整事件键由 unified_code,suspended_at,resume_key,record_key 组成，不假定单个 record_key 全表唯一。两表同事务归档，日期集合并集去重，相同事件和相同日期不执行写入；同一记录多次出现、未知复牌时间、同时间不同说明均保留。

正式按来源日期查询改为关联表 EXISTS/JOIN，跨日范围中同一事件只显示一次，分页前去重；生效时间查询仍查事件本体。源日期未知不能用空关联集合冒充“已确认无记录”。迁移前若 source_dates 为 NULL/空值或损坏，必须保留未知状态的明确表达并停止该记录完整性通过，不能补成当天；采用事件表 source_dates_known 标志表示已知性，具体有效空集合规则与现有契约一致。

迁移后删除旧 JSON 日期列及运行时读写路径，来源日期 API 可由新表重建相同逻辑输出。迁移不改变业务规范内容摘要；如实现确实改变规范摘要，执行第 5 节精确失效与版本升级。

### 3.5 项目状态：保持每项目一条

继续 collection_state(namespace,project_id) 一行，不新增按证券/页/轮次的 SQL 状态表。现有约 5 MB 的财报状态主要来自逐证券报告期集合，不能用最大日期或数量替代集合证明。

优先实现事务内有界路径读取和 JSON_SET/JSON_REPLACE 更新单个证券单元及进度，归档不再把全项目 payload 拉到 Python、复制、序列化后整体 UPDATE。公共接口区分全状态审计读取与归档单元读写，仍锁定正确项目行，保证来源/旧版本核验、业务写入和状态更新同事务。

动态 JSON 路径来自经过验证的业务身份并参数化；禁止原始来源字符串直接拼接 SQL。财报、分红等实际保存 units 的路径须逐一检查；manifest 与 progress 更新不能抹掉其他证券单元。相同状态不写；可信摘要命中仍完全免 SQL。

MySQL JSON 局部更新不保证所有场景都减少物理磁盘写入，JSON 扩容也可能重写；必须区分“已减少客户端传输/序列化”和“已测得磁盘收益”。本轮不默认压缩日期集合，除非对任意非季末日期、空集合及历史异常实现无损往返并证明收益。

## 4. 实施顺序与代码范围

1. 建立基线：文件摘要、实际 DDL/索引、插件归属、业务键及查询清单、各表来源分布、队列/隔离状态、体量与有界查询耗时。生产只读，不获取/输出凭据或保存成功响应全集。
2. 实现统一证券身份及固定来源契约；在隔离测试中证明错误身份/来源拒绝。
3. 同步修改 sql/schema.sql、数据集归档、正式查询、数据准备、插件启动检查、测试和维护工具。重点目录：contracts、plugins/datasets、plugins/data、plugins/infra、plugins/pipeline，UI 保留用户可读市场/代码展示。
4. 实现来源日期关系化、状态单元访问及查询索引；所有功能走原统一入队/归档链路，不添加旁路。
5. 实现一个显式维护入口，建议 scripts/migrate_business_schema.py，提供只读 preflight、迁移、verify、状态检查/失败恢复子命令；命名可沿项目习惯调整，但只保留一个总入口。
6. 在隔离 MySQL/Redis 完成从旧结构到新结构的迁移及故障演练，补齐专项与集成测试。
7. 同步程序内说明、页面关联、结构/恢复/来源文档和实现状态；生成交接报告。进入待独立审阅状态，不宣称正式部署已完成。

所有旧维护脚本逐一核查：仍有独立用途者更新为现行结构；被本入口取代者退役并移除文档调用。旧格式只在维护入口转换，运行时不保留自动识别/双写兼容层。

## 5. 迁移与故障恢复工程

### 前置条件

- 核实真实程序目录配置与根目录配置目标是否一致，不输出密码。连接目标必须明确限制到本次 Empire 表集合，router_* 等不在范围。
- 最终迁移时正常关闭 Empire，等待采集、归档和连接退出；确认 Stream 待归档业务消息为 0，隔离及分页暂存不存在未处理业务。队列非空则通过原归档链路排空，故障保留并停在此处，不清队硬迁移。
- 保存当前代码/包身份、DDL、非敏感配置摘要和精确范围基线。既有业务库按需要制作本机受控恢复副本并验证可恢复，空间不足则不得开始；不把业务副本或凭据提交 Git。
- 对 SQL 全量业务键、规范内容、版本、来源日期关系和覆盖证明生成流式有序摘要。分表统计精确记录数只是辅助，不能替代集合/内容核验。大表分块且有界内存。

### 执行与校验

- preflight 检查固定来源、证券映射一对一、目标键冲突、字段合法性、未知日期、旧契约版本及磁盘余量。发现冲突不给“自动去重”选项。
- 明确 MySQL DDL 隐式提交，不承诺一个 SQL 事务回滚全部表。采用可恢复阶段设计，记录本机迁移日志、源/目标结构身份及各阶段验证；重复执行必须识别已完成阶段且不重复转码。
- 如使用影子表，写入原理、空间峰值、切换边界和多表一致性必须演练；维护副本不成为运行时双写路径。只有全表转换和关系核验通过后才切换，不能逐表让新旧应用同时运行。
- 改变物理键不改变财报报告期、停复牌事件身份、资本事件 record_key、业务金额精度、NULL、来源版本及北京时间。摘要对比使用共同规范业务表示，不能直接比较不同物理布局的 SQL 行字节。
- 缓存/摘要若规范内容不变则保持；凡键或规范规则变化，只精确失效受影响数据集/来源摘要及到期索引，升级相应规范版本，并明确覆盖/完成标记的重建依据。不得删除共享 Redis、生产者代理 key、有效待归档消息或其他项目状态。
- 版本/完成状态转换与业务转换一起验证；不能把旧 manifest 留下冒充新规则验收通过。完成证明可在维护期间根据旧证据和新内容核验等价后无损转换，无法证明则标待核验，不自动启动全量补采。

### 回退

切换前失败保留旧正式表和应用路径；切换后未恢复业务写入时可按已演练步骤恢复旧表/包。恢复写入之后禁止直接回滚到旧快照丢失新增数据，必须先停写并制定增量保全/反向转换或前向修复。回退同步处理对应 Redis 摘要，不能用新摘要信任旧库。

旧维护副本在最终核验通过前保留；最终交接明确位置、用途、清理条件。删除副本是明确指定对象的维护动作，不能递归清理项目目录或共享数据库。

## 6. 必需验证矩阵

| 范围 | 必须覆盖的反例/证据 |
| --- | --- |
| 来源 | 固定来源正常；错误 Envelope.source；旧库出现额外来源；新闻不同来源同 news_id 共存 |
| 证券身份 | 沪深北、同代码不同市场、前导零、非法格式、旧代码/退市证券不在当前 stock、已有北交所别名；无证据不得合并 |
| 迁移 | 精确业务键及内容集合一致、金额/NULL/日期/版本不变；目标冲突拒绝；中断后恢复、重复执行、前后结构识别和回退演练 |
| 来源日期 | 单事件多日期、重复日期无写入、跨日分页不重复、未知日期不冒充无记录；不同原因/复牌时间分别保留；来源日与生效日不同 |
| 状态 | 更新证券 A 不丢 B；manifest/progress 与业务同事务；旧响应拒绝；不同证券并发/事务失败；冷缓存恢复与 Redis 丢失后 SQL 起点 |
| 归档 | 原始来源→规范化→Redis→统一归档→正式查询；重复无业务 DML、有效修订、迟到旧响应、SQL 提交后 Redis 失败重放；缓存可信命中零 SQL 且成功清队，损坏/过期回 SQL |
| 完整性 | 相同条数不同业务集合拒绝，旧记录必需字段补齐，分页失败不推进断点；采集继续入队下一批且不逐批等待归档；整轮确认不只看最高页 |
| 查询 | 全市场日期首/中/末页、单证券历史、代码前缀及市场筛选、股票名称关联、来源日及生效日查询；顺序稳定、历史记录无丢失 |
| 桌面 | 页面按需创建、插件独立启停、数据准备及范围查询、名称/代码显示、保留草稿、鼠标滚轮不改值 |

所有适用数据集逐项交付，不用一个通用假插件测试替代实际来源语义；明确不适用原因。常规相同财报归档不得读取或整体发送数 MB 状态，使用 SQL 捕获/传输字节及调用计数证明；不能只断言使用了 JSON_SET。

性能比较：同一隔离数据集、配置、查询参数及缓存状态下记录前后 EXPLAIN、实际耗时（建议各 5 次，列全部值/中位数）、读取行数（可测时）、客户端传输/峰值内存及新增索引体积。冷/热场景分开，索引创建成本另列。新日期索引应能有界定位目标页；全历史完整性审计可以扫描，但不得伪装成页面常规刷新。生产不做反复全表压测或刷新 buffer pool。

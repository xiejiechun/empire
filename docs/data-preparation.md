# 数据准备：一项工作只负责一种数据

进入一级“数据准备”，默认只显示需要开发的采集项目。每一行都是能够单独开发、采集、保存和补齐的一份数据，各自显示进度。用“工作类型”切换到整理、计算或核对项目。选中一行，先看“还差什么”；“要准备什么”说明本项范围、字段和时间要求；“逐项看看”解释检查结果；程序细节放在“详细检查记录”。

当前规划为 **85 项采集工作、12 项整理/计算/核对工作**。这表示工作拆分，不代表已经新增全部采集器；当前实际接入包括股票列表、交易日历、新浪最新新闻、通达信沪深 A 股历史停复牌、分红送转、增发、配股、公司全称更名、股票简称更名、同花顺利润表、资产负债表、现金流量表、当前行业及开盘啦分时与竞价。分时及分钟量额由现有开盘啦项目检查，不另列“分钟行情”采集任务；这不表示已核实完整分钟 OHLC 或复权口径。盘口及委托分析沿用现有历史盘口摘要和分钟买卖委托汇总，不另列日内五档盘口回放准备项；现有数据不表示全天各档盘口变化或完整交易所事件。各项已归档范围与数据准备结果独立显示，接入不表示全范围验收完成。尚未选定或核实的来源、授权、历史起点，必须在对应功能开发时确认，不能因为列进计划就声称可以采到。

## 怎样才算够用

页面先显示清单和本轮未确认状态，再按项目逐项更新；上方呈现当前检查项目及完成数量。进度轮询只读有界检查证据，不新增SQL、不读取完整业务正文。一轮检查中禁止叠加刷新，结束后可点击“重新检查”；切页取消后返回会重新核验，筛选及范围草稿保留。三表使用当前所选用途、证券与报告期，开盘啦分时按所选证券与交易日期，其他项目仍按自身范围。数据尚未检查完不能显示通过，旧范围快照不能冒充新范围。

交易日历的时效按每月 SQL 确认及可用的统一 Redis 摘要共同核验。缓存必须具有有效摘要、规范且不异常超前的版本、未过期索引，并匹配 SQL 已读取的完整月份内容；只能补充更晚确认，不掩盖缺日或异常 SQL 证据。Redis 未启用、不可用或证据无效时使用 SQL 确认；证据过旧则保留“待验收”，不为变绿额外写库或刷新缓存。历史范围和必需字段仍独立验收，未来安排仍允许来源修订。

以估值分析和通常的日频策略回测为基础用途。**一份数据可以由一个来源独立完成，不要求几个网站相互印证。** 检查的是能否正确取得、保存和使用这个来源提供的数据：必需字段、单位、去重、日期、分页和明显异常。来源自身记录、页数、返回范围及本地保存结果可用于检查，不强制拿第二个网站作证明。

- 按声明的证券、市场、日期范围验收。写清来源支持起点、已采区间和已知缺口，范围外的历史不足不否定范围内可用。声明范围内漏页、解析错误或缺少关键字段仍须处理；不能把自己的漏采改称来源限制。
- 字段分为必需和可选。来源事件编号、版本号、公告链接、精确到秒的公布时刻及完整旧版本历史不作通用门槛。没有来源编号时使用稳定业务组合键；没有版本号时明确内容比较和旧响应处理规则，不伪造来源版本。
- 时间精度按用途确定。停复牌、上市退市等成交约束按生效日期判断；日频数据通常不需要秒级时刻。财报、新闻等作为选股信号仍要说明公布日期或可用日期，不能提前使用。来源只提供修订后值可以采集使用，但须说明它不适合严格重放修订前的信号。
- 多来源比较、严格历史时点重放、盘中策略和审计溯源按实际需要增加，不作为所有采集项目默认的完成条件。保存新闻旧正文等明确以版本保存为目的的独立项目，仍按自身目的检查。

“已准备好”表示本项在声明范围和用途内可用，不表示所有年份、所有市场、所有策略都适用。相同内容免写、旧响应防覆盖、失败保留队列及归档成功清队等公共存储规则继续执行。

例如，“历史停复牌”必需市场/代码、停牌开始日期、复牌日期（来源尚未给出时可空）、全天/临停类型；名称、原因、公告时间和来源修订号可选。只用单一来源也可以通过，不要求先做公告采集或跨网站核对。通达信采集器按 2004-12-27 至今逐自然日核验完整响应、原始计数及业务键集合，来源日历关联完整后归档；数据准备同时检查现行完整性版本、连续覆盖和缺失来源日期，不以运行成功替代验收。停复牌插件仅遇源端完全重复时追加完整响应复核后决定能否合并重复；装满响应另按其容量边界扩容。这是该来源异常与边界处理，正常未装满且无重复的完整日只读一次，不能推广成所有采集默认双读。

## 怎么划分项目

- 一项采集工作只交付一份能够独立保存、独立补齐的数据，并由独立采集插件负责；网站同一栏目不是合并依据。例如指数成分名单和成分权重是两项，融资余额和融券余量是两项。
- 同一条记录的字段不机械拆开。日线中的开盘、最高、最低、收盘、成交量是同一条日线；一份分红送转方案中的现金和送转比例是同一方案；停牌及对应复牌是同一事件的起止。
- 不同输入、处理过程或完成范围单列。例如新闻最新正文、历史补采分别采集；新闻对应股票的识别、修改前正文的保留分别属于整理工作。
- 采集与计算分开。股价和股本分别采集，市值另外计算；PE/PB/PS 和股息率分别计算，不伪装成一个“估值采集”项目。
- 跨数据核对单列。行情漏了哪天，需要合并日历、上市、退市和停牌记录才能判断，另列“核对股票行情缺了哪些天”；三张财务报表之间的核对也单列。
- 仅用于配合的数据不阻止当前采集项目完成。计算和核对项目确实需要输入时，才显示“要先准备好哪些数据”。本项完成不代表使用它的回测或其他项目也完成。

## “6 项检查”不是“6 个采集功能”

一份数据仍要检查必需信息、重复、声明范围内的漏采、明显错误、更新情况及日期用途。这是检查同一份数据的质量，不要求一个采集器顺带开发其他数据。可选字段缺少应在检查说明中标注，不返回失败或等待补齐；不适用的检查说明原因后通过。

功能检查核对任务登记、保存规则、查询检查能力和当前版本测试记录。测试文件存在不算通过，代码变化后旧证据失效，测试跳过也不算通过。全部属于本项的检查通过，才显示“已准备好”。

一个项目 ID 只允许对应一个独立计划项；不同采集输出必须由独立采集插件负责，并各自登记任务身份与结果范围，不能用一个项目的成功给其他项目一起打勾。任意一个来源独立通过即可完成；第二个来源未接入或有问题不拖住第一个来源。多个来源也不能仅靠各过几项检查凑成通过。

## 当前新闻如何判断

“最新财经新闻正文”只负责最新窗口及之后的持续积累，检查新闻编号、标题、正文、分类、时间、重复和至少一页经校验后保存的确认。页面会展示已积累的起止时间；它不承诺历史全部完整，也不要求把新闻对应的股票识别出来。

这项检查通过，不会把“以前的财经新闻补采”“保存新闻修改前的内容”“找出新闻对应的股票”标成完成。这三项保持独立的未开发/未完成状态。当前表仍只更新当前来源版本；本次没有增加历史正文表或改变采集存储规则。

当前股票和交易日历保持原范围：股票全量列表与发布数量、标识和近期确认；日历从 1990-12-19 至下一年末逐日完整与逐月近期确认。SQL 旧确认可能落后于临时缓存，不能仅据此断言停更。最新新闻来源停更和软件漏采需要另行核实。

## 开发接入与验证

唯一目录入口是 [preparation_catalog.py](../src/empire/contracts/preparation_catalog.py)，按证券基础、事件、其他市场数据、处理工作等职责组织声明。Requirement 的 kind 区分工作类型，boundary 说明本项边界，related 仅表示配合使用，dependencies 只用于确实需要输入的处理项目。目录启动校验身份、引用、依赖环以及采集项目不依赖其他项目完成。

PreparationContribution 精确登记 requirement、query capability、来源、project_id/job_key/dataset、任务能力及专项测试。相同项目跨多个计划项会被拒绝。检查器返回本项 CheckEvidence；重复、未知或无效检查结果、查询超时和失败都不能通过。代码绑定的 JUnit 执行证据由正式发布门禁产生，随软件打包，不保存第二套人工完成状态。

新增来源继续遵守 [采集开发指南](collector-development-guide.md)。本次只调整工作规划、进度判断和只读检查，不新增实际采集器，不执行 DDL 或生产数据改写。集成测试使用独立来源与命名空间。验证包括项目边界、跨项目不能冒领进度、采集独立完成、计算依赖、新闻正文不冒充历史、页面筛选及原有回归。界面截图属于离屏检查，不等同真机操作验收。

随后按实际用途修正需求的[发布验证记录](evidence/data-preparation-practical-2026-09-28.json)：935 项通过、2 项因 Windows 符号链接权限跳过，完整发布门禁通过。验证覆盖单一来源独立通过、其他来源失败不阻塞、范围内漏采仍不通过，以及必需/可选字段展示；窗口布局为离屏检查。

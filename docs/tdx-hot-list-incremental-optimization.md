# 龙虎榜增量请求优化实施方案

2026-10-23 用户授权先编写实施文案并开始实施。本次只调整详情选择与复查频率；全市场日期目录仍每天读取，暂不引入尚未核实的按日全市场接口。

## 基线与目标

当前5580证券，近7日252个详情、近90日3650个详情；7134个来源无席位日期全部位于2002—2006年，另14个partial日期位于2024—2025年。旧策略每天预计16378次请求，失败重试与新增目录日期另计。

目标：保持每日19:30、代理优先、每日全部目录集合发现；将重复回查分摊到不同日期。固定当前数据集合估算每日平均约6556次，约减少60%，不承诺实际每天相等或耗时同比降低。

## 唯一选择规则

1. 初始化、强制重新采集以及显式日期范围继续请求范围内全部目录日期。
2. 新增日期、SQL无日头或pending日期立即请求，不受年龄或轮转分组限制；错误不伪装成空内容。
3. 最近7自然日（本轮日期减6日至本轮日期）每天请求全部状态的详情。
4. 第8～90自然日的详情按证券代码与榜单日期的SHA-256稳定散列分7组，每个自然日读取一个组。
5. 超过90日且状态为source_empty或partial的详情分30组，每个自然日读取一个组。30日为固定轮转周期，不是自然月；原始质量状态保留。
6. 超过90日的present详情不日常重读，仍通过显式范围重查发现独立修订。每日目录继续发现任意历史新增日期。

轮转槽采用北京时间日期序数取模，业务键采用完整证券代码与日期，禁止Python随机hash。边界优先按最近7日、8～90日、90日外判断，避免同一日期重复下载。所有正常完整响应仍一次请求，异常沿用共享有界重试。

## 生命周期与恢复

本轮through固定于启动日，跨日续采沿用原through和原分组。按日期倒序发布，失败不推进last_date；完成只在统一归档确认后显示。来源目录、SQL日头与统一归档仍为唯一正式路径，不增加逐日SQL状态、业务副本或新下载器。

无需维护“上次复查时间”：同日重跑选择相同组；Redis丢失后依据SQL日头重新选取当天组，可能重复但不漏掉pending。停机错过的轮转组在恢复后下一个7/30日周期内检查，不承诺停机期间仍满足日历时效，也不在重启时集中补发所有旧组。近7日每日、温数据每7日、旧缺失每30日的延迟以程序按日实际运行且请求成功为前提。

断点增加有界review_policy版本字段，冻结选择语义；旧完整断点开启新轮次时自然替换。旧未完成断点拒绝混用新规则，须先用旧版本完成或显式重新采集。本机旧初始化已完成后才部署新实现；不清生产断点。

## 存储与证明边界

无DDL、无新增数据集、无业务字段或业务唯一键变化。日期目录、规范内容摘要、旧响应保护、来源空明细保留旧参考规则全部沿用。collection_state中的原证券完整证明表示已采齐来源目录，不代表每条详情当天重查；新策略也不以旧完成证明声称修订及时性。无需重建已有内容摘要；断点中的策略版本只管理任务恢复。
